Git branching

branch, merge, rebase and conflict resolution

In plain words

Think of your project as a shared notebook. A branch is a photocopy of the notebook where you can scribble freely without disturbing anyone. When your work is ready, you bring your pages back into the main notebook. Merge glues your pages in and adds a note saying "joined here". Rebase rewrites your pages as if you had started from the latest version of the notebook. A conflict happens when you and a teammate changed the same line in different ways, and Git asks a human to decide which version is right.

How it works

A branch is just a pointer. Every commit in Git is a snapshot with an ID (a hash like a1b2c3d) and a link to its parent commit. A branch is only a small label that points to one commit. Creating a branch is instant and free, because Git copies nothing. That is why teams create a new branch for every feature or bug fix.

Branch naming and commit messages. Clear names help everyone. A common convention is type/short-description, and many teams use Conventional Commits for messages. These messages can later be used to generate changelogs automatically.

PrefixMeaningExample
featNew featurefeat(auth): add refresh token rotation
fixBug fixfix(orders): prevent negative quantity
refactorCode change, same behaviorrefactor(users): extract password hashing
chore / ci / docs / testTooling, pipeline, docs, testsci: cache npm in GitHub Actions

Merge. When main has not moved since you branched, Git can do a fast-forward: it simply moves the main label forward to your last commit. When main has new commits, Git creates a merge commit with two parents. History stays 100% true, but it can get noisy.

Rebase takes your commits and replays them on top of the latest main. The result is a straight, readable history. The price: rebase creates new commits (new hashes), so you are rewriting history.

The golden rule of rebase: never rebase a branch that other people are working on (like main). Rebasing your own feature branch is fine. Always use --force-with-lease instead of --force: it refuses to push if someone else pushed to the branch since you last fetched, so you can't wipe out their work by accident.

Branching strategies. Most modern teams use trunk-based development (or GitHub Flow): short-lived branches (1–3 days) off main, merged through pull requests, with main always deployable. Long-lived branches like develop or feature branches open for weeks (Git Flow) create huge, painful conflicts. Small and frequent beats big and rare.

Common mistakes
  • Rebasing or force-pushing a shared branch (main, develop). Teammates' histories break. Only rewrite your own branches.
  • Using git push --force instead of --force-with-lease, and deleting a teammate's commits.
  • Resolving conflicts by picking "mine" or "theirs" for the whole file without reading. Always merge the intentions and run tests afterwards.
  • Long-lived branches that drift from main for weeks. Merge main into them (or rebase) often, or better, keep branches small.
  • Committing secrets (.env) or build output (dist/). Add them to .gitignore from day one.

Interview questions

What is the difference between merge and rebase?

Merge joins two histories with a merge commit and keeps every original commit unchanged. Rebase replays your commits on top of another base, creating new commits and a linear history. Merge is safe for shared branches. Rebase gives cleaner history but rewrites commits, so use it only on branches that you alone own.

Why use --force-with-lease instead of --force?

--force overwrites the remote branch no matter what. --force-with-lease only overwrites it if the remote is still at the commit you last saw. If a teammate pushed in between, it refuses, so you don't erase their work.

How do you resolve a merge conflict safely?

Read both sides and understand what each change was trying to do. Write code that keeps both intentions, remove the conflict markers, then build and run the tests before continuing the merge or rebase. If it gets messy, git merge --abort / git rebase --abort and try again, or ask the author of the other change.

Remember Keep branches short-lived, rebase only your own branches, push with --force-with-lease, and treat every conflict as "merge two intentions, then run the tests".

Code review

review for correctness, maintainability and risk

In plain words

Code review is a second pair of eyes before code reaches real users, like a co-pilot reading the checklist before take-off. The reviewer is not there to show they are smarter. They ask three questions: Does it work? (correctness) Will we understand and change it easily in 6 months? (maintainability) What could go badly wrong in production? (risk). Reviews also spread knowledge: after a review, two people understand the code instead of one.

How it works

A review checklist. Good reviewers look at things in order of importance. Formatting comes last, because tools (Prettier, ESLint) should handle it automatically.

AreaQuestions to ask
CorrectnessDoes it do what the ticket asks? Edge cases: empty list, null, duplicates, very large input, concurrent requests?
SecurityIs the input validated? Is the user allowed to touch this record (ownership)? Are secrets or passwords logged or returned?
Data & performanceN+1 queries? Missing index? Multi-step writes without a transaction? Unbounded findMany?
RiskIs the migration backwards compatible? Can this be rolled back? Is there a feature flag? What breaks if it fails?
MaintainabilityClear names? Logic in the right layer (controller vs service)? Duplicated code? Will a newcomer understand it?
TestsAre the important paths and failure cases tested? Would the tests fail if the code were wrong?

Being reviewed. The author has a job too: keep the PR small (under ~400 changed lines is a good target, because review quality drops sharply after that), review your own diff first, explain the context in the description, and answer every comment (either change the code or explain why not). Common mistakes
  • Spending the review on style (spaces, quotes) while missing a security hole. Automate style; review logic.
  • "LGTM" (looks good to me) on a 2,000-line PR after 3 minutes. If a PR is too large to review, ask for it to be split.
  • Comments without a reason ("change this"). The author learns nothing and may disagree silently.
  • Not marking severity, so the author can't tell a blocking bug from a personal preference.
  • Reviewing only the diff and never the surrounding code or the migration that comes with it.

Interview questions

What do you look for first when reviewing code?

Correctness and risk first: does it do what's required, does it handle failure and edge cases, is it secure (auth, ownership, validation), can it corrupt data (transactions, race conditions, migrations)? Then maintainability and tests. Style last, and ideally only via automated tools.

How do you handle disagreement in a code review?

Explain the reasoning with concrete risks or examples, and listen to the other side. If it's a preference, not a problem, let the author decide. If it's important and you still disagree, talk synchronously (a short call) or ask a third person, then record the decision so it isn't argued again.

Why are small pull requests important?

Reviewers find far more issues in small diffs. Small PRs are reviewed faster, conflict less, are easier to roll back and make it clear what caused a bug. Large PRs tend to get a rubber-stamp approval.

Remember Review in order: correctness → security → data/risk → maintainability → tests → style. Be kind, label severity, and always explain why.

Pull requests

write clear PR descriptions

In plain words

A pull request (PR) is a request saying "please pull my branch into main". The description is a cover letter for your code. The reviewer was not in your head while you worked for two days. A good description tells them why the change exists, what changed, how to test it and what could go wrong, so they can review in 15 minutes instead of an hour. It also becomes documentation: a year later, someone running git blame will land on your PR to understand why the code looks this way.

How it works

Notice what makes the good one useful: the reviewer knows the business reason, which files matter, the rules (only PENDING), how to check it, and that the migration is safe. A reviewer can now ask smart questions, like "what about orders in PAYMENT_PROCESSING?"

The title should follow the same style as commit messages (type(scope): summary). If your team uses "squash and merge", the PR title becomes the single commit on main, so it matters.

In a real NestJS project

In an API project, reviewers especially want to know about contract changes (the frontend depends on them), migrations and new env vars. Include request/response examples. If you use @nestjs/swagger, mention which DTOs changed:

Common mistakes
  • An empty description, or only "see ticket". Tickets describe the problem, not your solution or the risks.
  • Mixing a refactor, a feature and a formatting change in one PR. The reviewer can't see the real change.
  • Not reviewing your own diff first, so leftover console.logs and commented-out code reach the reviewer.
  • Forgetting to mention breaking API changes or new environment variables. The deploy then fails or the frontend breaks.
  • Opening a PR while CI is red and asking for review anyway. Make it green first (or mark it draft).

Interview questions

What makes a good pull request?

It is small and focused on one change, has a clear title, explains why and what, gives testing steps, calls out risks (migrations, breaking changes, config), includes tests, and has green CI before review is requested.

Squash merge vs merge commit vs rebase merge?

Squash turns the whole PR into one commit on main: clean history, easy to revert, but loses the individual commits. A merge commit keeps all commits plus a merge point. Rebase-merge puts the PR's commits on main linearly. Many teams choose squash for simplicity and one-commit-per-PR reverts.

How would you split a large feature into several PRs?

Split by layers that are safe to ship alone: first an additive migration, then the service with tests, then the endpoint (maybe behind a feature flag), then the cleanup. Each PR is deployable and reviewable on its own, and nothing is user-visible until the flag is turned on.

Remember A PR description answers Why, What, How to test, and What could go wrong. Small, focused PRs get better reviews and safer deploys.

Docker

containerizing a NestJS + PostgreSQL app

In plain words

"It works on my machine" happens because every machine is different: another Node version, a missing library, a different OS. Docker packs your app together with everything it needs (Node, node_modules, system libraries) into a sealed box called an image. A running copy of that image is a container. The same image runs on your laptop, in CI and in production, like a shipping container that fits on any ship, train or truck. Docker Compose is a recipe that starts several containers together (your API + PostgreSQL) with one command.

How it works

Vocabulary.

TermMeaning
DockerfileThe build instructions for an image (a recipe)
ImageThe built, read-only package (the cake). Has a name and tag: shop-api:1.4.0
ContainerA running instance of an image (a slice being eaten). You can run many from one image
LayerEach instruction creates a cached layer. Unchanged layers are reused, so build order matters
VolumeStorage that survives container restarts. Essential for database data
RegistryWhere images are stored and shared (Docker Hub, GitHub Container Registry, AWS ECR)

Step 1: a naive Dockerfile (and why it is bad).

Problems: the image is over 1 GB (full Debian, dev dependencies, TypeScript sources), any code change re-installs all packages, secrets may be copied in, it runs as root, and npm as the main process doesn't forward shutdown signals properly.

Step 2: a production multi-stage Dockerfile. A multi-stage build uses one stage to build (with all the dev tools) and a separate, small stage to run. Only the final stage becomes the shipped image.

Why each choice matters:

  • Copy package*.json before the source code. Docker caches layers. If only src/ changed, the npm ci layer is reused and the build takes seconds instead of minutes.
  • npm ci, not npm install. It installs exactly what the lockfile says and fails if package.json and the lockfile disagree. Reproducible builds.
  • Separate prod-deps stage. The final image has no TypeScript, Jest or ESLint. The generated Prisma client lives in node_modules/.prisma, so we copy it explicitly from the build stage.
  • USER node. The official Node image ships a non-root node user. If someone exploits your app, they are not root inside the container.
  • CMD ["node", ...] in exec form. When the orchestrator stops the container, it sends SIGTERM to PID 1. With npm in between, the signal may not reach Node and the container gets killed hard after a timeout.

Step 4: Docker Compose for NestJS + PostgreSQL 16. We also add a one-off migrate service. It builds the build stage (which still has the Prisma CLI), runs migrations, and exits. The API starts only after migrations succeed.

Note the host name db in DATABASE_URL: inside the Compose network, each service is reachable by its service name. localhost inside the API container means "this container", not your laptop. This is the #1 beginner confusion.

Step 5: everyday commands.

In a real NestJS project

Many teams use Compose only for local dependencies (Postgres, Redis) and run Nest itself with npm run start:dev for fast hot reload. The production image is built in CI. Two Nest-side details make containers behave well:

Common mistakes
  • Baking secrets into the image (COPY .env or ENV JWT_SECRET=...). Anyone who pulls the image can read them. Pass secrets at runtime.
  • Using localhost in DATABASE_URL inside a container. Use the service name (db).
  • Not using a volume for Postgres, then losing all data on docker compose down. Or using down -v without thinking.
  • Ordering the Dockerfile so that COPY . . comes before npm ci, which destroys layer caching.
  • Shipping a 1 GB image with dev dependencies, running as root, with npm start as PID 1.

Interview questions

What is a multi-stage build and why use it?

A Dockerfile with several FROM stages. Early stages contain build tools (TypeScript, dev dependencies), and the final stage copies only the compiled output and production dependencies. The result is a smaller, faster, more secure image with less attack surface.

What is the difference between an image and a container?

An image is an immutable template (filesystem + metadata). A container is a running process created from an image, with its own writable layer. You can start many containers from the same image.

How do you make Docker builds fast?

Order instructions from least to most frequently changing: copy the lockfile and install dependencies first, then copy the source. Use .dockerignore to keep the context small, and use CI layer caching (e.g. the GitHub Actions cache backend for BuildKit).

Remember Multi-stage build, npm ci, lockfile copied first, non-root user, node dist/main.js as PID 1, secrets only at runtime, and use service names (not localhost) between containers.

CI

automatically lint and test code

In plain words

Continuous Integration (CI) is a robot that checks every change automatically. Each time someone pushes code or opens a pull request, a fresh computer downloads the code, installs it, and runs the linter, the type checker and the tests. If anything fails, the PR shows a red ❌ and can't be merged. Humans forget to run tests. Robots never forget. CI turns "I think it works" into "it is proven to build and pass tests on a clean machine".

How it works

GitHub Actions basics. A workflow is a YAML file in .github/workflows/. It is triggered by events (push, pull_request), contains jobs (which run in parallel by default on fresh virtual machines called runners), and each job has steps (shell commands or reusable actions).

Prepare scripts that CI can run. The default Nest lint script uses --fix, which silently changes files instead of failing. Add CI-friendly scripts:

The real workflow. Two jobs: a fast quality job (lint, types, unit tests) and an e2e job with a real PostgreSQL 16 database as a service container.

Some details explained:

  • localhost works here (unlike in Compose) because the job runs directly on the runner, and the service's port is mapped to the runner.
  • concurrency saves minutes: if you push 3 commits quickly, only the newest run continues.
  • permissions: contents: read follows least privilege. The workflow's token can't push code.
  • timeout-minutes stops a hanging test (e.g. an open DB connection) from burning 6 hours of CI time.
  • Running prisma migrate deploy in CI catches broken migrations before they reach production.

Make CI mandatory. On GitHub: Settings → Branches → add a branch protection rule (or a ruleset) for main: "Require status checks to pass" (select Lint, types & unit tests and E2E tests), "Require a pull request before merging", and "Require approvals: 1". Now nobody, not even admins if you choose so, can merge red code.

Common mistakes
  • Running eslint --fix in CI. It "fixes" the files on the runner and passes, while the repo stays unfixed. Use a check-only script.
  • Using npm install instead of npm ci, so CI may install different versions than the lockfile.
  • Flaky tests (random failures) that people "just re-run". Flakiness hides real bugs. Fix or quarantine them quickly.
  • CI that is not required by branch protection, so people merge on red "because it's probably fine".
  • Putting real production secrets in the CI test environment. CI should use throwaway values and a throwaway database.

Interview questions

What is Continuous Integration?

The practice of merging small changes into the main branch frequently, with every change automatically built and tested on a clean environment. It finds integration problems early, when they are cheap to fix.

How do you run tests that need a database in CI?

Start a real database as a service container (e.g. postgres:16-alpine in GitHub Actions) with a health check, apply migrations with prisma migrate deploy, run e2e tests against it, and clean data between tests. Using the same database engine as production avoids "works with SQLite, fails on Postgres" surprises.

What should a CI pipeline check for a TypeScript backend?

Formatting, lint (with zero warnings), type-check (tsc --noEmit), unit tests with coverage, a successful build, migrations applying to a clean DB, and e2e tests. Often also a dependency audit and a Docker build.

Remember Every push and PR runs lint, type-check, tests and build on a clean machine, and branch protection makes a green CI mandatory for merging.

CD

automatically build and deploy

In plain words

CI answers "is this code good?". Continuous Delivery/Deployment (CD) answers "get the good code to users, the same way every time". Instead of someone SSH-ing into a server at 11 pm and typing commands from memory, a pipeline builds a Docker image, labels it with the commit, runs database migrations, deploys it, checks that it is healthy, and can roll back. Continuous Delivery means every merge is ready to deploy, with a human pressing "approve" for production. Continuous Deployment means it goes to production automatically.

How it works

The typical pipeline.

The key idea: build once, deploy many times. The exact image tested in staging is promoted to production. You never rebuild for production, because a rebuild could pull different dependencies.

Tagging images. Tag with the git commit SHA (ghcr.io/acme/shop-api:3f9c2ab). Tags like latest are moving targets, so you can never tell which code is running and you can't roll back reliably.

The deploy workflow. It runs after CI succeeds on main, builds and pushes the image to GitHub Container Registry, then deploys to staging and production. Production uses a GitHub Environment with required reviewers, so it waits for a human approval.

Secrets like DEPLOY_SSH_KEY are stored per environment in GitHub (Settings → Environments), so the staging job can't read production secrets. On the server, the Compose file uses images instead of build:: the api service has image: ghcr.io/acme/shop-api:${TAG}, and the migrate service has image: ghcr.io/acme/shop-api:${TAG}-migrate with command: npx prisma migrate deploy. (The small runtime image has no Prisma CLI, which is why migrations use the second image.) The same idea works for other platforms: on Kubernetes you would run kubectl set image; on AWS ECS, Fly.io, Render or Railway you call their CLI or API with the new image tag.

Rollback. Because every image is tagged by SHA, rollback is "deploy the previous tag":

⚠️ Rolling back code is easy. Rolling back the database is not. That is why migrations must be backwards compatible (next point): the old code must still work with the new schema.

Deployment strategies.

StrategyHowPros / cons
RecreateStop old, start newSimple, but downtime
RollingReplace instances one by oneNo downtime; old and new run together for a while (so both must work with the DB)
Blue-greenStart a full new copy, switch traffic at onceInstant switch and rollback; costs double resources during deploy
CanarySend 5% of traffic to the new version, then increaseLimits damage of bugs; needs good monitoring and a smart load balancer
In a real NestJS project

Zero-downtime deploys require the app to shut down gracefully: stop accepting new requests, finish the ones in flight, close the DB pool. With app.enableShutdownHooks() (see the Docker point), Nest calls lifecycle hooks on SIGTERM:

Also expose the deployed version, so you can check what is live: e.g. pass APP_VERSION=${TAG} as an env var and return it from /health.

Common mistakes
  • Deploying the latest tag. You don't know what's running and can't roll back to a specific version.
  • Rebuilding the image separately for each environment. Production then runs something that was never tested.
  • Starting the new app before migrations run (code expects a column that doesn't exist yet → 500s).
  • No health check after deploy. The pipeline is green while users see errors.
  • Production secrets stored as repository-wide secrets that every workflow and branch can read. Use protected environments.
Practice exercise

At 16:05 you deploy commit a1b2c3d. At 16:10 error rates jump from 0.1% to 8%. The previous version was 9f8e7d6. The deploy included an additive migration (new nullable column). What do you do, in order?

Show answer
  1. Mitigate first, debug later: roll back the code to 9f8e7d6 (TAG=9f8e7d6 docker compose up -d api, or re-run the deploy job with that tag).
  2. Leave the migration in place. It only added a nullable column, so the old code ignores it. Rolling back the DB is riskier than leaving it.
  3. Confirm recovery: error rate back to normal, /health OK.
  4. Tell the team (incident channel), then investigate with logs and error tracking for a1b2c3d.
  5. Fix forward in a new PR with a test that reproduces the bug, and write a short post-mortem.

Interview questions

Continuous Delivery vs Continuous Deployment?

Continuous Delivery: every change that passes the pipeline is releasable, but a human decides when to push to production. Continuous Deployment: every passing change goes to production automatically, with no manual step.

Why tag images with the commit SHA?

The tag is immutable and traceable: you know exactly which code runs, you can promote the same artifact from staging to production, and rollback means redeploying a known previous tag.

How do you achieve zero-downtime deployments?

Run several instances and replace them gradually (rolling or blue-green) behind a load balancer, use readiness checks so traffic only reaches healthy instances, shut down gracefully on SIGTERM, and keep database migrations backwards compatible so old and new versions work at the same time.

Remember Build once, tag by SHA, promote the same image from staging to production, migrate before switching traffic, health-check after, and always have a one-command rollback.

Production migrations

safe database migration strategy

In plain words

Changing a production database is like renovating a shop while customers are inside. You can't close the doors, knock down a wall and hope nobody gets hurt. You put up the new shelf first, move the products over, and only then remove the old shelf. Code can be rolled back in seconds. A dropped column with a million rows of customer data cannot. So every migration must be planned so that the old code and the new code can both run against the database at the same time.

How it works

Prisma commands: which one where.

CommandWhereWhat it does
prisma migrate devYour laptop onlyCreates a new migration from schema changes, applies it, may reset the dev DB
prisma migrate dev --create-onlyLaptopGenerates the SQL file without applying it, so you can edit it
prisma migrate deployCI, staging, productionApplies pending migration files in order. Never generates or resets anything
prisma migrate statusAnywhereShows applied / pending / failed migrations
prisma migrate resolveProduction (incident)Marks a failed migration as rolled back or applied after you fixed it by hand
prisma db pushPrototyping onlySyncs schema without migration history. ❌ Never in production

Common mistakes
  • Running prisma migrate dev or db push against production. They can reset or drift the schema. Production uses only migrate deploy.
  • Merging a migration without reading its SQL, so a rename silently becomes DROP + ADD.
  • Editing a migration file that was already applied somewhere. Its checksum changes and environments disagree. Create a new migration instead.
  • Dropping a column in the same release that stops using it. During a rolling deploy, old instances still query it and crash.
  • One giant UPDATE on millions of rows inside a migration, locking the table for minutes. Backfill in batches, outside the migration.

Interview questions

What is the expand/contract pattern?

A way to make breaking schema changes without downtime: first expand (add new structures, keep old ones), deploy code that works with both, backfill data, switch reads to the new structure, and only later contract (remove the old structures). Every step is backwards compatible.

Why must migrations be backwards compatible?

During a rolling deploy, old and new app versions run at the same time against the same database, and you may need to roll the code back. If the schema change breaks the old code, either situation causes errors in production.

Difference between prisma migrate dev and prisma migrate deploy?

migrate dev is for development: it detects schema changes, creates new migrations, and may reset the database. migrate deploy only applies existing, committed migration files in order, which is safe and predictable for CI and production.

Remember Read every generated SQL file, only add things in one release and remove them in a later one (expand → contract), backfill in batches, and use only prisma migrate deploy in production.

Environment configs

dev, staging and production

In plain words

Your app runs in several places: your laptop (development), a copy of production for final testing (staging), and the real thing (production). The code is the same everywhere. What changes is the configuration: which database, which API keys, how much logging. Think of an actor: the same actor, but a different costume for each stage. Configuration lives in environment variables, outside the code, and the app should refuse to start if an important setting is missing, instead of crashing at 3 am on the first request.

How it works

What usually differs per environment:

SettingDevelopmentStagingProduction
DatabaseLocal Docker PostgresSeparate staging DB (anonymized data)Managed Postgres with backups
Secrets.env file (fake values)Secret manager / CI environmentSecret manager / CI environment
Log leveldebug, prettydebug or info, JSONinfo, JSON
CORS originshttp://localhost:5173https://staging.shop.comhttps://shop.com

The principle (from the "12-factor app"). Store config in environment variables. Never write if (env === 'production') all over your code. Instead, make each behavior a setting (SWAGGER_ENABLED=true), and let each environment set it. Then staging can really behave like production.

Step 1: files. Commit an example file with every variable and fake values. Ignore the real ones.

Step 2: validate at startup. With @nestjs/config you can pass a validate function. If anything is missing or wrong, Nest fails to boot with a clear message. A crash at deploy time is much better than a crash at the first login.

Step 3: read config through a typed service, not process.env.

NODE_ENV vs APP_ENV. Many libraries (Express, some loggers) switch to slower debug behavior unless NODE_ENV=production. So set NODE_ENV=production in both staging and production (staging should behave like production), and use a separate APP_ENV to know which deployed environment you are in (for example, to tag errors in Sentry).

Where do real secrets live? Not in Git and not in the Docker image. Use GitHub Environments secrets for the pipeline, and the platform's secret store at runtime (AWS Secrets Manager / SSM, GCP Secret Manager, Doppler, Vault, or your PaaS's env settings). Each environment has different secrets, so a leaked staging key can't touch production.

In a real NestJS project

As the app grows, group settings by feature with registerAs and inject a typed config object. No more string keys scattered around:

Register it with ConfigModule.forRoot({ load: [authConfig], ... }) (or ConfigModule.forFeature(authConfig) inside AuthModule).

Common mistakes
  • Committing .env to Git. Even if you delete it later, it stays in history. Rotate any secret that was ever committed.
  • Reading process.env.X everywhere with no validation, so a typo in a variable name shows up as undefined in production.
  • Code full of if (NODE_ENV === 'production'), so staging never tests the production code paths.
  • Sharing the same database or API keys between staging and production.
  • Printing the whole config at startup "for debugging", leaking every secret into the logs.

Interview questions

How do you manage configuration across environments in NestJS?

Use @nestjs/config with environment variables, validate them at startup (class-validator or Joi), read them via ConfigService or typed registerAs namespaces, commit only .env.example, and inject real secrets from a secret manager or the deployment platform per environment.

Why validate environment variables at startup?

To fail fast. A missing or malformed variable stops the deploy immediately with a clear message, instead of causing confusing runtime errors later, possibly only on a rarely used code path.

What is the purpose of a staging environment?

To test the exact artifact and configuration shape that will go to production, with production-like infrastructure but separate data and secrets. It catches deployment, migration and integration problems before real users see them.

Remember Same code, different config: env vars validated at startup, typed access through ConfigService, behavior controlled by settings (not "if prod"), and separate secrets per environment.

Monitoring

error tracking and uptime checks

In plain words

Once your app is live, you can't watch it with your own eyes. Monitoring is the dashboard of a car: the speedometer (traffic), the temperature light (errors), the fuel gauge (database connections). Uptime checks are a friend who calls your shop every minute and tells you if nobody answers. Error tracking is a black box recorder: when something crashes, it saves exactly what happened (stack trace, request, user, version). The goal: you find out about problems before your customers tell you on Twitter.

How it works

The building blocks.

Tool typeAnswersExamples
Health endpoint"Is this instance alive and can it reach the DB?"@nestjs/terminus
Uptime check"Can users reach the API from the internet?"UptimeRobot, Better Stack, Pingdom, Checkly
Error tracking"What crashed, where, for whom, since which release?"Sentry, Rollbar, Bugsnag
Logs"What exactly happened in this request?"Pino JSON logs → Loki, CloudWatch, Datadog
Metrics"How many requests, how slow, how many errors, over time?"Prometheus + Grafana, Datadog, OpenTelemetry
Alerting"Wake someone up when it matters"PagerDuty, Opsgenie, Slack alerts

Google's SRE book suggests watching four "golden signals" for every service: latency (how slow), traffic (how many requests), errors (how many fail), saturation (how full: CPU, memory, DB pool).

Step 1: a health endpoint with Terminus.

The orchestrator (Docker, Kubernetes, ECS) uses these endpoints: if liveness fails, restart the container; if readiness fails, stop sending it traffic. Don't put the database check in liveness: if the DB is down, restarting every API container won't fix it and only makes things worse.

Step 2: uptime checks from outside. Your health endpoint can say "OK" while DNS, TLS or the load balancer is broken. An external service calls https://api.shop.com/health every minute from several regions, and alerts you (Slack, SMS) after e.g. 2 failures in a row. Also monitor the TLS certificate expiry date. Expired certificates still cause big outages every year.

Step 3: error tracking with Sentry. The official @sentry/nestjs SDK captures unhandled exceptions with stack traces, request data and the release version.

Sentry groups identical errors into one issue, tells you "first seen in release a1b2c3d", and counts affected users. Expected errors like a 404 or a 400 validation failure are not bugs. Report 5xx errors, not every HttpException, or the real problems drown in noise.

Step 4: structured logs. Logs should be JSON with a request ID, so you can search "all logs for request X" or "all errors for user 42".

Step 5: alert on symptoms, not on everything. Good alerts are rare, urgent and actionable. "Error rate > 2% for 5 minutes", "p95 latency > 1 s for 10 minutes", "uptime check failed twice". Bad alerts: "CPU > 70% once" (nobody can act on it, so people start ignoring all alerts). Each alert should link to a short runbook: what it means and the first steps to take.

In a real NestJS project

Combine logs and error tracking in one global filter: log every server error with context, and return a safe message to the client. Never leak stack traces in production responses.

If you register your own catch-all filter like this, use it instead of SentryGlobalFilter (or decorate its catch method with @SentryExceptionCaptured()), so errors are not reported twice.

Common mistakes
  • A /health endpoint that always returns 200 without checking anything, so it says "healthy" while the database is down.
  • Checking the database in the liveness probe, causing restart storms when the DB has a short hiccup.
  • Sending every 4xx to Sentry. Quota gone, real bugs invisible.
  • Logging passwords, tokens, full card numbers or entire request bodies. Logs are copied to many systems and kept for a long time.
  • Too many noisy alerts, so the team mutes the channel and misses the real outage.

Interview questions

What is the difference between liveness and readiness checks?

Liveness asks "is the process stuck or broken?"; failing it makes the orchestrator restart the container. Readiness asks "can this instance handle traffic right now?" (DB reachable, warmed up); failing it only removes the instance from the load balancer until it recovers.

Logs, metrics and traces: what's the difference?

Logs are detailed records of individual events. Metrics are numbers aggregated over time (request rate, error rate, latency percentiles), cheap to store and good for alerts. Traces follow one request across services and show where time was spent. Together they are called the three pillars of observability.

What makes a good alert?

It fires on a user-visible symptom (errors, latency, downtime), not on every internal blip; it is urgent and actionable; it has a clear owner; and it links to a runbook. If an alert is regularly ignored, fix or delete it.

Remember Health endpoints (live vs ready), external uptime checks, error tracking tagged with environment and release, structured logs without secrets, and a few actionable alerts on user-visible symptoms.
