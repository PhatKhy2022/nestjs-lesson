Trade-offs

compare simplicity, flexibility, performance and cost

In plain words

Every technical choice is like buying a car. A sports car is fast but expensive and has no space. A van carries a lot but is slow to park. There is no "best car", only the best car for your situation. Junior developers often ask "what is the best way?". Senior developers ask "best for what? For whom? Under which constraints?" Then they compare options honestly on a few dimensions, usually simplicity, flexibility, performance and cost (money and people's time), choose one, and write down why.

How it works

The four dimensions.

DimensionQuestionHidden cost if ignored
SimplicityCan a new team member understand and change it in a day?Slow onboarding, bugs from misunderstanding
FlexibilityHow easily can it adapt to likely future needs?Rewrites when requirements change
PerformanceIs it fast enough for the real load?Slow pages, timeouts, bigger servers
CostMoney (infrastructure, licenses) + time to build + time to operateA "free" tool that needs one engineer full-time to babysit

These pull against each other. More flexibility usually means more abstraction, which hurts simplicity. More performance often means caching or extra infrastructure, which adds cost and complexity. You can't maximize all four, so you must choose which ones matter most right now.

Case study: product search. The shop has 20,000 products. Product asks for "search by name". Let's compare three options.

A: containsB: pg_trgmC: Search engine
Simplicity✅✅✅✅✅❌ new system + sync
Flexibility❌ substring only✅ fuzzy similarity✅✅✅ ranking, facets, typos
Performance at 20k rows✅✅✅✅✅
Performance at 5M rows❌✅✅✅
Cost≈ 0≈ 0 (one migration)$$ + on-call + sync code

Decision: start with A (ship today), add B when the table grows or queries slow down (a 1-hour change, no API change), and only consider C if the business needs ranking and typo tolerance. Note the important trick: the API contract (GET /products?search=...) stays the same for all three, so we can upgrade later without breaking the frontend. Keeping a decision reversible is itself a trade-off you can choose.

One-way vs two-way doors. Some decisions are easy to undo (a library for date formatting, an internal function shape). Decide those quickly. Others are very expensive to undo (the database engine, the public API shape, how money is stored, splitting into microservices). Slow down for those, involve more people, and write an ADR (see Documentation).

Avoid the two classic extremes.

The principle is called YAGNI ("You Aren't Gonna Need It"): don't build for imagined futures. But don't confuse it with "no design": put clean boundaries where you have real evidence of change.

In a real NestJS project

A common real trade-off: sending the order confirmation email inside the request, or via a queue (BullMQ + Redis).

For an MVP with 50 orders a day, option 1 with a try/catch that logs failures may be the right call. When orders grow, or when emails become business-critical, the queue is worth its cost. A senior engineer can explain both sides and when the answer flips.

Common mistakes
  • Choosing technology because it is popular or fun ("let's use Kafka") instead of because the problem needs it.
  • Only comparing performance and ignoring operating cost: who gets paged at 3 am when the new system breaks?
  • Presenting a decision with only benefits. If you can't name the downsides, you haven't understood the option.
  • Treating irreversible decisions as quick ones, and reversible decisions as week-long debates.
  • Optimizing for a scale you don't have ("we need microservices") while the real problem is shipping features.

Interview questions

Tell me about a technical trade-off you made.

Use a structure: the context and constraints (team size, deadline, load), the options you considered, how they compared (simplicity, flexibility, performance, cost), what you chose, the downside you accepted, and what would make you change the decision. Interviewers want to hear that you saw the downsides, not that you picked the "right" tool.

How do you avoid over-engineering?

Design for known requirements, keep decisions reversible where possible, add abstractions only when there is a second real use case or a clear change pattern, and prefer boring, well-understood tools. Revisit the design when evidence (load, new requirements) appears.

What is the difference between a one-way and a two-way door decision?

A two-way door can be reversed cheaply (try it, roll back if wrong), so decide fast. A one-way door is costly or impossible to reverse (data model, public API, core infrastructure), so it deserves more analysis, more reviewers and written documentation.

Remember There is no "best", only "best for this context". Name the options, compare simplicity, flexibility, performance and cost, state the downside you accept, and keep the decision reversible when you can.

Code ownership

understand the whole feature, not only your file

In plain words

A plumber who replaces one pipe but never checks whether the water now leaks into the kitchen hasn't really fixed anything. Code ownership means you care about the whole result, not just "my file compiles and my ticket is closed". You follow the data from the button the user clicks, through the API, the database, emails, reports and the admin panel. And you stay responsible after the merge: you watch it go to production and check that it actually works for users.

How it works

"Done" means more than "merged".

Junior "done"Owner "done"
The endpoint returns 200 on my machineEdge cases handled, tests cover failure paths
My file is changedEvery place that reads or writes this data still behaves correctly
PR mergedDeployed, verified in production, dashboards/errors checked after release
Ticket closedDocs, .env.example, API consumers and support team updated

Case study: a "small" change that broke invoices. Ticket: "Add a 10% discount code at checkout." A developer changes only the order total:

Checkout works. Two weeks later: the PDF invoice shows the undiscounted price (it recalculates from items), the accounting CSV export doesn't have a discount column, refunds give back the full item price (more than the customer paid!), and one coupon was used 4,000 times because nothing limited it. Each of those lives in a different file the developer never opened.

How an owner approaches the same ticket: trace the data.

Now the plan includes: store subtotal, discountAmount and total on the order (one source of truth); make invoice and refunds use stored amounts; add maxRedemptions and a unique (couponId, userId) constraint; add the column to the export; tell analytics that revenue is now total, not the sum of items. Twenty minutes of tracing saved two weeks of production bugs.

Ask questions before writing code. Owners clarify the requirement with product/QA: Can coupons stack? Do they apply to shipping? What happens on partial refund? What if the coupon expires while the user is on the checkout page? Each answer is a test case.

Ownership after deploy.

In a real NestJS project

Nest's modular structure helps you find "who depends on what". Look at a module's exports and search who imports it. Also, design so that one concept has one owner in the code: a single method computes order amounts, and everyone else uses it.

Common mistakes
  • "That's not my file." Bugs don't respect file or team boundaries; users experience the whole feature.
  • Closing the ticket at merge and never checking production.
  • Duplicating business logic (prices, permissions) in several places, so a change has to be remembered everywhere.
  • Not asking clarifying questions and implementing a guess of the requirement.
  • Owning without communicating: changing an API field silently and breaking the mobile app.
Practice exercise

Ticket: "Let users change their email address." Before writing code, list every part of the system you would check or change.

Show answer
  • Validation & uniqueness: case-insensitive unique email (store lowercase or use citext), race between two users choosing the same email (rely on the DB unique constraint, catch Prisma P2002 → 409).
  • Verification: send a confirmation link to the new address; only switch after confirmation. Notify the old address (security: account takeover).
  • Auth: require the current password; do JWTs or sessions contain the email? Revoke refresh tokens if needed. Does login use email as the username?
  • Other systems: payment provider customer email (e.g. Stripe), newsletter/CRM sync, invoices (historical invoices keep the old email).
  • Audit: log the change (who, when, from which IP) without logging tokens.
  • Frontend / support: UI messages, support documentation, rate limit on the endpoint.

Interview questions

What does "ownership" mean to you as an engineer?

Being responsible for outcomes, not just code: understanding the requirement and the whole flow, considering every consumer of the data, testing failure paths, shipping it, verifying it in production, and fixing or following up when something goes wrong, even outside my original scope.

How do you get familiar with an unknown part of the codebase quickly?

Follow one real request end-to-end: start at the route, read the controller, service, Prisma queries and events it triggers. Search for usages of the key models and fields, read the tests, check recent PRs and git log for that area, and ask the people who changed it last. Draw a small map as you go.

Your feature works but you notice a bug in a neighboring module. What do you do?

I don't ignore it. If it's small and clearly related, I fix it in a separate PR. If it's bigger or another team owns it, I create a ticket with reproduction steps and tell the owner directly. If it's a serious production risk, I raise it immediately.

Remember Map the whole flow before coding, keep one source of truth for each business rule, and your job ends when users get a working feature in production, not when the PR is merged.

Technical debt

identify and prioritize debt

In plain words

Technical debt works like a credit card. Taking a shortcut (no tests, a quick hack, copy-paste) lets you "buy" a feature today. But you pay interest: every future change in that area is slower and riskier. A little debt taken on purpose to hit an important deadline can be smart. Debt you don't know about, or never pay back, grows until the team spends all its time fighting the code instead of building features. The senior skill is not "zero debt"; it's knowing which debt is expensive and paying that first.

How it works

Kinds of debt (based on Martin Fowler's "debt quadrant"):

RecklessPrudent
Deliberate"We don't have time for tests." (forever)"We ship without bulk import now and do it properly next sprint." (ticket created)
Inadvertent"What's a transaction?""Now that we understand the domain, we see a better design."

Identifying debt. Look for signals, not opinions like "this code is ugly":

  • Changes in one area are always slow or always cause bugs.
  • People avoid touching a file ("don't touch OrdersService, it breaks").
  • The same bug comes back, or the same logic exists in several places.
  • Outdated dependencies with known vulnerabilities, or an unsupported Node version.
  • Missing tests on critical paths (payments, auth), no transactions on multi-step writes, money stored as Float.

Use data: files that are both complex and changed often ("hotspots") are where debt costs the most interest. Debt in code nobody touches costs almost nothing.

Prioritizing. Write each debt item as problem → impact → fix → cost, then score it. A simple formula many teams use: priority ≈ (impact × frequency) / effort, with risk as an override (security and data-loss issues jump the queue).

Debt itemImpactHow often it hurtsEffortPriority
Order creation without a transaction (stock can go wrong)High (data)Every failureS🔴 Now
OrdersService 1,800 lines, every feature touches itMediumWeeklyL (in steps)🟠 Plan, do gradually
Prices stored as FloatHigh (money)Rounding issues monthlyM (migration)🟠 Next quarter
Old admin module, ugly but stable, rarely changedLowRarelyL🟢 Leave it

A debt register entry makes debt visible and discussable with product managers in their language (time, money, risk):

Paying it back. Three strategies that work in practice:

  • Boy Scout rule: leave the code a little cleaner than you found it, in the area you are already changing.
  • Budget: reserve ~10–20% of each sprint for debt from the register.
  • Attach debt to features: "Adding refunds will take 5 days, or 3 days after we fix TD-014 (2 days), and future features also get faster." This makes the business value visible.
In a real NestJS project

Make deliberate debt traceable in code, and let tools stop new debt from sneaking in:

Common mistakes
  • Calling every piece of code you dislike "tech debt". Debt is about cost to the business, not taste.
  • Asking for a "refactoring sprint" with no explanation of impact. Product says no, and the debt stays.
  • Rewriting a stable module nobody touches, while the painful hotspot stays as it is.
  • Taking deliberate shortcuts without writing them down, so "temporary" becomes permanent.
  • Big-bang rewrites ("we'll rebuild it from scratch in 3 months") that take 12 and still miss features.
Practice exercise

You have time for two items this sprint. Choose and justify: (1) upgrade NestJS 9 → 11 (Node 16 is end-of-life and has known CVEs), (2) rename confusing variables in reports.service.ts (changed twice a year), (3) add tests to the payment webhook handler (changed monthly, caused 2 incidents), (4) replace Moment.js with date-fns across the app, (5) split a 2,000-line UsersService that every sprint touches.

Show answer

Pick (3) and (1).

  • (3) Payment webhook tests: high impact (money, incidents already happened), changed often, small effort. Clear win.
  • (1) Runtime upgrade: security risk on an end-of-life runtime overrides normal scoring; the longer you wait, the bigger the jump.
  • (5) is important but large. Start it gradually with the Boy Scout rule (extract one service each time a feature touches it) instead of a single sprint.
  • (4) works today; do it opportunistically. (2) is rarely touched: low interest, low priority.

Interview questions

What is technical debt?

The future cost of choosing a quicker or easier solution now instead of a better one. Like financial debt, it has "interest": extra time and risk in every future change to that area. It can be deliberate (a conscious trade-off) or accidental (lack of knowledge, changing requirements).

How do you convince a product manager to prioritize technical debt?

Translate it into business terms: hours lost per week, incident risk, slower delivery of upcoming features, security exposure. Propose a concrete, scoped fix with an estimate, ideally linked to an upcoming feature it will speed up, rather than a vague "cleanup sprint".

How do you decide which debt to pay first?

By impact × frequency relative to effort: debt in hotspots (complex and frequently changed code) and debt that risks security or data integrity comes first. Stable code that rarely changes can usually wait, even if it's ugly.

Remember Debt is a tool, not a sin. Make it visible, measure its interest (hotspots, incidents, hours lost), pay the expensive debt first, and explain it in business terms.

Refactoring

improve code without changing behavior

In plain words

Refactoring is tidying a messy kitchen while still serving meals. You move one pot at a time to a better shelf, and after every move the kitchen still works. You don't empty the whole kitchen onto the floor. The key rule: the behavior does not change. Same inputs, same outputs, same side effects. Only the structure gets better, so the next change is easier. If you change behavior at the same time, it's not refactoring anymore, and when a bug appears, nobody can tell whether it came from the cleanup or from the new behavior.

How it works

The safe refactoring loop.

  1. Lock the behavior with tests. If there are no tests, write characterization tests: tests that record what the code does today (even if it looks odd).
  2. Make one small change (rename, extract a function, move a method).
  3. Run the tests. Green → commit. Red → undo, smaller step.
  4. Repeat. Never mix refactoring and new features in the same commit (and ideally not in the same PR).

Before: a typical "grown over time" function.

Problems: any, deep nesting, magic numbers (24000 is an exchange rate, 500000 is a free-shipping threshold), unclear names (s). Adding a new rule here is scary.

Step 1: characterization tests that record current behavior, including weird cases:

Step 2+: small refactorings, each one followed by a green test run and a commit:

  • Replace magic numbers with named constants.
  • Replace nested conditionals with guard clauses (return early).
  • Extract function for each rule.
  • Add types instead of any.

The tests still pass without any change, which is the proof that behavior is identical. Now a new rule ("express is free for VIP customers") is a one-line, low-risk change in internationalShipping.

Common refactorings, with names (from Martin Fowler's catalog, useful vocabulary in reviews):

RefactoringWhen
Rename variable/functionName doesn't explain the purpose (s, data2, handle())
Extract function / classA block needs a comment to explain it, or a class has several responsibilities
Guard clausesDeeply nested ifs
Introduce parameter objectMany parameters travel together (page, limit, sort, order)
Replace conditional with map/polymorphismLong switch on a type that keeps growing
Move functionLogic lives in the wrong layer (business rules in a controller)

Large refactors: the strangler fig pattern. For a big legacy module, don't rewrite it at once. Build the new version next to the old one, route a small part of the traffic or one use case to the new code, and grow it until the old code can be deleted. Each step is deployable and reversible.

In a real NestJS project

A frequent refactor is splitting a "god service". Nest's DI makes it safe: extract a new provider, inject it into the old service, and move one method at a time. The controller and its e2e tests don't change, so they guard the behavior.

Common mistakes
  • Refactoring without tests and "checking manually". You will miss an edge case.
  • Mixing refactoring with a behavior change in one PR. Reviewers can't tell which diff lines are supposed to change behavior.
  • "Fixing" odd behavior during a refactor. That odd behavior may be something a client depends on. Record it, then change it on purpose in a separate PR.
  • Big-bang rewrites instead of small, continuous steps.
  • Refactoring code nobody needs to change, just for taste, while real hotspots stay messy.

Interview questions

What is refactoring, and how is it different from rewriting?

Refactoring is a series of small, behavior-preserving changes to improve structure, each verified by tests. Rewriting replaces the code with a new implementation, usually changing behavior along the way and carrying much more risk.

How do you refactor code that has no tests?

First add characterization tests around the part you'll change, recording current behavior (high-level e2e or integration tests are often easiest). Then refactor in small steps, running the tests after each step. Use safe automated IDE refactorings (rename, extract) where possible.

When should you not refactor?

When the code is stable and rarely changed, when you're under a critical deadline for an unrelated change (note it as debt instead), when there's no way to verify behavior yet, or when the code is about to be deleted.

Remember Tests first, tiny steps, run tests after each step, commit often, and never mix refactoring with behavior changes.

Documentation

document important decisions and complex behavior

In plain words

Code tells you what the system does. It almost never tells you why it does it that way, what alternatives were rejected, or how to run it. That knowledge lives in people's heads, and people go on holiday, change teams or forget. Documentation is a letter to your future teammates (and to future you). The goal is not to document everything. It's to document the things that are expensive to rediscover: decisions, tricky business rules, setup steps and what to do when things break.

How it works

What to document, and where.

TypeAnswersWhere
READMEWhat is this? How do I run it, test it, deploy it?README.md in the repo
ADR (Architecture Decision Record)Why did we choose X over Y?docs/adr/0007-*.md
API docsWhich endpoints, inputs, outputs, errors?Swagger/OpenAPI generated from code
Code commentsWhy is this tricky line written like this?Next to the code
RunbookAlert X fired: what do I check and do?docs/runbooks/, linked from the alert

Keep docs in the repo, next to the code, and change them in the same PR as the code. Docs in a separate wiki go out of date because nobody reviews them.

Comments: explain why, not what.

Architecture Decision Records (ADRs). A short document (one page) for each significant decision, numbered and never deleted. If a decision changes, a new ADR "supersedes" the old one. This gives a history of why the system looks the way it does.

A README that actually helps. Test: can a new developer go from git clone to a running app with passing tests in under 30 minutes, without asking anyone?

In a real NestJS project

API documentation should be generated from the code, so it can't drift. With @nestjs/swagger, document the behavior that types can't show: error cases and business rules.

Note that the "not found" description hides whether the order exists for another user. That's a deliberate security choice worth documenting, so nobody "fixes" it to 403 later.

Common mistakes
  • Comments that describe what the code does, and then become lies when the code changes.
  • Docs in a wiki nobody updates. Put them in the repo and review them in PRs.
  • Documenting nothing about decisions, so the team re-debates the same question every six months.
  • Writing huge documents nobody reads. One clear page beats twenty vague ones.
  • A README that stopped working three Node versions ago. Test it with every new team member.

Interview questions

What is an ADR and why use one?

An Architecture Decision Record is a short document capturing one significant decision: context, options, the decision and its consequences. It preserves the reasoning so future developers understand why the system is built this way and don't repeat old debates or undo deliberate choices.

What makes a good code comment?

It explains intent, reasons, constraints or non-obvious consequences ("why"), which the code can't express. If a comment explains "what" the code does, it's usually better to improve names or extract a function.

How do you keep documentation up to date?

Keep it in the repo next to the code, update it in the same PR as the behavior change (add a checkbox to the PR template), generate API docs from code, and test the README during onboarding.

Remember Document what is expensive to rediscover: decisions (ADRs), the why behind tricky code, how to run the project, and what to do when it breaks. Keep docs in the repo and update them with the code.

Mentoring

explain concepts clearly to junior developers

In plain words

Mentoring is like teaching someone to ride a bike. You don't ride it for them, and you don't hand them a physics textbook. You explain just enough, hold the seat at first, then let go a little more each time, and you stay close when they fall. A senior engineer's impact is measured not only by their own code, but by how much better the people around them become. If you are the only person who understands the payment module, that's not job security, that's a risk for the team.

How it works

Principles for clear explanations.

  • Start from what they know. Ask first: "Have you used Express before?" Then connect the new idea to it.
  • Why before how. Explain the problem a concept solves before its syntax.
  • One concept at a time, with a concrete example from your codebase.
  • Check understanding by asking them to explain it back or apply it, not by asking "is that clear?" (everyone says yes).

Example: explaining Dependency Injection.

Ask, don't tell (most of the time). When a junior is stuck, guiding questions build skill; giving the answer builds dependency. Balance it: if they've been stuck for hours or production is down, just help directly.

Teaching through code review. Reviews are the most frequent mentoring moment. Explain the principle, link to a resource, and praise what's good.

Pairing styles. In driver/navigator pairing, the junior types (driver) and the senior guides (navigator). Let the junior drive: people learn by doing, not by watching you type fast.

In a real NestJS project

A concrete first-two-weeks plan for a junior joining a Nest + Prisma team:

DayActivityLearns
1Run the project from the README (fix the README where it fails)Setup, Docker, Prisma migrate
2Trace one request together: POST /orders from controller to DBModules, DI, DTOs, guards
3–4"Good first issue": add a validated query filter to GET /products with a testDTOs, class-validator, Prisma where, e2e tests
5–10A small real feature, paired at the start, reviewed in detailThe full PR → CI → deploy cycle

Fixing the README on day 1 is valuable twice: the junior gets a quick first PR, and the docs improve for the next person.

Common mistakes
  • Using jargon to explain jargon. Use plain words and analogies first, then introduce the official term.
  • Taking the keyboard and fixing it yourself. Fast today, but the junior is just as stuck tomorrow.
  • Asking "Does that make sense?" and accepting "yes". Ask them to explain it back or to apply it.
  • Only giving negative feedback. Point out what is good, so they know what to repeat.
  • Making people feel stupid for asking. Then they stop asking and start guessing, in production.
Practice exercise

A junior asks: "Why can't I just put @Body() body: any and use it directly? It works." Write a short, friendly explanation (5–8 sentences) with a tiny example.

Show answer

"Good question, and you're right that it works when the client sends correct data. The problem is that clients don't always do that, and some send bad data on purpose. TypeScript types disappear at runtime, so any means nobody checks anything. For example, someone could send { "role": "ADMIN" } to the update-profile endpoint and make themselves an admin, if we pass body straight to Prisma. A DTO class with class-validator plus ValidationPipe({ whitelist: true }) checks types and removes unknown fields before your code runs. Want to try it? Send that request with any and then with a DTO, and compare."

Notice the structure: validate the question, explain the risk with a concrete attack, show the fix, and invite them to try it.

Interview questions

How do you mentor a junior developer?

Understand their current level and goals, give them gradually harder real tasks, pair at the start and step back over time, use code reviews to teach principles, ask guiding questions instead of giving answers, give regular specific feedback (positive and constructive), and make it safe to ask questions.

How would you explain a complex concept to someone new?

Start with the problem it solves, use an everyday analogy, show a minimal concrete example from our codebase, let them apply it, and check understanding by having them explain it back. Introduce official terminology only after the idea is clear.

A junior keeps making the same mistake in PRs. What do you do?

Talk one-on-one rather than repeating PR comments. Make sure they understand the why, pair on one example, and if possible automate the check (lint rule, test, PR template item) so the tooling catches it in the future.

Remember Problem first, analogy second, real code third, then let them do it. Ask guiding questions, give kind and specific feedback, and measure success by how independent they become.

System thinking

understand frontend, backend, database and deployment

In plain words

A car mechanic who only knows the engine can't explain why the car pulls to the left. You need to see the whole car: engine, wheels, brakes, steering, and how they affect each other. A web application is the same. A "slow page" might be the browser making 30 requests, a missing database index, a tiny connection pool, or a server in the wrong region. System thinking means you can follow a user's click through every layer (frontend, network, backend, database, infrastructure) and understand how a change in one layer affects the others.

How it works

The journey of one request. Learn this path by heart. When something is slow or broken, walk it step by step.

Example 1: the connection pool math. Each Prisma client keeps a pool of database connections. The default size is num_cpus × 2 + 1. PostgreSQL's default max_connections is 100. Now look at the whole system:

SituationConnectionsResult
3 instances × 2 vCPU → 5 per pool15✅ fine
Black Friday: autoscaling to 25 instances125 (+ migrations, admin tools, workers)❌ "too many connections", the whole site goes down because it scaled

A backend-only view says "add more instances". A system view sees that the database is the shared limit. Fixes: set an explicit pool size per instance, cap autoscaling, or put a connection pooler (PgBouncer, or your cloud's equivalent) in front of Postgres.

Example 2: the timeout chain. Every layer has a timeout. Inner layers must give up before outer layers, otherwise work continues for a user who is already gone.

Example 3: the frontend is part of your system. Backend decisions change the user's experience:

  • An endpoint without pagination works in development (10 rows) and sends 8 MB of JSON to a phone in production.
  • A product page that needs 6 sequential API calls is slow even if each call is fast (6 × 150 ms round trips on mobile). Sometimes one well-designed endpoint is better.
  • A changed response field breaks old mobile app versions that users haven't updated. Mobile clients can stay old for months.
  • CORS, cookies (SameSite, Secure) and cache headers are shared contracts between frontend and backend.
In a real NestJS project

You can't reason about a system you can't see. A small interceptor that logs duration per route is a cheap first step (later: OpenTelemetry tracing across services):

Combine it with Prisma query logging (new PrismaClient({ log: [{ emit: 'event', level: 'query' }] }) and a listener that logs queries above 200 ms) to see whether time is spent in the database or in your code.

Common mistakes
  • Optimizing code in your layer while the real bottleneck is elsewhere (network round trips, the DB pool, a third-party API).
  • Scaling the backend horizontally without checking what the database can handle.
  • Missing or badly ordered timeouts, so stuck work piles up behind the scenes.
  • Changing an API response without thinking about old frontend or mobile versions.
  • "It works on my machine": local has 10 rows, no network latency and one user.
Practice exercise

Users report: "The order history page is fast for new users, but takes 8 seconds for loyal customers, and only in production." Walk through the layers and list what you would check, in order.

Show answer
  1. Frontend / network: browser DevTools → how many requests, which one is slow, how big is the response? "Only loyal customers" suggests data volume.
  2. API: does GET /orders paginate? Probably not: a customer with 900 orders gets everything, plus items, maybe as N+1 queries.
  3. Database: EXPLAIN ANALYZE the query with a real loyal user's id. Is there an index on "Order"("userId", "createdAt")? Production has millions of rows, local has 50.
  4. Infrastructure: are DB pool waits or CPU high at the same time? Is the instance in the same region as the database?
  5. Fix in the right layer: cursor pagination (backend + frontend "load more"), include instead of N+1, a composite index. Then verify with the timing logs and the dashboard.

Interview questions

What happens when a user types a URL and presses Enter?

DNS resolves the host to an IP, the browser opens a TCP connection and negotiates TLS, sends the HTTP request, which passes through a CDN/load balancer to an app instance. The app runs middleware, auth, validation and business logic, queries the database or cache, serializes the response, and it travels back to the browser, which parses and renders it (often triggering more requests).

Why can scaling out the API cause a database outage?

Each instance opens its own connection pool. More instances multiply total connections, and PostgreSQL has a fixed max_connections, with each connection costing memory. Past the limit, new connections fail. Use explicit pool sizes, a connection pooler like PgBouncer, and capacity planning that includes the database.

How should timeouts be configured across layers?

Every outbound call and query needs a timeout, and inner timeouts should be shorter than the outer ones (DB < service < client < load balancer), so work is cancelled when nobody is waiting for it anymore and resources are freed.

Remember Follow the request through every layer: browser, network, load balancer, Nest, pool, database, third parties. Shared limits (DB connections, timeouts, API contracts) are where systems break.
8

Failure design

think about what happens when everything goes wrong

In plain words

Buildings have fire exits, sprinklers and emergency lights, not because architects expect a fire every day, but because one day there will be one. Software is the same: networks drop, databases restart, payment providers time out, and your own code has bugs. Failure design means asking, for every step, "what if this fails, is slow, or happens twice?" and deciding in advance what should happen: retry, wait, show a fallback, or fail cleanly without corrupting data.

How it works

The "what if" questions for every external call.

What if...Tool
...it never answers?Timeout
...it fails temporarily?Retry with exponential backoff + jitter
...the request is sent twice (retry, double click, network replay)?Idempotency
...it's down for a long time?Circuit breaker + graceful degradation
...we crash between two steps?Transactions, outbox pattern, reconciliation jobs

1. Timeouts. Without a timeout, a hanging dependency holds your request, your memory and maybe a DB connection forever.

2. Retries with exponential backoff and jitter. Retry only temporary failures (timeouts, 502/503/429), never a 400 validation error. Wait longer each time, and add randomness (jitter) so thousands of clients don't retry at the exact same moment and knock the service down again.

⚠️ Retrying a non-idempotent operation ("charge the card") can do it twice. That's why retries and idempotency always go together.

3. Idempotency. An operation is idempotent if doing it twice has the same effect as doing it once. GET, PUT and DELETE are idempotent by design; POST is not. Make POST safe with an Idempotency-Key header: the client generates a unique key per action, and the server remembers the result for that key.

4. Circuit breaker and graceful degradation. If a dependency is failing, stop calling it for a while ("open the circuit") instead of making every request wait for a timeout. Meanwhile, return something reasonable: the essential feature keeps working, the optional one degrades.

Libraries like opossum implement a full circuit breaker (closed → open after N failures → half-open test → closed).

5. Crashing between steps: the outbox pattern. "Save the order, then publish an OrderCreated event" is two systems. If the process dies after the DB commit and before the publish, the event is lost forever. Solution: write the event into an Outbox table in the same transaction as the order, and let a background worker publish pending outbox rows and mark them sent (at-least-once delivery, so consumers must be idempotent).

In a real NestJS project

The controller reads the key with @Headers('idempotency-key') and rejects requests without one (400). Old keys can be deleted by a nightly cleanup job after, say, 24 hours.

Common mistakes
  • No timeouts on HTTP calls or queries. One slow dependency freezes everything.
  • Retrying immediately, forever, without jitter. You turn a small outage into a big one (a "retry storm").
  • Retrying non-idempotent operations, causing double charges, double emails or duplicate orders.
  • Treating optional features as essential, so the whole page fails because of the "you may also like" widget.
  • Assuming "after the DB commit, the next line always runs". Processes crash; design for it (outbox, reconciliation).
Practice exercise

You call the payment provider to charge $50. After 5 seconds your request times out. You don't know whether the charge happened. What should your system do? Think about the user, the database and the provider.

Show answer
  • Never assume failure. A timeout means "unknown", not "not charged". Don't just retry with a new request, and don't tell the user "payment failed".
  • Store state first: before calling, save a Payment row with status PENDING and an idempotency key. On timeout, leave it PENDING.
  • Retry safely: retry with the same idempotency key; the provider returns the original charge if it exists.
  • Reconcile: listen to the provider's webhooks (payment.succeeded / failed) and run a job that queries the provider for payments stuck in PENDING for more than a few minutes.
  • User experience: show "We're confirming your payment" and update the order when the result is known; email the confirmation.

Interview questions

What is idempotency and why does it matter?

An operation is idempotent if repeating it gives the same result as doing it once. Networks cause retries and duplicates, so non-idempotent operations (payments, order creation) need protection, typically an idempotency key stored with a unique constraint and the original response replayed for repeats.

Why add jitter to exponential backoff?

Without jitter, all clients that failed at the same time retry at the same times (1 s, 2 s, 4 s...), creating synchronized traffic spikes that can keep the recovering service down. Random jitter spreads retries out.

What is the outbox pattern?

Writing an event to an outbox table in the same database transaction as the business change, then publishing it asynchronously from that table. It guarantees the event is eventually published if (and only if) the change was committed, avoiding lost events when the process crashes between the two steps.

Remember For every step ask: what if it hangs, fails, or happens twice? Add timeouts, retry only safe operations with backoff + jitter, make writes idempotent, degrade optional features, and never lose state between steps.
9

Production thinking

design for real users, not only the happy path

In plain words

The "happy path" is the demo: one user, good internet, correct input, clicks once, everything works. Real users are different. They double-click "Pay", lose signal in an elevator, paste a 10,000-character name full of emojis, live in a different time zone, use an app version from last year, and a few of them actively try to break things. Production thinking means designing for that world: real data volumes, real concurrency, real mistakes and real attackers, and being able to see and fix problems quickly when they happen anyway.

Ship safely: feature flags and gradual rollout. Deploying code and releasing a feature can be two different moments. Put risky features behind a flag, enable them for staff first, then 5% of users, then everyone. If something goes wrong, turn the flag off in seconds, without a deploy.

Learn from incidents: the blameless post-mortem. Things will still break. Mature teams write a short post-mortem that focuses on how the system allowed the mistake, not on who made it. People who fear blame hide information, and then nobody learns.

Common mistakes
  • Testing only with perfect input, one user and ten rows of data.
  • Relying on the frontend to prevent double submits or invalid input. The API must defend itself.
  • Storing local times without a time zone, then fighting "off by 7 hours" bugs forever.
  • Releasing big risky features to 100% of users at once with no flag and no rollback plan.
  • Blame-focused incident reviews, so people hide mistakes and the same incident repeats.
Practice exercise

Product asks for GET /admin/orders/export, "download all orders as CSV". The happy-path version is findMany() + build a string + return it. Today there are 2 million orders. Redesign it for production.

Show answer
  • Don't do it in the request. POST /admin/exports creates an Export job (status PENDING) and returns 202 Accepted with its id. A BullMQ worker generates the file.
  • Stream, don't load everything: read in batches with cursor pagination (take: 5000, cursor: { id: lastId }, skip: 1) and write rows to a stream (e.g. uploaded to S3/object storage), so memory stays flat.
  • Filters and limits: require a date range; cap the range (e.g. max 1 year) or the row count.
  • Security: admin role guard; exclude or mask personal data that isn't needed; the download link is signed and expires (e.g. 1 hour); audit log who exported what.
  • Correctness: escape CSV values (commas, quotes, newlines, and formulas starting with =/+/-/@ to prevent CSV injection in Excel); times in UTC with ISO format.
  • Operations: run the queries against a read replica if available; notify by email when ready; failed jobs retry and are visible in monitoring; one concurrent export per admin.

Interview questions

What does "production-ready" mean to you?

The feature is correct for real-world inputs and concurrency, secure, performant at real data volumes, observable (logs, metrics, errors, alerts), resilient to dependency failures, backwards compatible, safely deployable and reversible (migrations, flags, rollback), and documented enough for others to support it.

How do you prevent duplicate submissions?

Defense in depth: disable the button on the client, but rely on the server: idempotency keys for create/payment requests, database unique constraints for natural keys, and atomic conditional updates (updateMany with a status condition) so a state transition can only happen once.

What is a blameless post-mortem?

An incident review that focuses on the timeline, the system conditions and process gaps that allowed the failure, and concrete action items, instead of blaming individuals. It encourages honesty, which is required to find and fix real root causes.

Remember Design for double clicks, bad input, big data, concurrency, time zones, old clients and failures. Release gradually, watch it, and when it breaks anyway, learn without blame.
