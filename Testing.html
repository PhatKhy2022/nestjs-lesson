Unit tests

Jest fundamentals

In plain words

A unit test is a tiny robot that checks one small piece of your code. You tell it: "when I give this function these inputs, it must return this". Then you can run hundreds of robots in a few seconds, every time you change something. If a change breaks old behaviour, a robot shouts immediately, long before a customer notices. Jest is the tool that runs the robots and reports which ones passed.

How it works

What nest new gives you. A new project is already set up for Jest. Look at package.json:

  • Unit tests live next to the code: src/users/users.service.spec.ts. Any file ending in .spec.ts under src runs with npm test.
  • e2e tests live in test/ and end in .e2e-spec.ts. They have their own config (point 4).
  • ts-jest compiles TypeScript on the fly, so you write tests in TypeScript.

The building blocks. Let's test a pure function first, with no Nest and no database. That is the simplest kind of unit test.

The Arrange → Act → Assert pattern (AAA) makes every test read the same way: set up the data, call the code once, check the result. One test should check one behaviour, and its name should read like a sentence: "calculateOrderTotal returns 0 for an empty cart".

The matchers you'll use 95% of the time.

MatcherChecksExample
toBeExact equality (Object.is): primitives, same referenceexpect(total).toBe(3999)
toEqualDeep equality of objects and arraysexpect(user).toEqual({ id: 1, email: 'a@x.com' })
toMatchObjectObject contains at least these fieldsexpect(user).toMatchObject({ role: 'USER' })
toThrowFunction throws (class, message or regex)expect(() => fn()).toThrow('between 0 and 100')
toHaveLength, toContainArrays and stringsexpect(list).toHaveLength(3)
toBeNull, toBeDefined, toBeTruthyPresenceexpect(found).toBeNull()
.notNegates any matcherexpect(body).not.toHaveProperty('passwordHash')

Async tests. Most Nest code is async. Make the test async and await, or Jest will finish the test before your promise settles, and it will pass even when it should fail.

Setup and teardown. beforeEach runs before every test in its describe block, so each test starts fresh. beforeAll runs once (good for expensive setup like starting an app). afterEach and afterAll clean up.

In a real NestJS project

When you run nest g service users, the CLI also creates users.service.spec.ts with a "should be defined" test. That test is only a starting point: it proves the class can be built, not that it works. Keep the scaffold, then add real behaviour tests next to it (points 2 and 3). The best unit-test targets are the parts of the app with logic: pricing, discount rules, permission maps, status transitions. They are pure functions or plain classes, so tests are fast and need no mocks.

Common mistakes
  • Forgetting await (or return) on async expectations. The test passes no matter what.
  • expect(fn()).toThrow() instead of expect(() => fn()).toThrow(). The error is thrown before Jest can catch it.
  • Using toBe for objects and arrays. Use toEqual.
  • Tests that depend on each other's order or shared state. Every test must pass when run alone (it.only).
  • Committing it.only or describe.only, which silently skips the rest of the file in CI.

Interview questions

What is the difference between toBe and toEqual?

toBe uses Object.is: same primitive value or the same object reference. toEqual compares recursively by value, so two different objects with the same fields are equal. Use toStrictEqual if undefined properties and class types must also match.

What makes a good unit test?

It is fast, isolated (no network or database), deterministic (same result every run), tests one behaviour through the public API, and has a name that describes that behaviour. When it fails, you should know what broke without reading the code.

How do you test that an async function rejects?

await expect(promise).rejects.toThrow(SomeError). The await is essential. Without it, the test finishes before the promise settles.

Remember Arrange, Act, Assert: one behaviour per test, await every async expectation, toEqual for objects, and wrap throwing calls in a function.

Testing services

mocking Prisma and repositories

In plain words

A service usually talks to the database. For a unit test we don't want a real database: it's slow, needs setup, and a failure might be the database's fault, not your code's. So we give the service a stunt double for Prisma: a fake object that looks like Prisma, returns whatever we tell it to, and remembers how it was called. Then we can check the service's own decisions, such as "throw 404 if the user is missing" or "hash the password before saving", in milliseconds.

How it works

The service under test. This is a typical UsersService:

Step 1: build a testing module with a fake PrismaService. Test.createTestingModule() creates a small Nest DI container, just like a real module. With { provide: PrismaService, useValue: prismaMock } we tell Nest: "whenever someone asks for PrismaService, give them this object instead". The service doesn't know the difference.

Step 2: test the decisions, not Prisma. For each method, ask: what does my code decide? findOne decides "missing user → 404". create decides "hash the password, lower-case the email, translate P2002 into 409".

In a real NestJS project

Unit tests with a mocked Prisma are great for service logic, but they can't tell you whether the query itself is right (a wrong field name, a missing include, a unique constraint that doesn't exist). A healthy project uses both:

  • Unit tests (*.spec.ts, mocked Prisma) for branches and error handling: fast, hundreds of them.
  • Integration and e2e tests (points 4–5) against a real PostgreSQL test database, to prove the queries and constraints work.

Common mistakes
  • Testing that Prisma was called with exactly the same object you wrote in the service, and nothing else. That only repeats the implementation. Test outcomes and decisions.
  • Not resetting mocks between tests, so a mockResolvedValue from test A leaks into test B. Use jest.clearAllMocks() in beforeEach or clearMocks: true in the config.
  • Keeping the CLI's "should be defined" test as the only test. It passes for a completely broken service.
  • Importing the real PrismaModule into a unit test, which then tries to connect to a database.
  • Mocking the class you are testing. Only its dependencies should be fake.

Interview questions

How do you replace a dependency in a NestJS unit test?

Build a module with Test.createTestingModule and register a custom provider that uses the real token: { provide: PrismaService, useValue: mock } (or useClass / useFactory). The class under test receives the mock through normal dependency injection.

What can't a unit test with a mocked Prisma catch?

Anything about the real database: wrong queries, missing relations, constraint behaviour, migrations, transaction semantics, and Prisma's actual return shape. You need integration or e2e tests against a real database for those.

Mock Prisma directly or introduce a repository?

Mocking Prisma directly is fine and common. A repository gives smaller, intention-revealing mocks and isolates the ORM, at the cost of an extra layer. Choose based on the size and complexity of the data access.

Remember Use the real service with fake dependencies. Mock Prisma (or a repository) to test your service's decisions, and leave query correctness to tests that use a real database.

Testing controllers

mocking providers

In plain words

A controller is the receptionist of your app. It takes the request, passes it to the right department (a service), and hands back the answer. When you test the receptionist, you don't need the real departments. You replace the service with a fake that says "yes, here's a user", and you check only the receptionist's job: did it ask the right department, with the right details, and pass the answer back correctly?

How it works

The controller under test. It uses the guards and decorators from Lesson 7:

Step 1: mock the service provider. Same idea as point 2, one level up: the controller is real, and UsersService is a fake.

What does not run in a controller unit test? You call the method directly, like a normal function. Nest's request pipeline is skipped completely:

PieceRuns when you call controller.findAll()?Where to test it
Your method body✅ YesController unit test
Guards (JwtAuthGuard, RolesGuard)❌ NoGuard unit test + e2e
Pipes (ParseIntPipe, ValidationPipe)❌ Noe2e (or DTO unit test)
Interceptors, exception filters❌ NoTheir own unit tests + e2e
Route paths and HTTP status codes❌ Noe2e

That's why controllers should be thin: if all the logic lives in services, controller tests stay short, and e2e tests cover the HTTP wiring.

Step 2: overriding guards that have dependencies. If a controller uses @UseGuards(SomeGuard) directly, Nest must create that guard when it compiles the testing module, even though it never runs it. If the guard needs ConfigService or Reflector from a module you didn't import, compilation fails. Replace the guard:

Common mistakes
  • Expecting ValidationPipe or ParseIntPipe to run when calling controller.create(dto). They don't. Test validation in e2e tests.
  • Believing a route is protected because the controller test "passes". Guards never ran. Test the metadata, and test the 401/403 in e2e.
  • Putting business logic in controllers, so you need a huge controller test full of mocks. Move it to a service.
  • Forgetting to mock a dependency, which gives "Nest can't resolve dependencies of the UsersController (?)". Every constructor dependency needs a provider or useMocker.

Interview questions

Do guards and pipes run in a controller unit test?

No. Calling the method directly bypasses Nest's request pipeline: no guards, pipes, interceptors or filters. Test those separately, and use e2e tests (with Supertest) to test them together over HTTP.

What is the difference between overrideProvider and overrideGuard?

Both replace something in the testing module before compile(). overrideProvider(Token) replaces an injectable provider (a service, a repository). overrideGuard(GuardClass) replaces a guard referenced with @UseGuards(), for example with { canActivate: () => true }.

How can you test that a route is protected without running the app?

Read the metadata the decorators attached: new Reflector().get(ROLES_KEY, Controller.prototype.method) and assert the expected roles. For full confidence, also write e2e tests that expect 401 and 403.

Remember Controller unit tests check delegation and response shaping, with mocked services. Guards, pipes and status codes need e2e tests.

e2e tests

Supertest and TestingModule

In plain words

Unit tests check each part of a car on a workbench. An end-to-end (e2e) test turns the key and drives the car around the block. We start the whole NestJS app in memory and send it real HTTP requests, just like a browser or mobile app would. The request goes through middleware, guards, pipes, the controller, the service and the database, and we check the final HTTP response: status code, headers and body. If an e2e test passes, a real client would see the same thing.

How it works

What the CLI generated. nest new creates a test/ folder with its own Jest config and one example:

Test.createTestingModule({ imports: [AppModule] }) builds the real app. createNestApplication() + init() create the HTTP layer without opening a port. Supertest's request(app.getHttpServer()) sends requests straight to that server object.

Trap #1: main.ts is not used. Everything you configure in main.ts (global ValidationPipe, cookieParser, global prefix, CORS) does not exist in the test app. Then validation tests pass in production but fail in tests, or the other way round. Fix: move that setup into one function and call it from both places.

Trap #2: speed. Starting the app takes a second or two. The generated example uses beforeEach, which restarts the app before every test. For a suite of 30 tests, use beforeAll and close the app in afterAll. Otherwise Jest warns "did not exit one second after the test run" because Prisma connections stay open.

A real e2e test: the full auth flow. request.agent() keeps cookies between requests, like a browser, which is perfect for our httpOnly refresh cookie.

Replacing only external services. e2e tests should use your real code and a real database, but not real e-mails or payments. Override just those providers:

Unit teste2e test
ScopeOne classWhole app over HTTP
DependenciesMockedReal (except external APIs)
DatabaseNoneReal test database
Speed~1–10 ms each~20–200 ms each, plus app start
FindsLogic bugsWiring bugs: guards, pipes, routes, queries, status codes
In a real NestJS project

Run e2e tests one file at a time (--runInBand) when they share a database, so two files don't wipe each other's data (point 5).

Common mistakes
  • Forgetting that main.ts doesn't run, so there is no ValidationPipe in tests. Share a configureApp() function.
  • Not calling app.close(), so open DB connections keep Jest running ("Jest did not exit…").
  • Pointing e2e tests at the development database and wiping your local data. Use a separate test DB (point 5).
  • Mocking services in e2e tests "to make them easier". Then they're just slow unit tests. Mock only things outside your system.
  • Not returning or awaiting the Supertest chain, so the test ends before the request finishes.

Interview questions

What does app.getHttpServer() give Supertest, and why is no port needed?

It returns the underlying Node HTTP server (Express by default). Supertest can send requests directly to a server object; if it isn't listening, Supertest binds it to a temporary port itself. So tests don't fight over port 3000.

Why might validation work in production but not in your e2e tests?

Global pipes, middleware and prefixes set in main.ts aren't applied to an app created by the testing module. Put that configuration in a shared function and call it in both places, or register pipes with APP_PIPE in a module.

What should and shouldn't be mocked in e2e tests?

Keep everything you own real: controllers, services, guards, Prisma and a real test database. Mock only external systems you don't control or don't want to call: email, payment providers, SMS, third-party APIs.

Remember e2e tests boot the real app and talk HTTP with Supertest. Share the main.ts setup, close the app, use a test database, and mock only the outside world.

Test database

isolated test data strategy

In plain words

e2e tests need a real database, but never your database. Think of a cooking school: students practise in a training kitchen, not in the restaurant during dinner service. Before each lesson, the counters are wiped clean, so nobody's leftover ingredients ruin the next recipe. A test database is that training kitchen: separate, disposable, and reset to a known clean state before each test, so every test gets the same result every time.

How it works

Rule 1: a separate database. Run a dedicated PostgreSQL for tests. With Docker it costs nothing, and tmpfs keeps the data in RAM, which is faster and gets thrown away when the container stops.

Rule 2: same schema as production. Apply your real migrations to the test DB before the tests run. Use migrate deploy (apply existing migrations), not migrate dev (which may create new ones). dotenv-cli loads .env.test for both Prisma and Jest. @nestjs/config does not overwrite variables that already exist in process.env, so the app picks up the test values.

Rule 3: a clean state for every test. If test A creates an@shop.com and test B registers the same email, B fails with 409, but only when A runs first. Such "flaky" tests destroy trust. The simplest reliable fix in PostgreSQL is to empty every table before each test with TRUNCATE:

Table names come from PostgreSQL itself, not from user input, so $executeRawUnsafe is safe here. One TRUNCATE of all tables takes a few milliseconds, much faster than deleteMany() on each model in the right foreign-key order.

Rule 4: each test creates its own data. Don't rely on a big shared seed file ("user 3 is the admin"). Each test creates exactly what it needs, using factories: small functions with sensible defaults that you can override.

Isolation strategies compared.

StrategyHowProsCons
Truncate before each testresetDatabase() in beforeEachSimple, reliable, works with real transactionsTest files must run one at a time (--runInBand)
Transaction rollbackWrap each test in a transaction, roll back at the endVery fastHard with Prisma: the app's own $transaction calls and HTTP requests use other connections
Database or schema per worker?schema=test_${JEST_WORKER_ID} and migrate eachParallel test filesMore setup; migrations run once per worker
TestcontainersStart a fresh Postgres container from the test codeZero manual setup; same in CINeeds Docker; slower start

Start with "truncate before each test + --runInBand". It's the easiest to understand and fast enough for hundreds of e2e tests. Move to schema-per-worker when the suite gets slow.

In a real NestJS project

In CI (GitHub Actions), the test database is a service container, so the pipeline runs the same commands as your laptop:

Common mistakes
  • Running e2e tests against the development database and losing your local data. Use a separate DB and add the _test safety check.
  • Using SQLite for tests while production runs PostgreSQL. Behaviour differs (case sensitivity, JSON, enums, constraints). Test on the same engine.
  • Tests that depend on data created by another test, or on a shared seed. Each test creates its own data with factories.
  • Running e2e files in parallel against one database with truncation, so files randomly wipe each other's data. Use --runInBand or one schema per worker.
  • Hard-coding ids (/users/1) instead of using the id returned by the factory.
Practice exercise

A test file fails only when run together with other files, never alone. List three likely causes, and how you'd confirm each one.

Show answer
  1. Leftover data from another file (missing reset, or a reset in beforeAll instead of beforeEach). Confirm: log the row counts at the start of the failing test.
  2. Parallel files sharing one database. Confirm: run with --runInBand. If it passes, that's it.
  3. Shared global state: mocks not cleared, fake timers left on, a module-level variable (like a counter or cache) changed by another test. Confirm: add clearMocks/restoreMocks to the config and check afterEach clean-up.

Jest's --randomize flag shuffles test order inside files, which helps flush out order dependencies early.

Interview questions

How do you keep e2e tests isolated from each other?

A dedicated test database with migrations applied, a reset (for example TRUNCATE … RESTART IDENTITY CASCADE) before each test, data created per test through factories, and no parallel writers to the same schema (run in band, or one schema per worker).

Why not just use SQLite in memory for tests?

It's a different database engine. Constraints, types, case-sensitivity, JSON and enum support, and raw SQL behave differently from PostgreSQL, so tests can pass while production fails. Use the same engine and version as production. Docker makes it cheap.

Why is transaction-rollback isolation tricky with Prisma and e2e tests?

The rollback only covers queries on the same connection or transaction. Requests through the HTTP app use Prisma's connection pool, and nested $transaction calls start their own transactions, so they escape the outer one. Truncation avoids these problems.

Remember Use a separate PostgreSQL with real migrations, reset it before every test, let each test create its own data with factories, and never let tests share state.

Mocking

jest.mock and manual mocks

In plain words

A mock is a stand-in actor. In a film, the stunt double looks enough like the star for the scene, does exactly what the director says, and nobody gets hurt. In tests, a mock looks enough like the real dependency (Prisma, argon2, an email sender, the clock), returns exactly what you tell it to, and records every call, so afterwards you can ask: "were you called? How many times? With what?".

How it works

1. jest.fn(): a fake function. It's the building block of every other mock.

2. jest.spyOn(): watch (or replace) a method on a real object. The object stays real. You only take control of one method, and you can restore the original afterwards.

3. jest.mock('module'): replace a whole imported module. Use this for libraries you import directly, like argon2. Real argon2 is deliberately slow (about 100 ms per hash), so 50 tests would waste 5 seconds. jest.mock calls are hoisted: Jest moves them above the imports, so the module is already fake when your code imports it.

jest.mocked(fn) doesn't change anything at runtime. It only tells TypeScript "this is a mock", so you get autocomplete for mockResolvedValue. For overloaded functions (like argon2.hash), the cast (argon2.hash as jest.Mock) is sometimes simpler.

4. Manual mocks: a __mocks__ folder. If many test files need the same fake module, write it once. For a node module, put the file in a __mocks__ folder in one of Jest's roots. With the Nest CLI config ("rootDir": "src"), that's src/__mocks__/. Jest then uses it automatically in every unit test.

This fake behaves believably: verify returns true only for the matching "hash", so most tests need no setup at all. For your own modules (for example src/mail/mail.client.ts), put the manual mock in src/mail/__mocks__/mail.client.ts and activate it in the test with jest.mock('./mail.client').

5. Fake timers: control the clock. Token expiry, "orders unpaid after 30 minutes are cancelled"… you don't want tests that really wait.

6. Resetting mocks between tests. Three similar-sounding functions:

CallClears recorded callsRemoves return values / implementationsRestores the original (spies)
mockClear() / clearMocks: true✅❌❌
mockReset() / resetMocks: true✅✅❌
mockRestore() / restoreMocks: true✅✅✅ (for spyOn)

Note: resetMocks: true also wipes the implementations of your __mocks__ files before every test, so the believable argon2 fake above would return undefined. clearMocks + restoreMocks is a safe default.

In a real NestJS project

In Nest, most mocking happens through dependency injection, not jest.mock. Anything that is a provider (PrismaService, MailService, JwtService, ConfigService) is replaced with useValue in the testing module. Use jest.mock only for things that are imported directly, like library functions (argon2) or helper modules. That's another reason to wrap libraries in providers (like PasswordService in Lesson 7): then you can swap them through DI as well.

Common mistakes
  • Mocking everything, including the code under test. Then the test proves only that mocks return what you told them. Mock dependencies, not the subject.
  • Mocks that return impossible data (a user without an email, the wrong shape). The test passes, and production crashes. Keep fakes realistic.
  • Forgetting mockRestore() on spies (or restoreMocks: true), so a spy on Logger.prototype leaks into other tests.
  • Calling jest.mock() inside a test or a beforeEach, expecting it to affect imports that already happened. Put it at the top level of the file.
  • Leaving fake timers on after a test, which breaks later tests that use real setTimeout or Prisma timeouts.

Interview questions

What is the difference between jest.fn(), jest.spyOn() and jest.mock()?

jest.fn() creates a standalone fake function. jest.spyOn(obj, 'method') wraps an existing method on a real object: it records calls, can replace the implementation, and can be restored. jest.mock('module') replaces a whole imported module (automatically, with a factory, or with a __mocks__ file).

Why are jest.mock calls hoisted?

Imports run before any other code in the file. To make sure the code under test receives the fake module, Jest (via babel-jest or ts-jest) moves jest.mock() calls to the top of the file. That's also why a mock factory can't use normal variables from the file scope, except ones whose names start with mock.

In NestJS, when do you use DI overrides instead of jest.mock?

Whenever the dependency is a provider injected through the constructor: use { provide: X, useValue: mock } or overrideProvider. It's explicit, type-friendly and per-test. Use jest.mock for modules imported directly (library functions, utility files).

Remember Use DI overrides for providers and jest.mock for imported modules. Keep fakes realistic, mock dependencies rather than the subject, and reset mocks between tests.

Test edge cases

validation errors, empty states, auth failures

In plain words

Testing only the "happy path" is like testing a door by walking through it once when it's open. Real users (and attackers) will push when they should pull, lean on it, try the wrong key, or try it when the room is empty. Most production bugs live at the edges: missing fields, the wrong format, an empty list, a deleted record, an expired token, a user who isn't allowed. Good tests deliberately poke every edge.

How it works

A checklist of edges for every endpoint. Go through it each time you write a feature:

CategoryQuestions to askExpected result
ValidationMissing field? Wrong type? Too short or too long? Unknown extra field?400 with a clear message
BoundariesExactly the minimum or maximum? One past it? 0, negative, huge numbers?Accept on the boundary, reject past it
Empty statesNo orders yet? Page beyond the last? Search with no hits?200 with [], not 404 or 500

AuthenticationNo token? Malformed? Expired? Wrong secret?401
AuthorizationWrong role? Another user's resource?403 / 404

1. Validation errors, with a table test. These run in e2e tests, because ValidationPipe only runs inside the HTTP pipeline. One it.each covers many bad inputs, and each row reads like a specification:

The role: 'ADMIN' row is a security test. It proves that forbidNonWhitelisted stops a client from setting fields it shouldn't. If someone removes that option one day, this test fails.

2. Empty states. A list endpoint for a brand-new user is the most common "forgotten" case. An empty list is a normal, successful answer.

3. Auth failures. Every way a token can be bad should give 401, and every "not allowed" should give 403. To create an expired or wrongly signed token, use a standalone JwtService (with no default options) inside the test:

4. Edge cases in unit tests. Service-level edges (not found, conflicts, failing dependencies) are cheaper to test with mocks, as in point 2. Use e2e for edges that depend on the HTTP pipeline (validation, guards, status codes) and unit tests for edges inside your logic.

In a real NestJS project

Pipes produce edge-case responses that clients rely on. Pin them down with tests, so a refactor (for example removing ParseIntPipe) can't silently turn a clean 400 into a 500 from Prisma:

When a bug reaches production, first write a test that reproduces it (it fails), then fix the code (it passes). That test is now a permanent guard against that edge case returning.

Common mistakes
  • Testing only the happy path, so the first empty list or missing field in production is a 500.
  • Returning 404 for an empty collection (GET /orders with no orders). An empty list is a valid 200.
  • Testing validation in controller unit tests, where ValidationPipe never runs. Those tests pass for any input.
  • Only testing "no token" for auth. Expired, wrongly signed, and the wrong token type (refresh used as access) are separate holes.
  • Asserting only the status code. Also check that the body doesn't leak internals (stack traces, passwordHash, SQL errors).

Interview questions

Where do you test request validation in NestJS, unit or e2e?

e2e (or at least through the HTTP pipeline), because ValidationPipe and other pipes run only when a request goes through Nest. Calling a controller method directly skips them. You can also unit-test a DTO with class-validator's validate(), but e2e proves the pipe is actually wired up.

Should an empty list return 404?

No. The collection resource exists; it just has no items. Return 200 with [] (or a paginated envelope with total: 0). Use 404 for a specific resource that doesn't exist (/orders/123).

Which auth failure cases should a test suite cover?

Missing token, malformed token, expired token, token signed with the wrong secret, the wrong token type (refresh used as access), a valid user without the required role (403), access to another user's resource (404/403), and identical responses for "unknown email" and "wrong password".

Remember Bugs live at the edges. For every endpoint, test bad input, boundaries, empty results, missing or foreign records, and every way auth can fail.

Test coverage

use coverage as a signal, not the only goal

In plain words

Coverage is a map that shows which roads your tests have driven on. It's very useful for finding roads nobody has driven: "the refund code has never been run by any test!". But driving on a road doesn't mean you checked it for potholes. A test can run a line of code without checking its result at all. So high coverage tells you "lots of code was executed", not "lots of code was verified".

Better questions than "what's the percentage?"

  • Is the critical code covered: auth, payments, permissions, money calculations?
  • Do the tests contain meaningful assertions, including the edge cases from point 7?
  • Does every bug fix come with a test that reproduces the bug?
  • Is coverage going down over time? Look at the trend and at diff coverage (coverage of the lines changed in this PR), which many CI tools report.

Mutation testing answers "would my tests notice a bug?". A tool such as StrykerJS makes small changes to your code (< becomes <=, - becomes +) and runs the tests. If they still pass, the "mutant survived", which shows a weak test even where line coverage is 100%. It's slow, so teams usually run it on critical modules only.

In a real NestJS project

A practical setup: unit tests with coverage on every push, e2e tests on every PR, and the HTML report uploaded as a CI artifact for reviewers.

A healthy NestJS codebase often sits around 70–85% unit coverage, with services and guards near 100% and generated or wiring code (modules, DTOs, main.ts) excluded. The e2e suite covers the HTTP wiring that unit coverage can't see.

Common mistakes
  • Chasing 100% and writing assertion-free tests to "cover" lines. The number goes up, and quality goes down.
  • Counting modules, DTOs and main.ts, which inflates or deflates the numbers meaninglessly. Configure collectCoverageFrom.
  • Looking only at line coverage. Branch coverage reveals the untested else where bugs hide.
  • Treating high coverage as proof of correctness. Coverage shows what ran, not what was checked.
  • No threshold at all, so coverage slowly erodes with every PR and nobody notices.

Interview questions

Is 100% coverage a good goal?

Usually not as a target. It measures execution, not verification, and the last few percent are often trivial or very expensive to test. It encourages low-value tests. Better: set a reasonable floor, demand high coverage for critical code, review the quality of assertions, and watch the trend and diff coverage.

What is the difference between line coverage and branch coverage?

Line coverage counts lines executed at least once. Branch coverage counts each possible path of every decision (both sides of an if, every case, short-circuit operands). A line like return a ?? b can be 100% line-covered while the b path was never tested.

How can you check whether your tests would actually catch bugs?

Mutation testing (for example StrykerJS) injects small bugs and checks whether a test fails. Surviving mutants point to weak or missing assertions. A simpler habit: when you write a test, briefly break the code and make sure the test turns red.

Remember Coverage shows where tests are missing, not whether the tests are good. Exclude wiring code, set sensible thresholds (higher for critical code), and focus on meaningful assertions.
