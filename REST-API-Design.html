REST principles

resources, verbs and statelessness

In plain words

Think of a library. Every book has a fixed address on a shelf (that's a resource and its URL). There are only a few things you can do with a book: look at it, add a new one, replace it, change a page, or remove it (those are the HTTP verbs). And the librarian doesn't remember you between visits: every time, you show your library card again (that's statelessness). Because every library follows the same rules, you can walk into any library and know what to do. A REST API gives developers that same feeling.

How it works

1. Resources are nouns, identified by URLs. A resource is a "thing" your API manages: a user, an order, a product. Use plural nouns and IDs. The URL says what, never what to do:

Keep nesting shallow: /users/7/orders is fine, but /users/7/orders/42/items/3/product is too deep. Once a resource has its own ID, give it a top-level URL (/orders/42).

2. Verbs (HTTP methods) say what to do. Each method has a meaning that clients, proxies and caches rely on:

MethodMeaningSafe?Idempotent?Typical success
GETRead a resource or a listYesYes200
POSTCreate a new resource (or run an action)NoNo201
PUTReplace the whole resourceNoYes200
PATCHChange some fieldsNoNot guaranteed200
DELETERemove a resourceNoYes204

Safe means "doesn't change anything on the server", so GET must never create or delete data. Idempotent means "doing it twice has the same effect as doing it once": deleting order 42 twice still leaves order 42 deleted. (More on this in the Idempotency topic.)

A full exchange looks like this:

3. Statelessness. Every request carries everything the server needs to handle it: who you are (a token), what you want (URL, method), and the data (body, query). The server does not keep a "conversation" in memory between requests. Why does this matter? Because then any of your 5 server instances can handle any request, so you can scale horizontally and restart servers without logging everyone out.

4. Actions that aren't CRUD. Some operations don't fit a simple verb, like "cancel an order" or "pay an order". Two common options: model it as a field change (PATCH /orders/42 { "status": "CANCELLED" }), or as a sub-resource action (POST /orders/42/cancel). The second is clearer when the action has its own rules and side effects (refunds, emails). Both are widely used. Pick one style and stay consistent.

In a real NestJS project

Nest's decorators map directly onto REST: one controller per resource, one method per verb + path.

Statelessness in Nest usually means JWT authentication (Lesson 7): the token is sent with every request and a guard verifies it, with no server-side session memory needed.

Common mistakes
  • Verbs in URLs (/createOrder, /orders/delete/42). The HTTP method already is the verb.
  • Changing data in a GET handler (e.g. GET /orders/42/confirm). Browsers, crawlers and prefetchers may call GET URLs on their own.
  • Mixing singular and plural (/order/42 and /products). Use plural everywhere.
  • Storing per-user state in server memory (a Map in a service), which breaks as soon as you run two instances.

Interview questions

What does "stateless" mean in REST, and why is it useful?

Each request contains all the information needed to process it, and the server keeps no client session in memory between requests. Any server instance can then handle any request, which makes horizontal scaling, load balancing and restarts simple.

What's the difference between PUT and PATCH?

PUT replaces the whole resource with the body you send (missing fields are reset), and it's idempotent. PATCH applies a partial change to only the fields sent. In practice most APIs use PATCH for updates.

What do "safe" and "idempotent" mean for HTTP methods?

Safe methods (GET, HEAD, OPTIONS) don't change server state. Idempotent methods (GET, PUT, DELETE and the safe ones) can be repeated with the same effect as doing them once. POST is neither by default.

Remember URLs are plural nouns, HTTP methods are the verbs, every request is self-contained, and the same patterns are used everywhere in the API.

Status codes

200, 201, 400, 401, 403, 404, 409, 422, 500

In plain words

A status code is the first word of the server's answer, before any details. Like a traffic light: the client's code can decide what to do just by looking at it. 2xx means "done", 4xx means "you (the client) did something wrong, fix your request", and 5xx means "I (the server) broke, try again later". If you always answer "200 OK" and put the error in the body, it's like a traffic light that's always green with a note taped to it.

How it works

CodeNameUse it whenShop example
200OKSuccessful read, update or action that returns dataGET /orders/42, PATCH /orders/42
201CreatedA new resource was createdPOST /orders (add a Location header)
204No ContentSuccess with no bodyDELETE /orders/42
400Bad RequestThe request is malformed or fails validationquantity: "abc", invalid JSON
401UnauthorizedNot authenticated: no token, expired or invalid tokenMissing Authorization header
403ForbiddenAuthenticated, but not allowedA normal user calls DELETE /products/3
404Not FoundThe resource doesn't exist (or the user may not know it exists)GET /orders/999
409ConflictThe request conflicts with the current stateEmail already registered, cancelling a shipped order
422Unprocessable ContentSyntax is fine, but the content breaks a business ruleOrder total below the payment minimum
429Too Many RequestsRate limit hitLogin brute-force protection
500Internal Server ErrorAn unexpected bug or crash on the serverUnhandled exception, DB down

401 vs 403 is a classic interview question. 401 = "I don't know who you are" (log in). 403 = "I know who you are, and the answer is no" (logging in again won't help).

404 to hide existence. If user 7 asks for order 42 that belongs to user 9, return 404, not 403. A 403 confirms that order 42 exists, which leaks information (and lets attackers enumerate IDs).

400 vs 422. Teams differ here. A common split: 400 for input that is wrong in shape or type (missing field, wrong type, bad JSON), and 422 for well-formed input that breaks a rule ("you can't order more than 10 of a limited item"). Nest's ValidationPipe returns 400 by default. Whichever you choose, document it and be consistent.

409 Conflict fits "the request is valid, but the current state of the resource doesn't allow it": duplicate unique values, state transitions that aren't allowed, or version mismatches.

500 is never "on purpose". You don't throw 500 for business situations. A 500 means a bug or an outage. Log it with full details on the server, and return a generic message to the client. Never leak stack traces or SQL errors.

How Nest picks the status code. Nest's defaults are: POST → 201, every other method → 200. Change it with @HttpCode(). For errors, throw Nest's built-in exceptions:

Prisma errors → correct status codes. Unhandled Prisma errors become 500, but some are really client errors. The two you'll see most: P2002 (unique constraint failed → 409) and P2025 (record to update or delete not found → 404). Handle them in one global filter instead of try/catch everywhere:

In a real NestJS project

Set codes on the controller, throw exceptions from services, and return a Location header for created resources when clients need it:

Common mistakes
  • Returning 200 with { "success": false } for errors. Clients, monitoring and retries all rely on the status code.
  • Using 401 when you mean 403, or the reverse.
  • Letting a Prisma unique-constraint error bubble up as a 500. That's a client conflict (409), not a server bug.
  • Using @Res() without passthrough: true. Nest then stops handling the response for you, and interceptors and serialization are skipped.
  • Returning 404 for an empty list. GET /orders?status=PAID with no matches is 200 with [].

Interview questions

What's the difference between 401 and 403?

401 means the client is not authenticated (missing, expired or invalid credentials). 403 means the client is authenticated but doesn't have permission. Re-authenticating can fix a 401, but not a 403.

When would you return 404 instead of 403?

When revealing that a resource exists would leak information, for example another user's order. Returning 404 for "not yours" and "doesn't exist" makes them indistinguishable.

When do you use 409 vs 422?

409 when the request conflicts with the current state of the resource (duplicate email, invalid state transition, version mismatch). 422 when the request is syntactically valid but its content violates validation or business rules. Many APIs use 400 for validation; the key is to document the choice.

Remember The status code is the answer, and the body is the explanation. Use 2xx for success, 4xx for client mistakes, and 5xx only for real server failures, and map Prisma errors to the right 4xx.

Request validation

class-validator with pipes

In plain words

A pipe is like a security scanner at a building entrance. Every visitor (every piece of incoming data) goes through it before reaching the office (your controller method). The scanner can do two things: transform (put your coat in a tray, i.e. turn the string "42" into the number 42) and validate (stop you if you carry something forbidden). If it stops you, you never reach the office, and your controller code never runs with bad data.

Common mistakes
  • Forgetting @Type(() => Number) in query DTOs. @IsInt() then fails on "2", because query values are strings.
  • Using @Type(() => Boolean) for ?active=false, which becomes true.
  • No @Max() on limit, letting a client request millions of rows.
  • Putting database lookups in a pipe or a validator, which mixes business rules into the HTTP layer and makes errors hard to control.
  • Registering the pipe only in main.ts and wondering why e2e tests don't validate.

Interview questions

What is a pipe in NestJS, and what are its two uses?

A class implementing PipeTransform that runs on handler arguments before the handler executes. It's used for transformation (e.g. string to number) and validation (throw an exception if the input is invalid).

What does transform: true do in ValidationPipe?

It converts the incoming plain object into an instance of the DTO class (applying @Type, @Transform and default values) and converts primitive params to their declared types. Without it, you get the raw plain object.

Where would you validate "the product must exist"?

In the service, not in a pipe. It needs a database query and is a business rule. Pipes should validate the format and shape of input only.

Remember Validate every input at the door with pipes: a global ValidationPipe for DTOs, parse pipes for single values, @Type for query strings, and business checks in the service.

Pagination

offset-based vs cursor-based pagination

In plain words

Pagination is reading a big list one page at a time. Offset pagination is like a book with page numbers: "jump to page 5". Easy, but if someone adds pages at the front while you read, the content shifts, and in a huge book finding page 50,000 is slow. Cursor pagination is like a bookmark: "continue after this line". You can't jump to page 5, but you never skip or repeat lines, and continuing is always fast.

How it works

Why paginate at all? GET /orders returning every order works with 20 rows and kills the server with 2 million: huge memory use, a slow query, and a slow response. Every list endpoint should be paginated from day one, with a maximum page size.

1. Offset-based pagination uses page and limit (or offset and limit). In SQL that's LIMIT 20 OFFSET 40; in Prisma, take and skip:

Problems with offset: (1) Slow deep pages: OFFSET 100000 makes PostgreSQL read and throw away 100,000 rows. (2) Shifting data: if a new order arrives while the user is on page 1, page 2 starts with the last item of page 1 again (duplicate); if one is deleted, an item is skipped. (3) count() on big tables is expensive.

2. Cursor-based (keyset) pagination says "give me the next N items after this one". The cursor is the position of the last item the client saw:

Under the hood this becomes WHERE id < 961 ORDER BY id DESC LIMIT 21, which PostgreSQL answers with an index lookup: just as fast for the millionth row as for the first.

Sorting by something other than id? The cursor must contain every column in the sort, and the sort must end with a unique column. For "newest first" use (createdAt, id). Encode it so clients treat it as an opaque token:

Add a matching index so PostgreSQL can walk it: @@index([userId, createdAt(sort: Desc), id(sort: Desc)]) in the Prisma schema.

Offset (page/limit)Cursor (cursor/limit)
Jump to page N✅ Yes❌ No (only next / previous)
Total count / page numbers✅ EasyUsually not shown
Speed on deep pages❌ Gets slower✅ Constant
Stable when data changes❌ Duplicates / skips✅ Stable

In a real NestJS project

Make pagination reusable: a shared query DTO and a generic response type, so every list endpoint looks the same:

Common mistakes
  • No maximum limit. One request with limit=1000000 can take the server down.
  • Paginating without a stable orderBy. PostgreSQL doesn't guarantee row order without one, so pages overlap randomly. Always end the sort with a unique column (id).
  • Fetching everything and slicing in JavaScript (rows.slice(skip, skip + limit)). Paginate in the database.
  • Exposing raw cursor internals that clients start to construct themselves. Make cursors opaque (base64url).

Interview questions

Why is offset pagination slow on large tables?

The database must read and discard all the skipped rows before returning the page, so OFFSET 100000 scans at least 100,000 rows. Cursor pagination uses an indexed WHERE condition to start directly at the right place.

Why can offset pagination return duplicates?

If rows are inserted or deleted between page requests, all following rows shift position. A new row at the top pushes the last item of page 1 onto page 2, so the client sees it twice.

What makes a good cursor?

It encodes the values of all sort columns of the last item, ending with a unique column so ordering is total. It's opaque to clients (e.g. base64url), and the sort columns are backed by an index.

Remember Paginate every list with a maximum limit and a stable sort. Use offset for admin tables that need page numbers, and cursors for feeds, infinite scroll and big tables.

Filtering & sorting

designing query parameters

In plain words

Filtering and sorting are like the filter panel on a shopping website: "only shoes, size 42, under $100, cheapest first". The query string (everything after ? in the URL) is that panel. A good design is one where a developer can guess the parameter names, and where your server only accepts filters it knows how to run safely and fast.

How it works

If you pass any client string into orderBy, a client can sort by passwordHash and learn things from the order (a side-channel leak), or sort by an unindexed column on a huge table and make every request slow. With raw SQL, it could even be SQL injection. Only allow what you've decided is safe and indexed.

Common mistakes
  • Passing client input straight into orderBy or where (where: query). Clients can then filter or sort by any column, including private ones.
  • Forgetting to scope by owner (userId) when building filters, so GET /orders?status=PAID returns everyone's orders.
  • Allowing filters and sorts without indexes, so the endpoint is fast in development and slow in production.
  • Inventing a different convention per endpoint (sortBy here, order there, sort elsewhere).
  • Not handling dates carefully: createdTo=2026-09-30 means midnight at the start of the 30th. Document it, or treat it as exclusive "before".

Interview questions

How do you design sorting in a REST API?

A single sort parameter with field names and a - prefix for descending (e.g. sort=-createdAt,name), validated against a whitelist of sortable, indexed fields, with a unique tie-breaker such as id appended on the server for stable ordering.

Why not pass the query object directly into Prisma's where?

It lets clients filter on any column, including private or unindexed ones, and changes your API whenever the schema changes. Explicitly mapping validated parameters to a where keeps the API contract controlled and safe.

Filters or a separate search endpoint?

Simple attribute filters belong on the collection (GET /products?category=shoes). Complex search with relevance ranking and many options can justify a dedicated endpoint (GET /search?q=…) or a search engine. Start with filters.

Remember Design query parameters to be guessable and consistent, validate them in a query DTO, whitelist sort fields, always scope by owner, and back every filter with an index.

Error response design

a consistent error shape

In plain words

Imagine every shop in a mall wrote receipts in a different format: one in a table, one as a poem, one on a napkin. Accountants would go mad. When every error from your API has the same shape, frontend developers write one error handler and it works for every endpoint. A good error also says what went wrong in a machine-readable way (a code), why in human words (a message), and where (which field).

How it works

The problem: Nest's defaults are inconsistent. Without a plan, you get several shapes from the same API:

Sometimes message is a string, sometimes an array, and only some errors have a code. The frontend has to guess.

Common mistakes
  • Leaking internals in 500 responses: stack traces, SQL, Prisma messages with table names. Log them and send a generic message.
  • Clients parsing message text to decide what to do. Messages change and get translated, so provide a stable code.
  • message being a string sometimes and an array other times.
  • Catching errors in every controller with try/catch and formatting them by hand. Use one global filter.
  • Returning different shapes for errors thrown by guards (401/403) vs services. A @Catch()-all filter handles both.

Interview questions

What should a good API error response contain?

The HTTP status, a stable machine-readable error code, a human-readable message, optional field-level details for validation, and context such as path, timestamp and a request ID for tracing. It should never contain stack traces or internal details.

How do you make all errors in a NestJS app use the same format?

Register a global exception filter with @Catch() (all exceptions) via APP_FILTER. It normalizes HttpExceptions, domain errors, ORM errors and unknown errors into one body. Combine it with a ValidationPipe exceptionFactory for field details.

What is RFC 9457?

The "Problem Details for HTTP APIs" standard (it replaced RFC 7807). It defines a JSON error format with type, title, status, detail and instance, served as application/problem+json, and allows extension fields.

Remember One error shape for the whole API, produced by one global filter: a status, a stable code, a clear message, field details when useful, and never internal secrets.

API versioning

URI, header or media-type versioning

In plain words

When a phone maker changes the charger plug, old phones still need the old charger for a while. An API is the same: mobile apps installed months ago keep calling your API the old way, and you can't force everyone to update on the same day. Versioning lets you serve the old "plug" and the new one side by side, then retire the old one slowly, with warning.

How it works

Breaking vs non-breaking changes. You only need a new version for breaking changes:

Non-breaking (no new version)Breaking (new version needed)
Adding a new endpointRemoving or renaming an endpoint
Adding an optional request fieldMaking a field required, or adding a required one
Adding a field to a responseRemoving or renaming a response field
Adding a new enum value (if clients handle unknowns)Changing a field's type (total: 3000 → total: "30.00")
Making validation less strictChanging status codes or error codes clients rely on

Example: v1 returned totalCents: 3000, and v2 returns total: { amount: "30.00", currency: "USD" }. Old app versions would break, so this needs v2.

The three main strategies:

StrategyProsCons
URIVisible, easy to test in a browser, easy to route and cache, easiest for clients"The same resource" has several URLs (purists dislike it)
HeaderClean URLsInvisible in links; caches and proxies need Vary: X-API-Version; easy to forget
Media typeMost "RESTful": version is part of content negotiationHardest for clients and tooling; rarely used outside big public APIs

Most teams pick URI versioning because it's the most obvious for everyone.

Retiring old versions. Announce, warn, then remove. Standard response headers tell clients in advance:

In a real NestJS project

Typical setup: setGlobalPrefix('api') + URI versioning with defaultVersion: '1' from day one, even if you only ever have v1. Adding versioning later changes every URL, which is itself a breaking change. Keep version-specific code in the HTTP layer only:

Common mistakes
  • Creating a new version for non-breaking changes (adding a field). Versions are expensive to maintain, so use them only for breaking changes.
  • Copy-pasting the whole service for v2. Version the HTTP layer (controllers, DTOs, mappers), not the business logic.
  • Making breaking changes silently "because only our app uses it". Old mobile app versions live for years.
  • Keeping old versions forever with no deprecation plan or usage tracking.
  • Header versioning behind a CDN without Vary, so cached v1 responses are served to v2 clients.

Interview questions

Which versioning strategies exist, and which would you choose?

URI (/v1/...), custom header (X-API-Version), media type (Accept: application/json;v=2), and sometimes a query parameter. I'd usually choose URI versioning: it's explicit, easy to test, works well with caches and docs, and Nest supports it with VersioningType.URI.

What counts as a breaking change?

Anything that can make an existing, correct client fail: removing or renaming fields or endpoints, changing types or formats, adding required inputs, tightening validation, or changing status and error codes. Adding optional inputs, new endpoints or new response fields is non-breaking.

How do you avoid duplicating logic across API versions?

Keep versions in the HTTP layer only. Different controllers, DTOs and mappers per version all call the same services and domain model.

Remember Version only for breaking changes, prefer URI versioning, turn it on from day one, keep versions in the HTTP layer, and retire old versions with Deprecation/Sunset headers.

Swagger / OpenAPI

@nestjs/swagger documentation

In plain words

OpenAPI is a standard "menu" for an API, written in JSON or YAML: every endpoint, what to send, what you get back, and what errors can happen. Swagger UI is a web page that displays that menu nicely and lets you try each dish right there. Interview questions

What's the difference between OpenAPI and Swagger?

OpenAPI is the specification format (a JSON/YAML description of an API). Swagger is the name of the original project and of tools around it, such as Swagger UI, which renders an OpenAPI document as interactive docs.

What does the @nestjs/swagger CLI plugin do?

At compile time, it analyzes DTO and entity classes and adds @ApiProperty metadata automatically from TypeScript types, optional markers, class-validator decorators and comments. That removes most of the manual decorators.

How do you document a generic paginated response?

Register the models with @ApiExtraModels, then describe the schema manually with getSchemaPath(model) for the data array, usually wrapped in a custom decorator built with applyDecorators.

Idempotency

safe retries for POST/PUT requests

In plain words

You press the elevator button five times. The elevator still comes once. That button is idempotent: pressing it again doesn't do anything extra. Now imagine a "Pay $50" button where the network drops after you tap it. Did it go through? If you tap again and it charges you twice, that's a real problem. Idempotency in an API means the client can safely retry a request, and the server makes sure the action happens only once.

How it works

Why retries happen. Networks fail in the worst place: after the server did the work but before the client got the answer. Mobile apps, HTTP clients and load balancers retry automatically. Users double-click. Without protection:

Which methods are already idempotent?

MethodIdempotent by definition?Why
GETYesReading changes nothing
PUT /users/7/avatarYes"Set it to X" twice gives the same result
DELETE /orders/42YesDeleted twice is still deleted (2nd call may return 404, but the state is the same)
PATCH /products/3 { stock: 10 }DependsSetting a value is idempotent…
PATCH /products/3 { stockDelta: +5 }No…but "add 5" twice adds 10
POST /ordersNoEach call creates a new resource

Note: "idempotent" is a promise you must implement. A PUT handler that also appends to a history table or sends an email each time isn't truly idempotent.

Solution 1: design idempotent operations. Prefer "set to" over "change by", and use upserts:

Solution 2: the Idempotency-Key header for operations that must be POST (create an order, charge a card). This is what Stripe and many payment APIs use. The client generates a unique key (a UUID) once per user action and sends the same key on every retry:

The server's rules:

  1. New key → reserve it, run the operation, store the response, return it.
  2. Known key, finished → return the stored response without running anything.
  3. Known key, still running (two retries racing) → 409 Conflict: "in progress, retry later".
  4. Known key, different body → 422: the client reused a key for a different request, which is a client bug.

In a real NestJS project

Use the Idempotency-Key interceptor on the few endpoints where duplicates cost money or trust: placing orders, payments, refunds, sending invitations. Webhook handlers use a unique constraint on the provider's event id. On the client side, generate the key when the user starts the action (e.g. on the "Place order" screen with crypto.randomUUID()), and reuse it for every retry of that action.

For critical flows, also consider putting the order creation and the "mark key completed" update in the same database transaction, so a crash between the two can't leave a created order with a released key.

Common mistakes
  • Check-then-insert without a unique constraint (findUnique, then create). Two simultaneous retries both see "not found" and both run. Let the database's unique constraint decide.
  • Keys that are global instead of per user, so one user could replay another user's response.
  • Not comparing the request body, so a reused key silently returns the response of a different order.
  • Keeping the key reserved after a failed request, which blocks the client from ever retrying.
  • Calling non-idempotent things "idempotent": a PUT that also increments a counter or sends an email every time.

  • (2) The insert fails with P2002. The row exists, the hash matches, but completedAt is null, so: 409 "still being processed". No second charge.
  • (3) The row exists, the hash matches, and it's completed: the stored body is returned with Idempotent-Replayed: true, status 201. The handler doesn't run.
  • (4) The row exists, but the hash differs: 422. The client has a bug (it reused a key for a different payment).

Interview questions

What does idempotent mean, and which HTTP methods are idempotent?

An operation is idempotent if performing it several times has the same effect on server state as performing it once. GET, HEAD, OPTIONS, PUT and DELETE are defined as idempotent. POST is not, and PATCH isn't guaranteed to be.

How would you make POST /payments safe to retry?

Require an Idempotency-Key header generated by the client per action. Store it with a unique constraint (scoped per user) and a hash of the request. The first request runs and saves its response; retries get the saved response; concurrent duplicates get 409; a reused key with a different body gets 422. Expire keys after a while.

Why isn't "check if the key exists, then insert" enough?

It's a race condition. Two concurrent requests can both see "not found" and both proceed. A database unique constraint (or primary key) makes the reservation atomic, so exactly one insert succeeds and the other gets a unique violation.

Remember Networks fail and clients retry, so design operations as "set to" where possible, protect important POSTs with an Idempotency-Key backed by a unique constraint, and let the database decide who wins.
