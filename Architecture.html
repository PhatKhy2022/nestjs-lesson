Layered architecture

controller, service, repository

In plain words

Think of a restaurant. The waiter takes your order and brings the food, but doesn't cook. The chef decides how to cook the dish, but doesn't talk to customers or go shopping. The storekeeper knows where every ingredient is kept, but doesn't care what dish it's for. Each person has one job, and they only talk to the person next to them.

A layered backend works the same way: the controller is the waiter (HTTP in, HTTP out), the service is the chef (business rules), and the repository is the storekeeper (reading and writing the database).

How it works

The running example. Our shop has users, products and orders. Here is the Prisma schema we'll use for the whole lesson. Money is stored as whole cents (Int) to avoid floating-point rounding problems:

Before: the "fat controller". This is what many first NestJS projects look like. It works, but everything is mixed together in one method:

Problems: you can't reuse "create an order" from a CLI command or a queue worker, because the logic is tied to HTTP. You can't unit-test the price calculation without a database. And when the method grows to 200 lines, nobody wants to touch it.

After: three layers. We split by responsibility. Each layer only calls the layer directly below it:

LayerKnows aboutMust NOT know aboutExample job
ControllerHTTP: routes, params, status codes, DTOsPrisma, SQL, business rulesRead the body, call the service, return the result
ServiceBusiness rules, use cases, transactionsreq/res, HTTP headers"Check stock, compute the total, create the order"
RepositoryPrisma / SQL, how data is storedHTTP, business decisions"Find products by ids", "insert an order"

The controller becomes thin. Its only job is translating HTTP into a method call:

The service holds the business logic. It talks about orders and stock, not about HTTP:

And the repository hides Prisma. It knows how to store things, not why:

The dependency rule. Arrows only point downwards: Controller → Service → Repository → Database. A repository never calls a service, and a service never imports Request from Express. If you follow this one rule, most "where does this code go?" questions answer themselves.

Why is this better? (1) Reuse: a nightly job can call ordersService.placeOrder() without HTTP. (2) Testing: you can test the service with a fake repository, no database needed. (3) Change: switching from REST to GraphQL changes only the controller. (4) Reading: a new developer knows where to look for a bug.

In a real NestJS project

The Nest CLI already pushes you towards layers: nest g resource orders generates a controller, a service, DTOs and a module. The repository layer is your own addition. Wire all three in the feature module:

Nest's own building blocks also fit into layers: guards, pipes and interceptors sit "in front of" the controller (HTTP layer), and exception filters turn errors into HTTP responses. Keep them in the HTTP layer too.

Common mistakes
  • Putting business rules in the controller ("if status is SHIPPED, reject"). Controllers should be boring: a few lines per route.
  • Passing req or res into a service. Pass plain values (userId, a DTO) instead.
  • A service that is just a pass-through to Prisma with nothing else in it, plus a repository that is also a pass-through. Two empty layers add files but no value (see the trade-offs topic).
  • Calling a repository directly from a controller, skipping the service. The rules in the service are then bypassed.

Interview questions

What is the responsibility of each layer in a NestJS app?

The controller handles HTTP: routing, reading params and body, choosing status codes. The service holds business logic and use cases. The repository handles persistence (Prisma queries). Each layer depends only on the one below it.

Why shouldn't a service receive the Express Request object?

It ties business logic to HTTP. The service can no longer be reused from a queue worker, a cron job or a GraphQL resolver, and tests have to build fake request objects. Pass only the values the service needs.

Where do you throw NotFoundException: service or controller?

In practice, most Nest teams throw it in the service because it's convenient and Nest maps it to 404 automatically. Stricter designs throw a domain error in the service and map it to HTTP in an exception filter, which keeps the service fully HTTP-free. Both are acceptable. Be consistent.

Remember Controller = HTTP, service = business rules, repository = data. Dependencies point downwards only, and a thin controller is a good controller.

Repository pattern

isolate Prisma from business logic

In plain words

A repository is like a library desk. You ask the librarian "give me the book with this ID" or "store this book", and you don't care whether the books are on shelf 3, in the basement, or in another building. If the library moves, you still talk to the same desk. In code, the service asks the repository for orders, and doesn't care whether they come from Prisma, raw SQL, or an in-memory list in a test.

How it works

The problem. When a service calls this.prisma.order.findMany({ ... }) directly, three things leak into business code: Prisma's query syntax, the database shape (column names, relations), and the need for a real database in every test. The same complex query also gets copy-pasted into several services.

Step 3: bind contract to implementation in the module. The service asks for OrdersRepository, and Nest hands it a PrismaOrdersRepository:

Step 4: enjoy easy tests. Because the service depends on the abstract class, a unit test can swap in a fake. No database, no Docker, and the test runs in milliseconds:

What about transactions? Placing an order must create the order and decrease stock atomically. Keep the transaction inside one repository method when the operation belongs together, so Prisma's $transaction doesn't leak into the service:

When a transaction must span several repositories, teams usually either pass a Prisma.TransactionClient as an optional parameter, or use a library such as @nestjs-cls/transactional that stores the transaction in async context. Start with the simple "one repository method per atomic operation" approach.

A shared PrismaService lives in a global PrismaModule, and each feature has its own repository that injects it. Repositories return Prisma's generated types (or domain objects, see the Mapper topic). A typical folder:

Common mistakes
  • A "generic repository" with findMany(where: any) that just forwards Prisma arguments. Prisma's syntax still leaks out, so you gain nothing. Name methods after business needs: findRecentPaid().
  • Putting business decisions in the repository ("if stock is low, send an email"). Repositories store and load. Services decide.
  • Using a TypeScript interface as the injection token. It disappears at runtime. Use an abstract class or a Symbol token with @Inject().
  • Starting a transaction in the service with this.prisma.$transaction and passing tx everywhere by hand, which brings Prisma right back into the service.

Interview questions

Prisma is already a data-access layer. Why add a repository on top?

Prisma gives you a typed query builder, but your services would still contain query details and depend on Prisma's API. A repository names queries in business terms, keeps them in one place, and makes services testable with simple fakes. For small CRUD apps it may be overkill, and that's a valid trade-off.

Why use an abstract class instead of an interface for the repository in Nest?

Nest's DI needs a runtime token. Interfaces are erased at compile time, while an abstract class remains a JavaScript value. So { provide: OrdersRepository, useClass: PrismaOrdersRepository } works and the service can inject it without @Inject().

How do you handle transactions with the repository pattern?

Prefer one repository method per atomic operation, using $transaction inside it. When an operation spans several repositories, pass a transaction client explicitly or use a "unit of work" helper based on async local storage (for example @nestjs-cls/transactional).

Remember A repository hides how data is stored behind methods named for what the business needs. Use an abstract class as the token, and keep all Prisma code inside it.

DTOs

class-validator and class-transformer

In plain words

A DTO (Data Transfer Object) is like a customs form at an airport. Everything that enters the country must be written on the form in a fixed format, and the officer checks it before you're allowed in. Your API does the same: every request body is checked against a DTO class, and anything wrong or unexpected is rejected at the door, before it reaches your business code.

How it works

Why a class? TypeScript types vanish at runtime (Lesson 1), so a body: CreateOrderDto annotation alone checks nothing. The JSON from the client could be { "items": "hello" }. A DTO class with decorators carries rules that still exist at runtime:

  • class-validator: decorators like @IsInt(), @Min(1) that describe the rules.
  • class-transformer: turns the plain JSON object into a real instance of your class, converting types (e.g. string "5" to number 5, nested objects to nested classes).
  • ValidationPipe: Nest glues the two together. It transforms, validates, and throws 400 Bad Request if anything fails.

Common mistakes
  • Forgetting @Type(() => ChildDto) on nested objects or arrays. Nested data is then never validated.
  • Not enabling whitelist, which allows mass assignment of fields like role or status.
  • Using an interface as a DTO. Nothing gets validated at runtime.
  • Returning a plain object (not a class instance) and expecting @Exclude() to hide fields. The serializer only applies rules to class instances.
  • Reusing the request DTO as the response type, which leaks internal fields or forces awkward optional properties.

Interview questions

What is the difference between class-validator and class-transformer?

class-transformer converts plain objects into class instances (and back), including type conversion and nested classes. class-validator checks an instance against the rules in its decorators. ValidationPipe uses the transformer first, then the validator.

What do whitelist and forbidNonWhitelisted do?

whitelist removes properties that have no validation decorator. forbidNonWhitelisted rejects the request with 400 instead of silently removing them. Together they prevent mass-assignment attacks.

Why do nested DTOs need @Type()?

JSON has no type information, so class-transformer can't know the nested object should become an OrderItemDto. Without that, the nested value stays a plain object and @ValidateNested has no rules to apply.

Remember DTOs are classes that guard the door: validate every input with class-validator, enable whitelist and transform, add @Type for nested data, and use separate DTOs for responses.

Feature modules

organize by domain, not by file type

In plain words

Imagine a supermarket that sorted products by material: all glass things in one aisle (jam jars, wine, light bulbs), all plastic things in another. To make breakfast you'd walk the whole shop. Real supermarkets sort by purpose: dairy, bakery, cleaning. Code is the same. Sorting by file type (controllers/, services/) means one change touches five folders. Sorting by feature (orders/, products/) keeps everything for one job in one place.

How it works

Before: organized by file type. To add a field to orders you open controllers/, services/, dto/ and repositories/. Nothing tells you which files belong together, and everything can import everything:

After: organized by feature (domain). Each folder is a Nest module with a clear boundary. Shared, feature-less code goes in common/ or infra/:

A module is a box with a door. In Nest, providers are private to their module by default. Only what you list in exports can be used by other modules. This is how you enforce boundaries:

The orders feature needs product information, so it imports the products module and uses its exported service:

If you try to inject ProductsRepository into OrdersService, Nest fails at startup with "Nest can't resolve dependencies of the OrdersService (OrdersRepository, ?)". That error is a feature: the module boundary just stopped someone from reaching into another feature's internals.

Infrastructure modules. Things every feature needs (database, config, logging) can be marked @Global() so you don't import them everywhere. Use this sparingly: only for true infrastructure, never for business features.

How big should a feature be? A good feature module matches a word your business people use: "orders", "payments", "catalog", "shipping". If two folders always change together, they're probably one feature. If one folder has 40 files covering unrelated things, split it.

By file typeBy feature
Adding a field to ordersEdit files in 4–5 foldersEdit files in orders/
BoundariesNone: anything imports anythingEnforced by module exports
Deleting a featureHunt across foldersDelete one folder + one import
Splitting into a microservice laterVery hardThe folder is already the boundary
In a real NestJS project

nest g resource orders generates a feature folder for you. Larger codebases often group features under src/modules/ and add a path alias (@modules/orders). Some teams also add an index.ts per feature that exports only the module, the public service and public DTOs, which documents the feature's public API:

Common mistakes
  • Exporting every provider "just in case". The boundary disappears, and features become tangled.
  • Making business modules @Global() to avoid writing imports. Dependencies become invisible.
  • A shared/ or common/ folder that slowly fills with business logic ("OrderUtils", "UserHelpers"). Common code should be feature-free.
  • Adding a provider to the providers array of two modules. You get two separate instances. Provide it once and export it.

Interview questions

Why organize by feature instead of by layer?

Changes usually happen per feature, so keeping its controller, service, repository and DTOs together reduces the number of places to touch. It also lets Nest modules enforce boundaries through exports, and makes features easier to delete or extract later.

What happens if you register the same service in two modules' providers?

Nest creates two separate instances, one per module. Any state (cache, counters) is not shared. The fix is to provide it in one module, export it, and import that module where needed.

When is @Global() appropriate?

For cross-cutting infrastructure that almost every module needs and that has no business meaning, such as Prisma, config or logging. Global business modules hide dependencies and should be avoided.

Remember One feature = one folder = one Nest module. Export only the public service, keep repositories private, and reserve @Global() for infrastructure.

Domain layer

separate business rules from infrastructure

In plain words

The rules of chess don't change if you play on a wooden board, a phone app, or by post. The rules are the domain; the board is infrastructure. In your shop, "a shipped order can't be cancelled" is a rule of the business. It's true no matter whether orders arrive by HTTP or a queue, or are saved in PostgreSQL or MongoDB. The domain layer is where these rules live, in plain TypeScript, with no framework or database code at all.

How it works

Before: rules scattered across services. The "can this order be cancelled?" rule is checked in the orders service, again in the admin service, and forgotten in the refund job:

An order's status is just a field anyone can overwrite. The "rule" exists only as copy-pasted if statements.

After: a domain model that protects its own rules. An Order class owns its state. The only way to change the status is through methods that check the rules. These are called invariants: things that must always be true.

Domain errors describe what went wrong in business terms. They don't know about HTTP status codes:

The service becomes an "application service": it loads the domain object, asks it to do something, and saves it. The rule lives in exactly one place:

The admin service and the refund job call order.cancel() too, so they can't forget the rule.

A common folder layout inside a feature that has real business rules:

You don't need this for every feature. A "tags" or "settings" feature with no rules is fine as plain controller + service + Prisma. Use a domain layer where the rules are rich: orders, payments, subscriptions, bookings.

Common mistakes
  • An "anemic" domain model: a class with only public fields and no methods, while all rules stay in services. You get the extra files without the protection.
  • Importing @nestjs/common exceptions (BadRequestException) into domain code. The domain shouldn't know about HTTP.
  • Using the Prisma-generated type as the domain model. Anyone can set status directly, and the rules are bypassed.
  • Running validation rules for new objects when restoring old ones from the database. Keep create() and restore() separate.

Interview questions

What belongs in the domain layer?

Business concepts and rules that are true regardless of technology: entities with behavior (order.cancel()), value objects (Money), invariants and domain errors. It must not depend on Nest, Prisma or HTTP.

What is an anemic domain model, and why is it a problem?

A model that is only data (getters and setters) while all logic lives in services. Rules get duplicated across services and can be bypassed by setting fields directly. A rich model encapsulates state and exposes behavior that enforces the rules.

How do domain errors become HTTP responses?

The domain throws its own error types with a business code. A global exception filter in the HTTP layer maps each code to a status (409, 422, …) and a response body. The domain stays independent of the transport.

Remember Put business rules inside domain objects written in plain TypeScript. Services orchestrate, the domain decides, and infrastructure stores.

Mapper pattern

entity vs DTO vs domain model

In plain words

The same thing can have different "costumes" depending on where it is. A song is a set of notes in the composer's head, a file on a server, and a sound coming out of a speaker. In your app, an order is a database row (Prisma entity), a business object with rules (domain model), and a JSON response (DTO). A mapper is the dressing room where one costume is changed into another, in one known place.

How it works

The three shapes of an order:

These three change for different reasons. If they're one object, renaming a database column breaks the public API, and a mobile app crashes. Mappers keep them independent.

Common mistakes
  • Returning Prisma rows straight from controllers, leaking columns like passwordHash or deletedAt and coupling the API to the schema.
  • Putting business logic in mappers ("if total > 100, add free shipping"). Mappers translate shapes, nothing more.
  • Mapping in many places (some in controllers, some in services, some inline). Pick one place per direction.
  • Returning Date objects or Decimal values and letting JSON.stringify decide the format. Be explicit (ISO strings, fixed decimals).

Interview questions

What's the difference between an entity, a domain model and a DTO?

The persistence entity mirrors the database table (Prisma type). The domain model represents the business concept with behavior and rules. The DTO is the shape of data crossing the API boundary. They change for different reasons, so mapping between them keeps those changes isolated.

Isn't mapping just boilerplate?

It is some extra code, but it buys a stable API that doesn't break when the schema changes, prevents data leaks, and keeps formatting in one place. In small CRUD features, a single response mapper (or a Prisma select) is often enough.

Where should mapping happen?

Persistence ⇄ domain mapping belongs in the repository (infrastructure). Domain → response DTO mapping belongs at the HTTP edge (controller or a dedicated presenter), or at the end of the service if the team prefers services to return DTOs. Be consistent.

Remember Row, domain object and DTO are three different shapes that change for different reasons. Translate between them in mappers, in one known place, and never return raw Prisma rows to clients.

SOLID

each principle with practical NestJS examples

In plain words

SOLID is five pieces of advice for writing classes that are easy to change. Think of building with LEGO instead of carving one big block of wood. Each brick does one thing (S), you add new bricks instead of re-carving old ones (O), any 2x4 brick fits where a 2x4 is expected (L), bricks only have the studs they need (I), and you design around the standard stud shape, not one specific brick (D).

How it works

S: Single Responsibility Principle. "A class should have only one reason to change." Here, "reason" means a person or team who could ask for a change.

Marketing can change the email without anyone touching order logic. (Later in the DI topic we'll go one step further and use events.)

O: Open/Closed Principle. "Open for extension, closed for modification": you should be able to add new behavior without editing working code. Classic smell: a growing switch.

L: Liskov Substitution Principle. "Any implementation must be usable wherever its abstraction is expected, without surprises." If the contract says findById returns null when nothing is found, every implementation must do that:

LSP is about behavior, not just types: the compiler checks signatures, but you must keep the promises (what's returned, what's thrown, side effects).

I: Interface Segregation Principle. "Don't force clients to depend on methods they don't use." Split big contracts into small, focused ones:

Note: TypeScript lets a class implements several abstract classes, because implements only checks the shape.

D: Dependency Inversion Principle. "High-level code should depend on abstractions, not on concrete details." The business logic (CheckoutService) shouldn't import the Stripe SDK. Both depend on the PaymentGateway abstraction:

Dependency Inversion (the principle) is achieved with dependency Injection (Nest's mechanism). Swapping Stripe for another provider, or for a fake in tests, is a one-line change in the module.

PrincipleSmell that breaks itNestJS tool that helps
SA 900-line serviceMore small providers, events
OEver-growing switch/if chainsStrategy classes + useFactory token
L"This implementation behaves differently, be careful"Clear contracts on abstract classes, shared contract tests
IMethods that throw "not implemented"Several small abstract classes
Dnew SomeSdk() inside a serviceCustom providers (useClass, useExisting, useFactory)
In a real NestJS project

Nest itself is built on SOLID ideas: guards, pipes, interceptors and filters are small single-purpose classes (S), you add behavior by adding new ones rather than editing the framework (O), and everything is wired through DI (D). In your own code, the two principles you'll use daily are S (keep services focused) and D (inject abstractions for external systems: payments, email, storage, SMS).

Common mistakes
  • Applying SOLID mechanically: an interface for every class, a strategy for every if. Use it where change actually happens.
  • Confusing Dependency Inversion (a design principle) with Dependency Injection (a technique). You can inject concrete classes and still violate DIP.
  • Splitting a class "by method" instead of "by reason to change", producing many tiny classes that always change together.
  • Implementations that silently weaken a contract (throwing where the contract returns null), which breaks LSP.

Interview questions

Explain the Single Responsibility Principle with a NestJS example.

A class should have one reason to change. An OrdersService that also renders emails and PDFs changes whenever marketing or accounting want something. Moving those into OrderNotifier and InvoiceService means each class changes for one audience only.

How does NestJS help with the Dependency Inversion Principle?

Its DI container lets high-level services depend on abstract classes or tokens, while modules bind those to concrete implementations with useClass, useExisting or useFactory. Services never construct their dependencies, so implementations can be swapped per environment or in tests.

Give an example of a Liskov violation.

A repository contract says findById returns null when not found, but one implementation throws an error instead. Code written against the contract (if (!order) throw new NotFoundException()) then behaves differently depending on the implementation.

Remember SOLID is a toolbox for code that changes. In Nest you'll use S and D every day, O for growing families of rules, and I/L to keep contracts small and honest.

DI design

avoid tight coupling between modules

In plain words

Dependency injection (DI) is like electricity in a house. Your lamp doesn't build its own power plant. It has a plug, and the house provides power. That keeps the lamp simple and lets you move it anywhere. But if every room's wiring is connected directly to every other room, one change makes the whole house flicker. Good DI design is about having a few clean sockets between rooms (modules), not a tangle of wires.

How it works

Signs of tight coupling between modules:

  • Circular dependencies: OrdersModule imports UsersModule and UsersModule imports OrdersModule, so you end up sprinkling forwardRef().
  • A service with 8+ constructor dependencies from 5 different modules.
  • Modules exporting their repositories so others can query their tables directly.
  • You can't test one feature without bootstrapping half the app.

Example: a circular dependency. When an order is paid, we update the user's loyalty points. And the users feature needs to show "number of orders" on the profile:

forwardRef() makes the error go away, but the design problem remains: two features that can't exist without each other are really one big feature.

Fix 1: invert the direction with events. The orders feature shouldn't need to know that loyalty points exist. It announces "an order was paid", and whoever cares listens. Install @nestjs/event-emitter:

Now the dependency only goes one way (users knows about the OrderPaidEvent class; orders knows nothing about users). Adding "send a thank-you email" later means adding a new listener; OrdersService stays untouched.

⚠️ In-process events are lost if the server crashes between saving and handling. For important side effects (money, emails that must be sent), teams use a durable queue (BullMQ) or the "outbox" pattern. In-memory events are fine for learning and for non-critical work.

Fix 2: move the shared read to the side that owns the data. "How many orders does this user have?" is an orders question. Instead of UsersService calling OrdersService, let the orders feature expose an endpoint (GET /users/:id/orders/count) or let a small "profile" feature compose both, depending on both modules while neither depends on the other:

Choose the right kind of provider. Nest gives you several ways to register a dependency. Using the right one keeps coupling low:

useValueConstants, test doubles{ provide: CLOCK, useValue: { now: () => new Date() } }
useFactoryBuilding something from config or other providersCreate an SDK client from ConfigService
useExistingAn alias: two tokens, one instance{ provide: RefundGateway, useExisting: StripeGateway }

Keep scopes simple. Providers are singletons by default: one instance for the whole app, which is fast. Scope.REQUEST creates a new instance per request, and it "bubbles up": every provider that injects a request-scoped one also becomes request-scoped. Avoid request scope unless you really need per-request state. Pass the needed value (like userId) as a method parameter instead.

In a real NestJS project

A healthy module graph looks like a tree or a layered graph, with arrows pointing towards more "basic" modules: features → shared domain modules → infrastructure (Prisma, config, mail). A few checks you can apply in code review:

  • Does this module export only services (never repositories)?
  • Is there any forwardRef()? If yes, can an event or a third module remove it?
  • Does any service call new on an infrastructure class (new Stripe(), new S3Client())? Move it to a factory provider.
  • Is process.env read inside services? Inject ConfigService instead.

Tools like madge --circular src can detect circular imports at the file level in CI.

Common mistakes
  • Using forwardRef() as a permanent fix for circular dependencies instead of redesigning.
  • Creating dependencies with new inside services, which makes them impossible to replace in tests.
  • Making a provider request-scoped "just in case", slowing down every request and every provider that depends on it.
  • Using events for everything, including calls that need a return value. If you need an answer, call a service. Use events for "something happened" notifications.
  • Injecting ModuleRef and resolving providers manually everywhere (service-locator style), which hides dependencies.

Interview questions

How do you resolve a circular dependency between two Nest modules?

forwardRef() is the quick fix, but the better fix is a redesign: make one direction an event (the producer doesn't know the consumer), move the shared logic into a third module that both depend on, or move the query to the module that owns the data.

What are the four kinds of custom providers?

useClass (bind a token to a class), useValue (a ready-made value), useFactory (build the value with a function that can inject other providers), and useExisting (alias one token to another provider's instance).

Why avoid request-scoped providers?

A new instance is created per request, which costs performance, and the scope propagates to every provider that depends on it. Most per-request data can be passed as method arguments or read from async local storage instead.

Remember Keep the module graph one-directional: export services, not repositories; use events to announce what happened; inject infrastructure through providers; and treat forwardRef() as a design warning.

Architecture trade-offs

avoid unnecessary over-engineering

In plain words

You don't build a garden shed with the foundations of a skyscraper. Every layer, abstraction and pattern in this lesson has a cost (more files, more indirection, slower onboarding) and a benefit (easier change, easier tests). Good architecture is not "use every pattern". It's choosing the patterns whose benefit is bigger than their cost for this project, right now, and leaving room to add more later.

How it works

A decision guide. Add a pattern when you can name the problem it solves today:

PatternWorth it when…Skip it when…
Service layerAlmost always (cheap, gives reuse)Rarely skipped
RepositoryComplex or reused queries; you want fast unit tests of servicesSimple CRUD where services just call findMany
Domain modelReal rules: state machines, money, limits, invariantsData in, data out, no rules
MappersPublic API must stay stable; shapes differA Prisma select already gives the exact shape
Strategy/abstraction2+ implementations exist, or an external system must be faked in tests"We might switch databases one day"
EventsSide effects owned by other features; breaking cyclesYou need the result immediately
MicroservicesIndependent teams, scaling or deployment needsOne team, one product, early stage: use a modular monolith

Key principles behind the guide:

  • YAGNI ("You Aren't Gonna Need It"): don't build for imagined futures. Abstractions for "maybe someday" usually guess wrong.
  • Rule of three: the first time, just write it. The second time, notice the duplication. The third time, extract an abstraction. By then you know what really varies.
  • Make it easy to change, not "future-proof": clear feature modules and thin controllers make refactoring cheap. That's better than guessing.
  • Consistency beats perfection: one well-understood pattern across the team is better than five clever ones.

Signs you've under-engineered: controllers with business logic; the same rule copied in three places; tests that need a database for simple logic; fear of changing anything. Signs you've over-engineered: adding a field touches 8 files; mappers that copy identical shapes; interfaces with exactly one implementation and no test fake; new team members need a diagram to add an endpoint.

In a real NestJS project

A pragmatic default that works for most NestJS + Prisma teams:

  • Feature modules for every domain area, with exports limited to services.
  • Thin controllers, validated DTOs, a global ValidationPipe, response shaping with Prisma select or a small mapper.
  • Services call Prisma directly until queries get complex or reused; then extract a repository for that feature.
  • A domain model only for the 2–3 features with rich rules (orders, payments, subscriptions).
  • Abstractions (tokens or abstract classes) for every external system: payments, email, storage, SMS. These are almost always worth it, because you need fakes in tests.

Write the agreed conventions down in a short ARCHITECTURE.md or as ADRs (Architecture Decision Records) so the team applies them consistently.

Common mistakes
  • Copying a "clean architecture" template with 10 folders per feature into a small CRUD project.
  • Adding abstractions "in case we switch from Prisma/PostgreSQL" when there's no plan to do so.
  • The opposite: refusing any structure ("we'll refactor later") until the code is too tangled to refactor safely.
  • Splitting into microservices to fix a messy monolith. You get a messy distributed system with network failures added.
  • Applying different patterns randomly per developer, with no team convention.

Interview questions

How do you decide whether to add a repository layer?

I add it when it solves a concrete problem: complex or duplicated queries, or the need to unit-test business logic without a database. For simple CRUD features, services using Prisma directly are clearer, and I can extract a repository later because the service already isolates the logic.

What is over-engineering, and how do you avoid it?

Adding structure whose cost (files, indirection, onboarding time) is greater than its benefit. Avoid it with YAGNI, the rule of three, and by tying every pattern to a problem you can name today, while keeping code modular enough to refactor cheaply later.

Monolith or microservices for a new NestJS product?

Usually a modular monolith: feature modules with clear boundaries in one deployable app. It's simpler to develop, test and deploy. If a module later needs independent scaling or a separate team, its boundaries already make extraction possible.

Remember Every pattern has a cost. Start simple with clear feature boundaries, add layers when a real problem appears, and let rich features be rich and simple features stay simple.
