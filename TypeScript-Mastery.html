Variables and types

let, const, type inference, strict mode

In plain words

JavaScript lets any variable hold anything, at any time. TypeScript adds a label to each variable that says what kind of value it is allowed to hold. If you break the rule, the editor underlines it in red before you run the code. The labels disappear when the code is compiled to JavaScript. They exist only to help you while writing.

How it works

const vs let. Use const when the variable will never be re-assigned, and let when it will. Never use var: it ignores block scope ({ }) and leads to confusing bugs. A good habit is to always start with const and switch to let only when the compiler tells you that you re-assign it.

Basic types. The primitive types are string, number (integers and decimals are both number), boolean, null, undefined, bigint and symbol. You write a type after a colon:

Type inference. You do not need to write the type everywhere. TypeScript looks at the value and works out the type for you. This is called inference. Good TypeScript code writes types at the "edges" (function parameters, public APIs) and lets inference handle the rest.

any vs unknown. any switches off type checking: anything goes, so bugs slip through. unknown means "I don't know the type yet". It is safe because TypeScript forces you to check the value before you use it.

Strict mode. In tsconfig.json, "strict": true turns on a group of safety checks. The two most important ones:

  • strictNullChecks: null and undefined are no longer allowed in every type. You must handle them explicitly. This catches the classic "Cannot read properties of undefined" bug.
  • noImplicitAny: if TypeScript can't infer a type, it reports an error instead of silently using any.
In a real NestJS project

A new Nest project (nest new) sets strictNullChecks but not full strict. Many teams switch on "strict": true right away. With strict mode, Prisma's findUnique() returns User | null, so the compiler forces you to handle "user not found", which is usually where you throw a NotFoundException.

Common mistakes
  • Using any to "make the red line go away". You lose all protection. Prefer unknown or a real type.
  • Thinking const makes an object immutable. It only prevents re-assignment. Use readonly or as const for immutability.
  • Writing types for everything (const x: number = 5). Let inference work. Annotate parameters and return types of public functions.
  • Using String / Number (capital letter). Those are wrapper objects. Always use lowercase string / number.

Interview questions

What is the difference between any and unknown?

Both accept any value. With any, TypeScript stops checking, so you can call anything on it. With unknown, you must narrow the type (with typeof, instanceof, a type guard…) before using it. unknown is the type-safe choice.

Do TypeScript types exist at runtime?

No. Types are erased during compilation, and the output is plain JavaScript. That's why you still need runtime validation (e.g. class-validator) for data coming from HTTP requests.

What does strictNullChecks do?

It removes null and undefined from every type unless you add them explicitly (e.g. string | null). The compiler then forces you to handle missing values, which prevents many runtime crashes.

Remember Start with const, let inference do the work, annotate the edges, avoid any, and always turn on strict.

Interfaces vs types

know when to use each and why

In plain words

Both interface and type let you give a name to a shape, so you can write User instead of repeating { id: number; email: string } everywhere. For describing objects they are 90% the same. The difference is in the edge cases: type can describe anything (unions, primitives, tuples), while interface only describes object shapes but can be extended and merged.

How it works

Things only type can do:

Things only interface can do: declaration merging. If you declare the same interface twice, TypeScript merges them. Libraries use this to let you add properties to their types.

Extending: interfaces use extends, types use & (intersection). Both work. extends gives clearer error messages and is slightly faster for the compiler on big hierarchies.

Union, tuple, primitive alias, function typetype (only option)
Mapped / computed types (keyof, Partial…)type
Augmenting a library type (e.g. Express Request)interface (declaration merging)
In a real NestJS project

A classic use of declaration merging is adding user to Express's Request after authentication:

Note that DTOs in Nest are classes, not interfaces or types. Classes exist at runtime, so ValidationPipe and Swagger can read them. Interfaces and types vanish after compilation.

Common mistakes
  • Using an interface for a request DTO in Nest. Validation decorators can't run on it, because it doesn't exist at runtime. Use a class.
  • Mixing interface and type randomly in one codebase. Pick a team convention (e.g. "interface for objects, type for everything else").
  • Accidentally merging an interface with an existing global one (e.g. naming yours Request or Event).

Interview questions

When must you use type instead of interface?

For anything that isn't an object shape: unions ('a' | 'b'), tuples, primitive aliases, and mapped/conditional types.

What is declaration merging?

When two interface declarations have the same name in the same scope, TypeScript combines their members into one interface. It's used to extend third-party types, such as adding user to Express's Request.

Why are NestJS DTOs classes rather than interfaces?

Interfaces are erased at compile time. Classes remain as JavaScript constructors, so decorators (@IsEmail(), @ApiProperty()) can attach metadata that ValidationPipe and Swagger read at runtime.

Remember interface = extendable object contract. type = can name any type. For runtime validation in Nest, use a class.

Functions

optional/default params, overloads, arrow functions

In plain words

A typed function is like a vending machine with clear labels: "put in these things, you will get this thing back". TypeScript checks every place you call the function, so you can't forget a parameter or pass the wrong kind.

How it works

Parameter and return types:

Return types are usually inferred, but writing them on exported functions is good practice. It documents the contract and catches mistakes inside the function body.

Optional (?) and default parameters:

Optional parameters must come after required ones.

Rest parameters collect "the rest" into an array:

Arrow functions are a shorter syntax. They also do not have their own this: they use the this of the surrounding code. That makes them perfect for callbacks inside classes.

void and never: void means "returns nothing useful". never means "never returns at all", because it always throws or loops forever.

Overloads let one function have several call signatures. You write the "public" signatures first, then one implementation that handles all of them.

Without overloads, both calls would return number | number[] and you'd have to check every time. If a union parameter is enough, prefer that. Use overloads only when the return type depends on the input type.

In a real NestJS project

Every controller handler and service method is a typed function. Default parameters show up in query handling, and async methods return Promise<T>:

Common mistakes
  • Using a regular function as a callback inside a class and losing this. Use an arrow function.
  • Putting an optional parameter before a required one. Not allowed, so reorder them or use an options object.
  • Too many positional parameters (createUser(a, b, c, d, e)). With more than 3, pass one object: createUser({ email, name, role }).
  • Writing overloads when a simple union would do.

Interview questions

What's the difference between an arrow function and a regular function?

Arrow functions don't have their own this, arguments or prototype, and can't be used with new. They capture this from the surrounding scope, which makes them ideal for callbacks.

What's the difference between void and never?

void: the function finishes but returns nothing meaningful. never: the function never finishes normally (it always throws or loops forever). never is also used for exhaustive checks.

When would you use function overloads?

When the return type depends on the type of the arguments, and you want callers to get a precise type without manual checks.

Remember Type the parameters, let the return type be inferred (but write it on exported functions), use arrow functions for callbacks, and use an options object for many parameters.

Generics

generic functions, classes and constraints

In plain words

A generic is a type parameter: a placeholder for a type that will be filled in later. Think of a box with a label slot. Box<T> means "a box of something". When you use it, you say Box<Apple> or Box<Book>, and TypeScript remembers what's inside. You write the code once and it works for many types, without losing type safety the way any would.

  • Using any where a generic would keep the type.
  • Adding generics that are used only once (function log<T>(x: T): void). If T doesn't connect two things (input → output), you probably don't need it.
  • Forgetting a constraint, then getting "Property 'id' does not exist on type 'T'".
  • Naming generics badly in complex code. T is fine for simple cases, but TEntity, TKey read better in bigger ones.

Interview questions

Why use generics instead of any?

Generics keep the relationship between input and output types. first<T>(arr: T[]): T returns the exact element type, while any throws the type information away.

What does <T extends X> mean?

It's a constraint: T can be any type, as long as it's assignable to X. That allows you to use X's properties inside the function.

Explain K extends keyof T.

keyof T is the union of T's property names. K extends keyof T means K must be one of those names, and T[K] is the type of that property.

Remember Generics are "type parameters". Use them when you need to keep a connection between types (input → output), and add extends constraints when you need to use properties.

Union & intersection types

narrowing and discriminated unions

In plain words

Union (A | B) means "either A or B", like a parcel that is either a letter or a box. Intersection (A & B) means "both A and B at the same time", like a person who is both an employee and a student. Narrowing is the process of checking which one you actually have, after which TypeScript knows the exact type.

How it works

Union types and narrowing:

Ways to narrow:

  • typeof x === 'string' for primitives
  • x instanceof Date for classes
  • 'prop' in x to check whether an object has a property
  • x === null, if (x) for null/undefined (truthiness)
  • Array.isArray(x) for arrays
  • A custom type guard: function isAdmin(u): u is Admin

Discriminated unions: the most useful pattern. Every member of the union has a common property (the "discriminant", often type or kind) with a different literal value. Checking that property narrows the whole object.

Intersection types combine several types into one:

In a real NestJS project

Discriminated unions are great for service results and domain events. They make "what can happen" explicit:

Prisma also uses unions heavily. For example, a where filter accepts string | StringFilter.

Common mistakes
  • Using as (type assertion) instead of narrowing: (x as Admin).permissions lies to the compiler and can crash at runtime.
  • Intersecting incompatible types, e.g. { a: string } & { a: number }. Then a becomes never and no value can satisfy it.
  • Forgetting the exhaustive never check, so new union members silently fall through.
  • Using optional fields instead of a discriminated union ({ success: boolean; data?: T; error?: string }), which allows invalid combos like success + error.

Interview questions

What is a discriminated union?

A union where each member has a common literal property (like kind: 'circle'). Checking that property lets TypeScript narrow to the exact member, so each case is fully typed.

What is type narrowing?

Refining a broad type into a more specific one through runtime checks (typeof, instanceof, in, equality, type guards). TypeScript follows the control flow and updates the type in each branch.

How do you make a switch exhaustive?

In the default branch, assign the value to a variable of type never. If any case is unhandled, the value isn't never, and compilation fails.

Remember | = one of, & = all of. Narrow with checks, not with as. Discriminated union + never check = bulletproof branching.

Enums

numeric, string and const enums

In plain words

An enum is a named list of fixed options, like the options in a dropdown menu. Instead of writing the magic string 'ADMIN' everywhere (and making a typo somewhere), you write Role.Admin, and the editor autocompletes it.

How it works

⚠️ Numeric enums are loosely checked in older TS versions, and the numbers are meaningless in logs and in the database (status: 2, but what is 2?).

String enums are the usual choice for backend code. The values are readable everywhere: logs, JSON, database.

Const enums are inlined at compile time: no JavaScript object is generated, and Role.Admin becomes literally 'ADMIN' in the output. They are faster, but they can't be iterated and cause problems with some build tools (isolatedModules). Avoid them unless you know why you need them.

Interview questions

String enum vs numeric enum: which do you prefer and why?

String enums. Their values are readable in logs, JSON and the database, and they don't change meaning if members are reordered.

What is a const enum?

An enum that is fully inlined at compile time: no runtime object exists. It's slightly faster, but you can't iterate it, and it doesn't work well with isolatedModules-based compilers.

What is the alternative to enums?

An as const object plus a derived union type. It's plain JavaScript, works with string literals, and is easy to iterate.

Remember Use string enums (or as const objects) for fixed sets of values. With Prisma, reuse the generated enums.

OOP

classes, constructors, access modifiers

In plain words

A class is a blueprint. An object (instance) is a thing built from that blueprint. The constructor is the setup step that runs when you build it. Access modifiers (public, private, protected) are like rooms in a house: some are open to visitors, some only to the family.

How it works

ModifierAccessible from
public (default)Anywhere
protectedThe class and its subclasses
privateOnly inside the class (compile-time only)
#fieldOnly inside the class, enforced at runtime by JavaScript
readonlyCan be set only in the declaration or constructor

Parameter properties: a TypeScript shortcut that declares and assigns a field in one go. Put a modifier in front of a constructor parameter:

The four OOP principles, briefly:

  • Encapsulation: hide internal data (private balance) and expose safe methods (deposit()), so rules can't be bypassed.
  • Abstraction: callers use a simple interface without knowing the details.
  • Inheritance: a class reuses another class (next topic).
  • Polymorphism: different classes respond to the same method call in their own way.
In a real NestJS project

Almost everything in Nest is a class: controllers, services, modules, guards, DTOs. The parameter-property shortcut is how Nest's dependency injection works. You'll write this hundreds of times:

private readonly is the convention: the dependency is internal to the service and should never be replaced.

Common mistakes
  • Thinking private protects data at runtime. It's a compile-time check only. Use #field if you need real runtime privacy.
  • Making all fields public and changing them from outside. That breaks encapsulation, and rules get bypassed.
  • Forgetting this. when accessing fields inside methods.
  • Putting heavy async work in the constructor. Constructors can't be async. In Nest, use onModuleInit() instead.

Interview questions

What's the difference between private and #private?

private is a TypeScript-only check and is erased in JavaScript, so the field is still accessible at runtime. #field is a native JavaScript private field, enforced by the runtime.

What are parameter properties?

Adding public/private/protected/readonly before a constructor parameter declares a class field and assigns it automatically. Nest uses this for dependency injection.

Explain encapsulation with an example.

Hiding internal state and exposing only controlled methods. For example, balance is private and can only change through deposit(), which validates the amount.

Remember Classes = blueprints. Keep state private, expose behavior through methods, and use constructor(private readonly x: X) {} for dependencies.

Inheritance

extends, super, abstract classes

In plain words

Inheritance means "this class is a kind of that class". A Dog is an Animal, so it gets everything an Animal has, and can add or change things. An abstract class is an unfinished blueprint: you can't build it directly, only extend it, and it can force children to implement certain methods.

How it works

  • extends: inherit from a parent class (only one parent is allowed).
  • super(...): call the parent constructor. It's required before using this in a child constructor.
  • super.method(): call the parent's version of a method.
  • override: explicitly marks a replaced method. With noImplicitOverride on, the compiler catches typos.

Abstract classes mix shared code with mandatory "fill-in-the-blank" methods:

This pattern, where the parent defines the steps and the children fill in the details, is called the Template Method pattern.

Composition over inheritance. Inheritance creates a tight bond between parent and child: changing the parent can break every child. Deep hierarchies (A → B → C → D) are hard to follow. Often it's better to give a class the thing it needs (composition) than to be that thing:

In a real NestJS project

Nest uses inheritance for its framework classes. You extend PassportStrategy, HttpException, AuthGuard('jwt'), or PrismaClient:

For your own business logic, prefer composition (inject services) over building big class hierarchies.

Common mistakes
  • Using this in a child constructor before calling super(). That's an error.
  • Building deep inheritance chains just to share one helper method. Use composition or a plain function.
  • Forgetting override, then renaming a parent method so the child silently stops overriding it. Turn on noImplicitOverride.

Interview questions

Abstract class vs interface?

An interface is a pure contract with no code, and a class can implement many interfaces. An abstract class can contain shared implementation and state, but a class can extend only one. Use an abstract class when children share real logic.

Why "composition over inheritance"?

Inheritance couples child to parent tightly, and changes ripple down. Composition (injecting collaborators) is more flexible, easier to test with mocks, and avoids fragile hierarchies.

What does super do?

super(...) calls the parent constructor. super.method() calls the parent's implementation of an overridden method.

Remember extends = "is a". Call super() first. Use abstract classes for shared logic with required hooks, and prefer composition for your own services.

Structural typing

implements, interfaces as contracts

In plain words

TypeScript cares about what something looks like, not what it is called. If an object has all the properties a type needs, it fits, even if it was never declared as that type. "If it walks like a duck and quacks like a duck, it's a duck." Java and C# work differently (nominal typing: the name must match).

How it works

Common mistakes
  • Trying to inject an interface directly (constructor(private s: Storage)) in Nest. It fails because the interface is gone at runtime. Use a token and @Inject().
  • Expecting instanceof SomeInterface to work. It can't, because interfaces aren't values.
  • Being surprised that two unrelated types with the same shape are interchangeable (e.g. UserId and OrderId both number). Use "branded types" if you need to tell them apart.

Interview questions

What is structural typing?

Type compatibility is decided by shape (members and their types), not by declared names. Any value with the required members fits the type.

Why can't you inject an interface in NestJS?

Nest's DI resolves dependencies at runtime using metadata, and interfaces are erased during compilation, so there's nothing to look up. You use a string or Symbol token with @Inject(TOKEN) instead.

Is implements required?

No. Structural typing would accept a matching shape anyway. implements documents intent and makes the compiler check the class at its definition, which gives clearer errors.

Remember Shape matters, names don't. Use interfaces as contracts with implements, and in Nest, inject them via a token.

Decorators

class, method, property and parameter decorators

In plain words

A decorator is a sticky note you put on a class, method, property or parameter with @something. Behind the scenes it's just a function that runs when the class is defined. Interview questions

What is a decorator, technically?

A function that is called at class definition time with information about the decorated element (class, method descriptor, property name or parameter index). It can attach metadata or replace or wrap the element.

What does emitDecoratorMetadata do and why does Nest need it?

It makes the compiler emit design:paramtypes metadata (the constructor parameter types) for decorated classes. Nest reads it to know which providers to inject, without you listing them manually.

What is a decorator factory?

A function that returns a decorator, so you can pass arguments: @Get(':id'), @MinLength(8).

Remember Decorators are functions that run once at class definition. They attach metadata or wrap behavior, and Nest reads that metadata to build your app.

Async TypeScript

Promise, async/await, error handling

In plain words

A Promise is like the buzzer a restaurant gives you: "your food isn't ready yet, but I promise to tell you when it is (or that something went wrong)". While you wait, you're free to do other things. Node.js is single-threaded, so instead of blocking while the database answers, it handles other requests. async/await is a nicer syntax for waiting on Promises that reads like normal top-to-bottom code.

How it works

Promise basics and typing:

async/await: an async function always returns a Promise. await pauses that function (not the whole server) until the Promise settles:

Error handling: a rejected Promise behaves like a thrown error, so you use try/catch. In catch, the error is typed unknown (with strict), so check it before use:

Sequential vs parallel: one of the biggest performance wins:

HelperBehavior
Promise.allWaits for all. Rejects immediately if any fails.

Promise.raceSettles with the first one to finish (useful for timeouts).

In a real NestJS project

Almost every service method is async, because Prisma calls return Promises. Nest automatically awaits whatever your controller returns. If your code throws an HttpException inside an async handler, Nest catches it and sends the right HTTP response:

Common mistakes
  • Forgetting await: const user = this.prisma.user.findUnique(...) gives you a Promise, not a user. Errors also escape your try/catch. Turn on the ESLint rule @typescript-eslint/no-floating-promises.
  • Using await inside a for loop over independent items, which makes it slow. Use Promise.all. But beware of firing 10,000 DB queries at once: batch them.
  • array.forEach(async (x) => ...): forEach doesn't wait. Use for...of or Promise.all(array.map(...)).
  • Swallowing errors: catch (e) {} with nothing inside hides bugs. Log the error and rethrow, or handle it properly.

Interview questions

What does an async function return?

Always a Promise. Returning a value resolves the Promise with it, and throwing rejects it.

Promise.all vs Promise.allSettled?

all rejects as soon as one promise rejects (fail-fast). allSettled waits for every promise and reports each outcome, so it's good when partial failure is acceptable.

Does await block the Node.js server?

No. It pauses only the current async function. The event loop keeps serving other requests while the awaited I/O completes.

Remember Always await your Promises, catch errors you can actually handle, and run independent work in parallel with Promise.all.

  • Thinking Omit<User, 'password'> removes the password at runtime. It only changes the type. You still need to actually remove it (destructuring, Prisma select, or class-transformer's @Exclude).
  • Copy-pasting types by hand instead of deriving them, so they drift apart over time.

Interview questions

Difference between Pick and Omit?

Pick keeps the listed keys. Omit keeps everything except the listed keys. Use whichever list is shorter and more stable.

How is Partial implemented?

As a mapped type: { [K in keyof T]?: T[K] }. It iterates over every key and adds the ? modifier.

Why use PartialType from Nest instead of TS Partial?

Nest's version produces a real class and copies the validation and Swagger metadata, with every rule made optional. TS Partial only exists at compile time.

Remember Derive types instead of duplicating them. Partial for updates, Omit to hide fields, Pick for subsets, Record for dictionaries, and Nest's PartialType for DTOs.

Modules

import/export, namespaces, barrel files

In plain words

Every .ts file with an import or export is a module: its own private room. Nothing inside is visible to other files unless you export it, and other files must import it explicitly. This prevents name clashes and makes dependencies obvious.

Note: these are TypeScript/JavaScript modules (files). NestJS @Module() is a different concept, covered in Lesson 2.

Type-only imports: import something only as a type. It is fully removed from the JavaScript output:

Barrel files: an index.ts that re-exports from a folder, so imports get shorter:

⚠️ Downside: barrels can create circular imports (A imports the barrel, the barrel imports B, B imports A). At runtime, one of them is undefined. In Nest, this shows up as the dreaded "Nest can't resolve dependencies… [?]" or "A circular dependency between modules" error. Use barrels for the public API of a folder, but import directly inside the same feature.

Namespaces are an older TypeScript way of grouping code (namespace Utils { ... }), from before ES modules existed. In modern code, use modules instead. You'll still see namespaces in .d.ts files, like declare global { namespace Express { ... } }.

CommonJS vs ES modules: Node.js has two module systems. require()/module.exports is CommonJS, and import/export is ESM. You write import/export in TS, and the compiler converts it based on "module" in tsconfig. NestJS projects compile to CommonJS by default.

Interview questions

Named vs default exports: which do you prefer?

Named exports. Names are consistent across imports, refactoring and auto-import work better, and a file can export many things clearly.

What is a barrel file and what's the risk?

An index.ts that re-exports a folder's contents for shorter imports. The risk is circular dependencies (some imports become undefined at runtime) and slower builds or tests from loading more than needed.

What does import type do?

It imports only type information, and the statement is removed entirely from the emitted JavaScript. That's good for avoiding runtime side effects and cycles, but don't use it for classes needed at runtime.

Remember One file = one module. Prefer named exports, use barrels carefully, avoid namespaces, and watch out for circular imports.

tsconfig

strict flags, paths, module resolution

In plain words

tsconfig.json is the settings file for the TypeScript compiler. It answers questions like: How strict should checking be? Which JavaScript version should I output? Where do the compiled files go? How do I find imported files? Understanding it means you're no longer scared when a build breaks.

How it works

The strict family. "strict": true enables all of these at once:

FlagWhat it catches
noImplicitAnyVariables or parameters whose type can't be inferred (silent any)
strictNullChecksUsing a value that might be null/undefined
strictPropertyInitializationClass fields never assigned in the constructor
strictFunctionTypesUnsafe function parameter assignments
strictBindCallApplyWrong arguments to .bind/.call/.apply
useUnknownInCatchVariablescatch (e) gives unknown instead of any
alwaysStrictEmits "use strict"

Extra flags worth knowing: noUnusedLocals, noUnusedParameters, and noUncheckedIndexedAccess (makes arr[0] typed as T | undefined, which is very safe but noisier).

⚠️ paths only tells the type checker where to look. The compiled JavaScript still contains '@common/...', which Node doesn't understand. The Nest CLI handles this for you during build, but tools like Jest need their own mapping (moduleNameMapper). Otherwise, plain node dist/main needs a helper like tsconfig-paths.

moduleResolution decides how an import string is turned into a file. "node" (Node 10 style, the Nest default with CommonJS) checks ./x.ts, ./x/index.ts and node_modules. In a real NestJS project

When you create a project with nest new, check whether "strict": true is on (newer versions set some flags but not all). Turning it on early is cheap. Turning it on later in a big codebase means fixing hundreds of errors. Also make sure experimentalDecorators and emitDecoratorMetadata stay true. Without them, dependency injection stops working.

Useful command: npx tsc --noEmit type-checks the whole project without building. It's great in CI.

Common mistakes
  • Leaving strict off and fighting null bugs at runtime instead.
  • Adding paths but forgetting Jest's moduleNameMapper, so tests fail with "Cannot find module '@common/...'".
  • Disabling emitDecoratorMetadata, after which Nest can't resolve any constructor dependencies.
  • Turning off checks (skipLibCheck is fine, but noImplicitAny: false is not) just to silence errors.

Interview questions

What does "strict": true enable?

A family of checks: noImplicitAny, strictNullChecks, strictPropertyInitialization, strictFunctionTypes, strictBindCallApply, useUnknownInCatchVariables, alwaysStrict and others. New strict checks added in future TS versions are included automatically.

Why might path aliases work in the editor but fail at runtime?

paths affects type resolution only. The emitted JavaScript keeps the alias, so the runtime (Node, Jest) needs its own mapping: a build step that rewrites paths, tsconfig-paths, or moduleNameMapper.

Difference between target and module?

target sets the JavaScript syntax level of the output (e.g. ES2021). module sets the module system used for imports and exports (e.g. CommonJS or ESNext).

Remember Turn on strict, keep the decorator flags on for Nest, use paths (and map them for Jest), and run tsc --noEmit in CI.
