Password hashing

bcrypt or argon2

In plain words

You must never keep a user's real password. Think of a meat grinder: you can turn a steak into minced meat, but you can never turn the minced meat back into the steak. A hash function is that grinder for passwords. When the user registers, you store only the "minced" version. When they log in, you grind the password they typed and check whether it gives the same result. If a hacker steals your database, they get only minced meat, and a slow grinder like bcrypt or argon2 makes guessing the original passwords very expensive.

How it works

Hashing is not encryption. Encryption is two-way: with the key you can decrypt. Hashing is one-way: there is no key and no "un-hash". That is exactly what we want for passwords. The server never needs to know the password again. It only needs to check it.

TechniqueReversible?Good for passwords?
Plain textNot needed, it's readable❌ Never
Encryption (AES)Yes, with the key❌ If the key leaks, all passwords leak
Fast hash (MD5, SHA-256)No❌ A GPU can try billions of guesses per second
Slow password hash (bcrypt, argon2id)No✅ Designed to be slow and salted

Why "slow" matters. Attackers who steal a database do not reverse hashes. They guess: hash "123456", compare, hash "password", compare, and so on, using huge lists of leaked passwords. SHA-256 is designed to be fast, so a single graphics card can test billions of guesses per second. bcrypt and argon2 are designed to be slow on purpose (about 50–250 ms per hash), and argon2 also needs a lot of memory, which GPUs are bad at. For your login endpoint, 100 ms is nothing. For an attacker who wants to try a billion guesses, it is years of work.

Why "salted" matters. A salt is a random value mixed into each password before hashing. Two users with the password Summer2024! get completely different hashes. This kills "rainbow tables" (pre-computed hash lists) and stops an attacker from cracking everybody who shares the same password at once. bcrypt and argon2 generate the salt for you and store it inside the hash string, so you need only one column.

Common mistakes
  • Using MD5, SHA-1 or SHA-256 for passwords "because it's a hash". They are far too fast. Use argon2id or bcrypt.
  • Swapping the argument order: it's argon2.verify(hash, plain) but bcrypt.compare(plain, hash). The wrong order simply returns false, which looks like "wrong password".
  • Returning the user object straight from Prisma, so passwordHash ends up in the JSON response. Use select or a response DTO.
  • Logging the request body of /auth/register or /auth/login, so plain passwords end up in your log files.
  • Using the synchronous APIs (bcrypt.hashSync). They block the event loop for 100+ ms, so every other request waits.

Interview questions

Why not just encrypt passwords with AES?

Encryption is reversible. Whoever gets the key (a leaked .env, a malicious insider) can decrypt every password. Hashing is one-way, so even the server can't recover the password. The server only needs to verify it.

What is a salt, and where is it stored?

A random value added to each password before hashing, so identical passwords produce different hashes and pre-computed tables are useless. bcrypt and argon2 store the salt inside the hash string, so no separate column is needed. The salt is not secret.

Why is a slow hash function good here, when we usually want fast code?

The legitimate server hashes once per login, so 100 ms is fine. An attacker must hash billions of guesses, so every millisecond is multiplied by billions. Memory-hard algorithms like argon2id also make GPU and ASIC attacks much more expensive.

Remember Store only an argon2id (or bcrypt) hash, verify with the library's own verify/compare, and never let the hash leave the server.

JWT

access tokens and refresh tokens

In plain words

A JWT is like a festival wristband. At the entrance (login) you show your ID once, and you get a wristband printed with "Name: An, VIP: yes, valid until 18:00", plus a tamper-proof seal. After that, every stand just looks at the wristband. It doesn't call the entrance to ask who you are. The seal proves the festival printed it, and nobody can change "VIP: no" to "VIP: yes" without breaking the seal. An access token is a wristband that expires quickly (minutes). A refresh token is a voucher, kept safely in your pocket, that you can trade at the entrance for a new wristband.

How it works

Structure. A JWT (JSON Web Token) is three Base64URL strings joined by dots: header.payload.signature.

The important lesson: the payload is only encoded, not encrypted. Anyone can paste a token into jwt.io and read it. The signature does not hide the data. It only proves that the data was created by someone who knows the secret and hasn't been changed since. So never put secrets (passwords, card numbers, internal notes) in a JWT.

Standard claims. "Claims" are the fields in the payload. Some have reserved names:

ClaimMeaningExample
subSubject: who the token is about (the user id)42
iatIssued at (Unix seconds)1728120000
expExpires at. Verification fails after it1728120900 (+15 min)
jtiJWT ID: a unique id for this token"9b1d…"
iss / audIssuer / audience: who made it, who it is for"shop-api"

Signing and verifying with @nestjs/jwt. JwtService wraps the jsonwebtoken library. signAsync creates a token; verifyAsync checks the signature and the expiry, and throws if either is wrong.

Why two tokens? A JWT is stateless: the server checks it with maths only, no database lookup. That is fast and scales well, but it has a big downside: you can't easily cancel a JWT before it expires. If a token valid for 30 days is stolen, the thief has 30 days. The solution is to split the job in two:

Access tokenRefresh token
PurposeSent with every API requestUsed only to get a new access token
LifetimeShort: 5–15 minutesLong: 7–30 days
Checked howSignature only (stateless, fast)Signature and database record (can be revoked)
Where the client keeps itMemory (JS variable)httpOnly cookie, sent only to /auth/refresh
SecretJWT_ACCESS_SECRETJWT_REFRESH_SECRET (different!)

So a stolen access token works for at most 15 minutes, and a stolen refresh token can be revoked in the database. You get the speed of stateless tokens for 99% of requests and control over the long-lived part.

Algorithms. HS256 uses one shared secret to sign and verify: simple, fine when only your API verifies tokens. RS256/ES256 sign with a private key and verify with a public key: useful when other services must verify tokens but must not be able to create them. For a single NestJS API, HS256 with a long random secret (at least 32 bytes) is fine.

In a real NestJS project

Step 2 of our flow: configure JwtModule and add a login method that returns a token pair. Lifetimes are written as literal constants. This also keeps TypeScript happy, because newer jsonwebtoken types accept only strings like '15m' or a number of seconds, not any string.

Common mistakes
  • Putting sensitive data in the payload, believing it's encrypted. It's only Base64. Anybody can read it.
  • Long-lived access tokens (7 days, "never expires"), so a stolen token can't be stopped. Keep access tokens short and use refresh tokens.
  • Using the same secret for access and refresh tokens, so a refresh token is accepted as an access token. Use different secrets (or check a typ claim).
  • Using jwt.decode() to read a token you then trust. Only verify checks the signature.
  • Weak or committed secrets ("secret", "jwt123"). Generate long random secrets and keep them out of git.
Practice exercise

A colleague suggests: "Let's put isPaidCustomer and the user's address in the access token, so we don't hit the database." Which of these is OK, which isn't, and why? Also: what happens if an admin changes a user's role from ADMIN to USER?

Show answer

Address: no. It is personal data, and the payload is readable by anyone who sees the token (browser extensions, logs, proxies).

isPaidCustomer: technically possible, but risky. It is not secret, but it can become stale. If the subscription ends, the token still says true until it expires.

Role change: the old access token still says ADMIN until it expires (max 15 minutes). This is the accepted trade-off of short-lived access tokens. If you need instant effect, revoke the user's refresh tokens and, for very sensitive actions, re-check the role in the database.

Interview questions

Is a JWT encrypted?

A normal JWT (JWS) is signed, not encrypted. The header and payload are Base64URL-encoded and readable by anyone. The signature guarantees integrity and authenticity, not confidentiality. Encrypted tokens (JWE) exist, but they are rarely needed.

Why use both access and refresh tokens instead of one long-lived token?

Access tokens are verified without a database lookup, so they can't be revoked. Keeping them short limits the damage of theft. The long-lived refresh token is checked against the database on every use, so it can be revoked (logout, password change, theft detection).

HS256 vs RS256?

HS256 is symmetric: the same secret signs and verifies, so every verifier could also forge tokens. RS256 is asymmetric: a private key signs, and the public key only verifies. Use RS256 when several services or third parties verify your tokens.

Remember A JWT is a signed, readable claim. Keep access tokens short and stateless, and keep refresh tokens long-lived, stored in the database and revocable.

Passport strategies

local strategy and jwt strategy

In plain words

Passport is a security desk with interchangeable "checkers". Each checker (a strategy) knows how to check one kind of proof. The local checker looks at an email and a password. The jwt checker looks at the wristband (token) in the Authorization header. Whichever checker you choose, the result is the same: if the proof is good, the person's details are pinned to the request as req.user. If not, the request is turned away with 401.

How it works

The three pieces. In NestJS, Passport has three parts that are easy to mix up:

PieceWhat it isExample
StrategyA provider class that knows how to check a credential. It has a validate() methodLocalStrategy, JwtStrategy
Strategy nameA string that links a guard to a strategy'local', 'jwt'
GuardAuthGuard('name'): runs the strategy for a route@UseGuards(AuthGuard('local'))

The flow for every request: the guard calls Passport → Passport extracts the credential (body fields, header…) → it calls your validate() → whatever validate() returns becomes req.user. If validate() throws, or returns null/false, the request fails with 401.

Step 1: validateUser in the service. The strategy should stay thin. The real logic (find the user, compare the hash) lives in AuthService, where it is easy to test.

Why the dummy hash? If unknown emails return in 2 ms but known emails take 100 ms (because of argon2), an attacker can measure the response time and find out which emails are registered. Doing the same slow work in both cases removes that signal. For the same reason, the error message is always "Invalid email or password", never "email not found".

Step 2: the local strategy. passport-local reads username and password from the body by default. We use email, so we tell it with usernameField.

Step 3: the JWT strategy. passport-jwt does the heavy work: it extracts the token, verifies the signature and checks exp. Your validate() is called only for a valid token, with the decoded payload.

Notice there is no database call in JwtStrategy.validate(). That's the stateless benefit of JWTs. You can load the user there (for example, to reject banned users immediately), but then every request costs one query. It is a conscious trade-off, not a rule.

Step 4: register everything. Strategies are providers. If you forget to list them, you get the error "Unknown authentication strategy 'jwt'".

Common mistakes
  • Forgetting to add the strategy to providers, which leads to "Unknown authentication strategy" at runtime.
  • Forgetting usernameField: 'email', so passport-local looks for username, finds nothing and returns 401 for every login.
  • Putting hashing and database logic directly inside validate(). Keep strategies thin and the logic in a testable service.
  • Different error messages for "unknown email" and "wrong password". That lets attackers discover which emails are registered.
  • Returning the full Prisma user (with passwordHash) from validate(), where it may end up in responses or logs.

Interview questions

What does a Passport strategy's validate() return, and where does it go?

It returns the authenticated "user" object, and Passport attaches it to req.user. Throwing (for example UnauthorizedException) or returning a falsy value makes the guard reject the request with 401.

Does JwtStrategy.validate() run for an expired token?

No. passport-jwt verifies the signature and expiry first. validate() is only called with the payload of a valid token, unless you set ignoreExpiration: true, which you should not do for access tokens.

Why is the login route protected by a guard instead of checking the password in the controller?

It keeps the controller simple and reuses the Passport pipeline: the guard runs the local strategy, rejects bad credentials with 401 before the handler runs, and gives the handler a ready req.user. Checking in the controller also works. Passport is a convention, not a requirement.

Remember A strategy checks one kind of credential and returns req.user. local checks email + password once, and jwt checks the bearer token on every request.

Guards

AuthGuard and custom guards

In plain words

A guard is the bouncer at the door of a route. Before the controller method runs, the bouncer looks at the request and answers one question: "Can this request come in? Yes or no." If yes, the request continues. If no, it is stopped right there and the controller code never runs. AuthGuard('jwt') is a ready-made bouncer that checks tokens, and you can write your own bouncers for any other rule.

How it works

A guard is a class with canActivate(). It receives an ExecutionContext (a wrapper around the current request) and returns true (allow) or false (deny). It can be sync or async. Returning false makes Nest throw a ForbiddenException (403). If you want another status, throw the exception yourself, for example UnauthorizedException (401).

Where guards run. Guards run after middleware and before interceptors, pipes and your handler:

That's why guards are the right place for "is this allowed at all?" decisions. They have access to the request and to metadata (via Reflector), which middleware doesn't have.

A custom guard from scratch. Example: an internal endpoint used by a cron service, protected with a static API key in the x-api-key header.

Three scopes.

ScopeHowWhen to use
Method@UseGuards(X) on a handlerOne special route
Controller@UseGuards(X) on the classAll routes of one resource
Global{ provide: APP_GUARD, useClass: X } in a moduleRules that apply everywhere, like "must be logged in"

Order: global guards run first, then controller guards, then method guards. All of them must say yes.

Secure by default: a global JWT guard plus @Public(). If you add @UseGuards(JwtAuthGuard) to each controller, one day someone forgets it, and an endpoint is open to the world. Common mistakes
  • Registering a global guard with app.useGlobalGuards(new JwtAuthGuard()), so Reflector is not injected. Use APP_GUARD.
  • Using reflector.get(KEY, context.getHandler()) only, so @Public() on a whole controller is ignored. Use getAllAndOverride with handler and class.
  • Doing authentication in middleware. Middleware doesn't know which handler will run, so it can't read decorators like @Public() or @Roles().
  • Returning false when you mean "not logged in". That gives 403. Throw UnauthorizedException for 401.
  • Comparing secrets with === in an API-key guard. Prefer timingSafeEqual.

Interview questions

Guard vs middleware vs interceptor: which one for authorization?

A guard. It runs before the handler and has access to the ExecutionContext, so it knows which handler and class will run and can read their metadata (@Public(), @Roles()). Middleware doesn't know the handler. Interceptors run after guards and are meant for transforming requests and responses.

What happens when canActivate returns false?

Nest throws a ForbiddenException, so the client gets 403 and the handler never runs. To return another status (for example 401), throw that exception yourself.

How do you make all routes protected by default but allow a few public ones?

Register a JWT guard globally with APP_GUARD, create a @Public() decorator with SetMetadata, and in the guard check that metadata with Reflector.getAllAndOverride. If it is set, return true without checking the token.

Remember Guards decide "may this request reach the handler?". Protect everything globally with APP_GUARD, and opt out explicitly with @Public().

RBAC

role-based and permission-based access control

In plain words

Authentication answers "who are you?" (your ID card). Authorization answers "what are you allowed to do?" (which doors your key card opens). In a hotel, guests' cards open their own room, cleaners' cards open every room on their floor, and the manager's card opens everything. That's role-based access control (RBAC): you give people roles, and each role comes with a set of rights. Permission-based control is the finer version: instead of asking "is this a manager?", the door asks "does this card have the open-storage-room permission?".

How it works

401 vs 403. These two status codes match the two questions:

StatusMeaningExample
401 Unauthorized"I don't know who you are." Missing, invalid or expired tokenNo Authorization header
403 Forbidden"I know who you are, but you may not do this"A USER calls DELETE /products/5

Step 1: a @Roles() decorator. It stores the allowed roles as metadata on the route. We reuse the Role enum generated by Prisma, so roles in code and in the database can never drift apart.

Step 2: a RolesGuard. It runs after the JWT guard, so req.user is already set. If a route has no @Roles(), any logged-in user may call it.

The order of APP_GUARD providers is the order the guards run in. If RolesGuard ran first, req.user would still be empty.

Step 3: permission-based access. Roles become clumsy as an app grows. You start writing @Roles('ADMIN', 'MANAGER', 'SUPPORT') everywhere, and adding a new role means editing dozens of controllers. The fix: routes ask for a permission (an action), and one central map says which role has which permissions.

Register it as a third global guard, after JwtAuthGuard: { provide: APP_GUARD, useClass: PermissionsGuard }. Now adding a SUPPORT role (can read all orders and refund, nothing else) means changing the enum and one line in the map. No controller changes at all.

Step 4: ownership, the rule guards can't handle alone. "A user may see their own orders" depends on the data, not only on the role. The guard doesn't know who owns order 17 without loading it. The cleanest place is the service query itself: add the owner to the where clause.

ApproachQuestion it answersWhere to check
Role-based"Is the user an ADMIN?"Guard + @Roles()
Permission-based"Can this user product:delete?"Guard + @RequirePermissions()
Ownership / attribute-based"Is this their order?"Service / query (or a library like CASL)
In a real NestJS project

Step 5 of our flow: the products and orders controllers combine everything. The global guards handle authentication and permissions; the service handles ownership.

For complex rules ("editors can update articles in their own team that are not yet published") look at CASL, which the NestJS docs recommend for attribute-based access control.

Common mistakes
  • Checking only the role and forgetting ownership. Every logged-in user can then read /orders/1, /orders/2… (IDOR, a top OWASP risk).
  • Registering RolesGuard before the JWT guard, so req.user is undefined and every protected call fails.
  • Hiding admin buttons in the frontend and calling that "security". The API must enforce every rule itself.
  • Hard-coding role strings like 'admin' in many places. Use the Prisma Role enum or a central permission map.
  • Returning 403 for someone else's resource, which confirms that it exists. 404 is often the better answer.

Interview questions

What is the difference between authentication and authorization?

Authentication proves identity ("who are you?"), for example with a password or a token. Failing it gives 401. Authorization decides what that identity may do ("are you allowed?"), for example with roles, permissions or ownership. Failing it gives 403 (or 404 to hide the resource).

Why move from roles to permissions?

Routes that check roles must list every role that may access them, so adding or changing a role means editing many routes. With permissions, routes declare the action they need, and one map links roles to permissions. Changes happen in one place, and the code says what it means.

What is IDOR and how do you prevent it in a NestJS + Prisma app?

Insecure Direct Object Reference: a user changes an id in the URL and gets someone else's data, because the server checks only "logged in", not "owner". Prevent it by scoping queries to the current user (where: { id, userId: user.sub }), unless the user has an explicit "read any" permission.

Remember Guards check roles and permissions, and queries check ownership. Keep the role-to-permission map in one place, and remember that 401 means "who are you?" while 403 means "not allowed".

Refresh token rotation

handling expiry securely

In plain words

Imagine a voucher that can be exchanged for a new festival wristband. With rotation, every time you use the voucher, the desk tears it up and gives you a new voucher along with the new wristband. Each voucher works exactly once. Now suppose a thief copied your voucher. Either they use it first, and your copy no longer works, or you use it first, and theirs no longer works. Either way, the moment someone shows an already-used voucher, the desk knows something is wrong and cancels the whole chain of vouchers, so everyone has to log in again.

How it works

The problem. Access tokens expire after 15 minutes. Users shouldn't have to type their password every 15 minutes, so the client silently calls POST /auth/refresh with the refresh token. But a refresh token lives for days, so it's a valuable target. Rotation plus reuse detection limits the damage if one is stolen.

Step 1: store refresh tokens in the database. Each refresh token gets a row. The id is the token's jti. The familyId links all tokens that come from one login. We store only a hash of the token, so a database leak doesn't hand out working tokens.

Why SHA-256 here and not argon2? Passwords are short and guessable, so they need a slow hash. A refresh token is a long random value that can't be guessed, so a fast hash is enough. Also, bcrypt only uses the first 72 bytes, and the first 72 bytes of most JWTs (the header) are identical, so bcrypt would treat different tokens as equal.

Common mistakes
  • Protecting /auth/refresh with the access-token guard. The access token is usually expired when the client calls it, so mark the route @Public().
  • Not rotating (reusing the same refresh token for 30 days), so a stolen token works silently until it expires.
  • Storing refresh tokens in plain text in the database. Store a hash.
  • Check-then-update without atomicity: two parallel refreshes both pass the "not revoked" check. Use updateMany with revokedAt: null and check count.
  • Forgetting to revoke refresh tokens when the password changes, so an attacker with an old session stays logged in.

One request wins the atomic updateMany. The other gets count === 0, is treated as reuse, and the whole family is revoked, so the user is logged out. That's safe but annoying.

Interview questions

What is refresh token rotation and why does it help?

Every refresh issues a new refresh token and invalidates the old one, so each token is single-use. A stolen token either stops working when the real user refreshes, or, if the attacker uses it first, the real user's next refresh shows reuse. Either way, theft is detected and the session family can be revoked.

How do you log a user out when using JWTs?

Revoke the refresh token(s) in the database and clear the cookie. The current access token stays valid until it expires (a few minutes). That's acceptable because it is short. If you need instant logout, keep a small denylist of access-token jtis (for example in Redis) until their exp.

Where should a browser app store the refresh token?

In an httpOnly, Secure, SameSite=Strict cookie scoped to the auth path. JavaScript can't read it, so XSS can't steal it, and SameSite plus the narrow path limit CSRF. The short-lived access token can stay in memory.

Remember Refresh tokens are single-use: store a hash, rotate on every refresh, revoke the whole family on reuse, and keep them in an httpOnly cookie.

Session vs token auth

know the trade-offs

In plain words

There are two ways to remember a logged-in guest. Session: like a coat check. You get a small numbered ticket (a session id in a cookie), and the server keeps the real information on its shelf (memory or Redis). The ticket means nothing on its own; the server always looks it up. Token: like the festival wristband. All the information is printed on the wristband itself, so the server doesn't need a shelf, but it also can't easily take the wristband back. Neither is "better". They make different trade-offs.

How it works

Session-based auth, step by step.

Token-based auth (what we built in points 2–6): the server signs a token with the user data inside. On each request it verifies the signature and needs no lookup.

Sessions in NestJS. Nest uses the Express express-session middleware. In production, store sessions in Redis. The default in-memory store leaks memory and loses all sessions on restart, and with two app instances, users get logged out randomly.

The trade-offs.

ConcernServer sessionsStateless JWT
Logout / revoke✅ Instant: delete the session❌ Valid until exp (needs short TTL or a denylist)

The honest conclusion. For a classic web app where the browser and API live on the same site, sessions are simple and very secure. For an API used by mobile apps, SPAs on other domains, or other services, tokens are more convenient. Many real systems end up with a hybrid, like the one we built: a short-lived stateless access token for speed, and a stateful, revocable refresh token in an httpOnly cookie for control.

Common mistakes
  • Using the default in-memory session store in production: memory leaks, sessions lost on restart, and broken logins behind a load balancer.
  • Not regenerating the session id at login (session fixation).
  • Saying "JWTs are stateless, so we can't log users out". Short TTLs, refresh-token revocation and denylists solve it.
  • Putting a long-lived JWT in localStorage "because sessions are old-fashioned". You traded CSRF risk for XSS risk and lost revocation.
  • Using cookie-based sessions without SameSite or CSRF protection on state-changing routes.

Interview questions

What is the main advantage of server-side sessions over JWTs?

Control. The server owns the state, so logout, banning a user or changing a role takes effect on the very next request. With JWTs, the token stays valid until it expires unless you add extra machinery.

Why are cookie-based sessions exposed to CSRF, and how do you defend against it?

Browsers attach cookies automatically, even when another site triggers the request. Defences: SameSite=Lax or Strict cookies, CSRF tokens on state-changing requests, and checking the Origin header. Bearer tokens in headers aren't sent automatically, so they don't have this issue.

How do sessions work when you run 3 instances of the API?

All instances must share the session store, usually Redis. Otherwise a user who logs in on instance A appears logged out on B. The alternative, "sticky sessions" at the load balancer, is fragile.

Remember Sessions give control, and tokens give portability and statelessness. A short access token plus a revocable refresh token gives you most of both.

OAuth basics

third-party login flows

In plain words

"Sign in with Google" works like a hotel valet key. You don't give the valet your house keys (your Google password). Instead, Google, which you already trust, gives our shop a limited, temporary pass that says "this person is an@gmail.com, and you may read their name and email, nothing else". Our app never sees the Google password. OAuth 2.0 is the standard for handing out these limited passes, and OpenID Connect (OIDC) is a small layer on top that adds "and here's who the person is".

How it works

The actors.

RoleIn our example

Resource serverGoogle APIs that return the profile

The Authorization Code flow, the one you should use for logins:

Key ideas:

  • The code is not the token. The browser only ever sees a short-lived, one-time code. Swapping it for tokens needs the client_secret, which lives only on the server.
  • state is a random value the server generates and checks on return. It stops attackers from forcing their own login code into your callback (login CSRF).
  • PKCE ("pixy") adds a one-time secret pair (code_verifier / code_challenge), so a stolen code is useless. It is required for mobile apps and SPAs that can't keep a client secret, and recommended for everyone.
  • Scopes limit what you ask for. For login, openid email profile is enough. Don't ask for Drive access to log someone in.
  • Google's access token is for Google's APIs, not yours. After the callback, your API issues its own JWTs, so the rest of the app (guards, roles) works unchanged.

Other OAuth flows, so you recognise the names:

Linking accounts in the database. One user may log in with a password and with Google. Store external identities in a separate table, keyed by provider and the provider's stable user id (sub), not by email, because email addresses can change.

Common mistakes
  • Identifying users by the email from the provider instead of the provider's stable id (sub). Emails change and can be reused.
  • Auto-linking to an existing account by an unverified email. An attacker registers that email at some provider and takes over the account.
  • Putting your own JWT in the redirect URL (?token=...), where it lands in browser history, logs and Referer headers.
  • Skipping state (and PKCE), which opens the door to login CSRF and stolen authorization codes.
  • Using Google's access token as your API's auth token. Issue your own tokens after the callback.

Interview questions

What is the difference between OAuth 2.0 and OpenID Connect?

OAuth 2.0 is about authorization: giving an app limited access to resources (an access token). OpenID Connect adds authentication on top: an id_token (a JWT) and a standard userinfo endpoint that say who the user is. "Sign in with Google" is OIDC.

Why does the Authorization Code flow return a code instead of a token directly?

The code passes through the browser, which is a less trusted channel. It is short-lived, single-use, and useless without the client secret (or PKCE verifier). The real tokens are fetched in a direct server-to-server call, so they never appear in the URL or browser history.

What is the state parameter for?

It's a random value tied to the user's browser and sent with the authorization request. The callback must return the same value. That proves the callback belongs to a login this browser started, which prevents CSRF and session-swapping attacks.

Remember Use the Authorization Code flow (with state and PKCE), identify users by provider + sub, link only verified emails, and finish by issuing your own tokens.
