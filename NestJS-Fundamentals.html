Modules

@Module, imports, exports, providers

In plain words

Think of a NestJS app as a company and each module as a department: Users, Orders, Payments. Each department has its own staff (services) and its own front desk (controllers). Staff are private by default. If the Orders department needs help from someone in Users, the Users department must export that person, and Orders must import the Users department. The @Module() decorator is the department's org chart. Nest reads all the org charts at startup and wires everyone together.

How it works

A module is just a class with the @Module() decorator. The decorator takes an object with four keys:

KeyWhat goes in itQuestion it answers
controllersController classes"Which HTTP routes does this module own?"
providersServices, repositories, helpers, factories"Which classes should Nest create and inject inside this module?"
importsOther modules"Which other modules' exported providers do I need?"
exportsA subset of providers (or imported modules)"Which of my providers may other modules use?"

Step 1: the smallest module. Every app has one root module, usually AppModule. main.ts gives it to NestFactory, which builds the whole app from it.

Step 2: a feature module. Each business area gets its own folder and module. The CLI command nest g resource users creates the module, controller, service and DTOs for you.

Step 3: using another module's provider. OrdersService needs to look up the user who places an order. Two things must be true: UsersModule exports UsersService, and OrdersModule imports UsersModule.

Why not just add UsersService to the providers of OrdersModule? Because then Nest creates a second, separate instance of it inside OrdersModule, and it would also need all of UsersService's own dependencies. Providers belong to exactly one module. Others reach them through imports and exports.

Step 4: what happens if you forget. If OrdersModule does not import UsersModule, or UsersModule does not export UsersService, the app crashes at startup with one of the most common Nest errors:

Read it literally: "inside the OrdersModule context, I cannot find UsersService". The fix is always one of: add it to providers (if it belongs here), or import the module that exports it.

Step 5: global modules and re-exporting. Some providers are needed everywhere (database client, config, logger). Instead of importing their module in 20 places, you can mark it @Global(). A global module must still be imported once (usually in AppModule), and its exported providers then become available in every module.

A module can also re-export a module it imports, so its consumers get both: imports: [UsersModule], exports: [UsersModule]. This is useful for a "shared" module that bundles several common modules.

Step 6: dynamic modules (a first look). Some modules need settings when you import them. They expose a static method like forRoot() or register() that returns a configured module. You will use these constantly, even if you don't write them yourself yet:

Why modules exist at all: they give each feature a clear boundary. You can see at a glance what a feature exposes, you can test one module in isolation, and as the app grows you can even move a module into its own service. Modules are singletons: if five modules import UsersModule, they all share the same instance and the same UsersService.

In a real NestJS project

A typical NestJS + Prisma backend has a folder per feature and one global PrismaModule:

Common mistakes
  • Adding another module's service to your own providers instead of importing its module. You get a duplicate instance and often a new "can't resolve dependencies" error.
  • Exporting a provider but forgetting to import the module (or importing the module but forgetting to export the provider). Both sides are required.
  • Putting a module in providers or a service in imports. Modules go in imports, classes Nest should create go in providers.
  • Making everything @Global(). It hides dependencies and makes modules harder to understand and test. Keep it for infrastructure like Prisma or config.
  • One giant AppModule with every controller and service in it. Split by feature from day one.

Interview questions

What is the difference between imports, providers and exports?

providers lists classes that this module creates and owns. exports makes some of those providers visible to other modules. imports brings in other modules so this module can use whatever they export. A provider is private to its module unless exported.

Are modules singletons?

Yes. Each module is instantiated once, so every module that imports UsersModule shares the same UsersService instance (with the default scope). That's why it's safe to keep things like a database connection in a provider.

When would you use @Global()?

For infrastructure providers that almost every module needs, such as a PrismaService, configuration or a logger. For business features it's better to import modules explicitly so dependencies stay visible.

Remember A provider lives in one module. To share it: export it from its home module and import that module where you need it.

Controllers

routing, @Get/@Post/@Param/@Body

In plain words

A controller is the receptionist of a feature. It stands at the door, listens for HTTP requests ("GET /users/5"), pulls out the useful pieces (the id, the body, the query string), hands them to the right staff member (a service), and gives the answer back to the client. A good receptionist does not do the actual work: no database calls, no business rules. It just routes.

How it works

Step 1: a route prefix and a handler. @Controller('users') sets the path prefix for every route in the class. Method decorators (@Get, @Post, @Put, @Patch, @Delete) map an HTTP method plus a sub-path to a method.

Nest serializes whatever you return to JSON. If you return a Promise, Nest waits for it. You don't call res.json() like in Express.

Step 2: reading data from the request. Parameter decorators pull out parts of the request:

DecoratorReadsExample request
@Param('id')A path segmentGET /users/42 → '42'
@Query('page')A query-string valueGET /users?page=2 → '2'
@Body()The parsed JSON bodyPOST /users with { "email": "..." }
@Headers('authorization')A request headerBearer eyJ...
@Req() / @Res()The raw Express request / responseUse rarely (see below)

Important: path and query values always arrive as strings. Writing id: number does not convert anything, because TypeScript types disappear at runtime. That's why we use ParseIntPipe (you'll learn pipes in point 8).

Step 3: DTOs for the body. A DTO (Data Transfer Object) is a class that describes the shape of incoming data. It must be a class, not an interface, because Nest needs something that exists at runtime to validate against.

Step 4: status codes and route order. Defaults: 200 for most methods, 201 for @Post. Change them with @HttpCode(). Errors are thrown, not returned: throw new NotFoundException() becomes a 404. Routes are matched in the order they are declared, so put fixed paths before parameter paths:

Step 5: why avoid @Res(). As soon as you inject the raw response with @Res(), Nest stops sending the response for you, and interceptors that transform the return value no longer work. If you only need to set a header or cookie, use @Res({ passthrough: true }) so Nest still handles the body:

(Using import type is fine here because Response is only used as a type on a decorated parameter, not as a DI token.)

Common mistakes
  • Putting Prisma queries or business rules directly in the controller. It becomes untestable and impossible to reuse.
  • Expecting @Param('id') id: number to give a number. It's a string until a pipe converts it.
  • Declaring @Get(':id') before @Get('me') or @Get('search').
  • Using @Res() without passthrough and then wondering why the request hangs or why interceptors are skipped.
  • Using an interface as a DTO. Validation needs a class.

Interview questions

What is the responsibility of a controller?

Handling the HTTP layer: mapping routes to methods, extracting params, query, body and headers, and returning the response. Business logic and data access belong in services so they can be reused and tested without HTTP.

Why must DTOs be classes and not interfaces?

Interfaces are erased at compile time. Classes exist at runtime, so ValidationPipe and class-transformer can read the decorators on them and validate or transform the incoming data.

What happens when you use @Res() in a handler?

Nest switches to "library-specific mode": you must send the response yourself (res.json()), and features that work on the return value (interceptors mapping the result, @HttpCode) no longer apply. @Res({ passthrough: true }) keeps the standard behavior while giving access to the response object.

Remember Controllers map HTTP to methods and nothing more. Read inputs with @Param/@Query/@Body, convert them with pipes, and delegate to a service.

Providers & services

@Injectable and business logic separation

In plain words

If the controller is the receptionist, a service is the expert in the back office who actually does the work: checks the rules, talks to the database, calculates totals. A provider is the general name for anything Nest can create and hand to others: services, repositories, helpers, even plain values. @Injectable() is the badge that says "Nest, you are allowed to create this class and give it what it needs".

Step 2: what @Injectable() really does. It marks the class so TypeScript emits metadata about its constructor parameters (thanks to emitDecoratorMetadata). Nest reads that metadata to know what to inject. A class with no constructor dependencies would technically work without it, but always add it: the moment you add a dependency, it becomes required, and it documents the intent.

  • Testing: you can unit-test the service by passing a fake Prisma client, with no HTTP server.
  • Readability: the controller shows the API surface; the service shows the business rules.

Step 4: "provider" is more than "service". The short form providers: [UsersService] is shorthand for { provide: UsersService, useClass: UsersService }. A provider is really a pair: a token (the key) and a recipe (how to make the value).

Common mistakes
  • Forgetting @Injectable() on a class that has constructor dependencies.
  • Creating services with new UsersService() yourself. You bypass DI and must pass dependencies manually; tests can no longer swap them.
  • Storing per-request data (current user, request id) in a field of a singleton service. All users share that instance, so data leaks between requests.

Interview questions

What is the difference between a provider and a service?

A provider is anything registered in a module's providers array that Nest can inject: a class, a value, or the result of a factory. A service is a class provider that holds business logic. All services are providers, but not all providers are services.

Why keep business logic out of controllers?

So it can be reused by other entry points (REST, GraphQL, queues, cron jobs), unit-tested without HTTP, and read independently of routing concerns. Controllers then only translate HTTP to method calls.

Is it safe to keep state in a service?

Only state that is meant to be shared app-wide (a cache, a client connection). Services are singletons by default, so per-request or per-user data stored in a field would be shared between concurrent requests.

Remember Mark classes with @Injectable(), register them in providers, and put all business logic in services so controllers stay thin.

Dependency injection

constructor injection and provider scopes

In plain words

Imagine a restaurant kitchen. A chef doesn't go out to buy a stove, knives and ingredients before cooking. The restaurant provides them, and the chef just says "I need a stove and a knife". Dependency injection (DI) works the same way: a class lists what it needs in its constructor, and Nest's IoC container (the restaurant manager) creates those things and hands them over. The class never calls new on its dependencies.

How it works

Step 1: without DI. In plain JavaScript you might write:

Problems: every class creates its own copies (wasteful), configuration is scattered, and in tests you can't replace the real mailer with a fake one.

Step 2: constructor injection. With Nest you just declare what you need:

The private readonly in the constructor is a TypeScript shortcut that declares a field and assigns it in one go (you saw it in Lesson 1). readonly prevents accidental re-assignment.

Step 3: how Nest figures it out. At startup Nest does roughly this:

  1. Scans every module and collects its providers into a registry: token → recipe.
  2. For each class, reads the constructor parameter types from the metadata saved by emitDecoratorMetadata (here: [PrismaService, MailService]).
  3. Recursively creates those dependencies first (and their dependencies), then calls new OrdersService(prisma, mail).
  4. Caches the instance, so the next class needing OrdersService gets the same object.

The type in the constructor is the lookup key (the "token"). That's why it must be a class, which exists at runtime, and not an interface or type alias.

Step 4: custom tokens with @Inject(). When the dependency isn't a class (a config value, a third-party client, an interface), you use a string or Symbol token:

Step 5: the four provider recipes.

RecipeUse it whenExample
useClassNest should instantiate a class (maybe a different one per environment){ provide: MailService, useClass: FakeMailService }
useValueYou already have the value (constant, mock object){ provide: 'APP_NAME', useValue: 'shop-api' }
useFactoryCreating it needs code or other providers; can be asyncCreate a Redis client from ConfigService
useExistingAn alias: a second token pointing to the same instance{ provide: 'Logger', useExisting: AppLogger }

Step 6: provider scopes. A scope decides how often a new instance is created.

ScopeInstancesTypical use
Scope.DEFAULT (singleton)One for the whole appAlmost everything: services, Prisma, clients
Scope.REQUESTA new one for every incoming requestPer-request context (tenant id, request-scoped cache)
Scope.TRANSIENTA new one for every class that injects itA logger that stores the name of its consumer

The scope "bubbles up". If OrdersService injects a request-scoped TenantContext, then OrdersService also becomes request-scoped, and so does the controller that injects OrdersService. Now three objects are created for every request. This costs performance, so keep the default singleton scope unless you really need per-request state. Often, passing the value as a method argument is simpler.

In a real NestJS project

The biggest everyday benefit of DI is testing. In a unit test you build a small module and replace real providers with fakes:

Common mistakes
  • Injecting an interface or type: constructor(private gateway: PaymentGateway). Interfaces don't exist at runtime; use @Inject(TOKEN).
  • Using import type { UsersService } for an injected class. The import is erased, the metadata becomes undefined, and DI fails.
  • Making a provider Scope.REQUEST without realizing that every class depending on it becomes request-scoped too.
  • Typos in string tokens ('STRIPE_CLIENT' vs 'STRIPE-CLIENT'). Export a constant or Symbol and reuse it.

Interview questions

What is Inversion of Control (IoC)?

The control of creating and wiring objects is moved from your classes to a container. Classes declare their dependencies; the framework creates and supplies them. DI is the technique Nest uses to implement IoC.

How does Nest know what to inject into a constructor?

With emitDecoratorMetadata, TypeScript stores the constructor parameter types as design:paramtypes metadata on decorated classes. Nest reads it and uses each type (or an explicit @Inject() token) as a key into its provider registry.

What are the provider scopes and their trade-offs?

Default (singleton, one instance, fastest), Request (new instance per request, gives access to the request but adds overhead and bubbles up the dependency chain), and Transient (new instance per consumer). Prefer singletons.

Remember Ask for dependencies in the constructor, let Nest create them, use @Inject(TOKEN) for non-class values, and stay with singleton scope unless you truly need per-request state.

Request lifecycle

middleware → guards → interceptors → pipes → handler

In plain words

Think of airport security. Before you reach your gate (the handler), you pass several checkpoints in a fixed order: the entrance door (middleware), the passport check that can refuse you (guards), a camera that records when you entered and left (interceptors), and the bag scanner that checks and repacks your luggage (pipes). If something goes wrong anywhere, a supervisor (exception filter) decides what to tell you. Knowing this order tells you where each piece of logic belongs.

How it works

The full order for one HTTP request:

What each layer is for:

LayerKnows the target handler?Best for
MiddlewareNoLogging raw requests, request ids, CORS, cookies, body parsing
GuardYes (ExecutionContext)Yes/no decisions: is the user logged in? do they have the role?
InterceptorYesWrapping the handler: timing, caching, mapping the response, timeouts
PipePer argumentValidating and transforming input (@Body, @Param, @Query)
Exception filterYesTurning thrown errors into HTTP responses

Why this order makes sense. Authentication (guards) runs before validation (pipes), so an anonymous user gets a 401/403 instead of learning about your DTO rules. Interceptors run before pipes, so a timing interceptor measures validation too. Interceptors also run after the handler, which is why they can transform the response, while guards and pipes cannot.

Seeing it for yourself. Add a console.log in each layer and call the route:

Where errors go. If any layer throws (a guard returning false causes a ForbiddenException, a pipe throws BadRequestException, a service throws NotFoundException), the remaining steps are skipped and the exception filters take over. Note that errors thrown by middleware are also caught by Nest's filters.

Common mistakes
  • Doing authorization in middleware. Middleware doesn't know which handler will run, so it can't read @Roles() metadata. Use a guard.
  • Expecting a guard to see validated/transformed DTOs. Pipes run after guards.
  • Trying to change the response in a guard or pipe. Only interceptors (and filters, for errors) see the outgoing response.
  • Using app.useGlobalGuards(new JwtAuthGuard()) and then wondering why its injected dependencies are undefined. Use APP_GUARD to get DI.

Interview questions

Describe the NestJS request lifecycle.

Middleware → guards → interceptors (before) → pipes → handler → interceptors (after) → response. If an exception is thrown at any point, exception filters handle it. Within each layer, global bindings run first, then controller, then route (filters are the reverse: route first).

What is the difference between middleware and a guard?

Middleware is a plain Express-style function with req, res, next; it doesn't know which handler will execute. A guard receives an ExecutionContext, so it can read the handler and class metadata (e.g. required roles) and returns a boolean that decides whether the request continues.

Why use APP_GUARD instead of app.useGlobalGuards()?

useGlobalGuards() takes an instance you create with new, outside the DI container, so it can't inject dependencies. Registering with APP_GUARD in a module lets Nest construct it with full DI.

Remember Middleware → guards → interceptors → pipes → handler → interceptors → (filters on error). Put each concern in the layer that runs at the right moment and has the right information.

Middleware

custom middleware and applying it to routes

In plain words

Middleware is the doorman of your app. Every request walks past it before anything else happens. The doorman can look at the request, add a sticker to it ("request #8812"), write in a logbook, or turn someone away. Then he says "go on" by calling next(). If he forgets to say "go on", the visitor waits at the door forever. Nest middleware is the same as Express middleware, just organized as a class with DI.

How it works

Step 1: the Express idea. A middleware is a function (req, res, next). It must either send a response or call next().

Step 2: a class middleware in Nest. Implement NestMiddleware. Because it's @Injectable(), it can inject services.

Step 3: applying it. Middleware is not listed in @Module(). Instead, the module implements NestModule and its configure() method uses the MiddlewareConsumer:

forRoutes() accepts path strings, { path, method } objects or controller classes. exclude() removes specific routes. apply() takes several middleware at once, and they run in the order given.

Nest 11 note: Nest 11 uses Express 5, whose path matching changed. Named wildcards are now preferred, e.g. forRoutes('{*splat}') for all routes or 'users/*splat' for a sub-tree. Plain '*' still works for "everything" in Nest 11 (it is converted automatically with a warning), but use the new syntax in new code.

Step 4: functional middleware. If the middleware has no dependencies, a plain function is enough:

Step 5: global middleware in main.ts. Third-party Express middleware (helmet, cookie-parser, compression) is usually registered with app.use():

app.use() runs for every route but cannot use DI (you pass a function, not a Nest class). Class middleware applied through configure() can.

When not to use middleware. Middleware runs before Nest knows which controller method will handle the request, so it can't read decorators like @Roles('admin') or @Public(). For anything that depends on the handler, use a guard or an interceptor.

In a real NestJS project

Typical uses: request ids for tracing, HTTP access logs, raw-body capture for webhook signature checks, and third-party Express middleware. For example, Stripe webhooks need the raw body to verify the signature, so you enable it in main.ts:

Common mistakes
  • Forgetting to call next() (or to send a response). The request hangs until the client times out.
  • Trying to do role checks in middleware. It can't see handler metadata; use a guard.
  • Adding middleware to providers and expecting it to run. It only runs when applied through configure() or app.use().
  • Calling next() and sending a response, which leads to "Cannot set headers after they are sent".

Interview questions

How do you apply middleware in NestJS?

Implement NestModule on a module and use consumer.apply(...).forRoutes(...) in configure(), optionally with .exclude(). For global third-party middleware you can also call app.use() in main.ts.

Can middleware use dependency injection?

Class-based middleware marked @Injectable() and applied through MiddlewareConsumer can inject providers available in that module. Functional middleware and anything passed to app.use() cannot.

When would you choose middleware over an interceptor?

When the logic is generic, works on the raw request/response, and doesn't need to know the target handler or modify the returned value (request ids, access logs, security headers, cookies). If you need handler metadata or the response body, use an interceptor.

Remember Middleware is the first door: it sees every raw request, must call next(), and is applied with configure(), not with providers.

Exception filters

custom exceptions and global error handling

In plain words

When something goes wrong deep inside your app, the code just throws an error and stops. An exception filter is the customer-service desk that catches that error and decides what the client is told: which status code, which message, which format. It makes sure a crash in the database turns into a polite, consistent JSON answer instead of a stack trace.

How it works

Step 1: the built-in filter. Nest already has a global filter. When you throw an HttpException (or a subclass), it produces a JSON response:

In a real NestJS project

Common mistakes
  • Returning error objects (return { error: 'not found' }) instead of throwing. The client gets a 200 with an error inside.
  • Throwing plain Error('Not found') and getting a 500 instead of a 404. Use the HTTP exception classes or a filter that maps your domain errors.
  • Sending exception.message or stack traces of unknown errors to the client. This leaks internals (SQL, file paths). Log them, send a generic message.
  • Catching errors in every service method just to re-throw them. Let a global filter handle common cases.
  • Forgetting that a filter must send the response itself (res.status().json()); if it doesn't, the request hangs.

Interview questions

What happens to an error that is not an HttpException?

The built-in global filter treats it as unknown and responds with 500 "Internal server error", logging the details. To map it to something else (e.g. Prisma P2002 → 409), write a filter with @Catch(ThatErrorClass).

What is ArgumentsHost?

A wrapper around the arguments of the current handler that works across transports. host.switchToHttp() gives you the request and response for HTTP; switchToWs() and switchToRpc() exist for WebSockets and microservices.

How do you set up global error handling with DI?

Register the filter as a provider with the APP_FILTER token in a module. Unlike app.useGlobalFilters(new X()), Nest then constructs it, so it can inject a logger, config or other services.

Remember Throw, don't return, errors. Use HTTP exceptions for expected failures, and global filters to turn everything else (like Prisma errors) into consistent, safe responses.

Pipes

validation pipes and transformation pipes

In plain words

A pipe is a quality-control station on a conveyor belt, placed just before the handler. Every argument (the id, the body, the query) passes through it. The station does one of two jobs: validation ("is this item OK? if not, reject it with 400") or transformation ("turn the string '42' into the number 42"). By the time data reaches your method, it's guaranteed to be clean and correctly typed.

Interview questions

What are the two main uses of pipes?

Transformation (convert input to the desired form, e.g. string to number) and validation (check input and throw a 400 if invalid). Both run right before the handler, on each argument.

What do whitelist, forbidNonWhitelisted and transform do?

whitelist removes properties that have no validation decorator. forbidNonWhitelisted rejects the request instead of silently removing them. transform converts the plain payload into an instance of the DTO class and converts primitive params based on their types.

Why do guards run before pipes?

Authorization should be decided before spending effort validating input, and unauthorized users shouldn't receive detailed validation messages about your API.

Remember Never trust input. Use a global ValidationPipe with whitelist and transform, DTO classes with class-validator, and Parse*Pipe for params.

Guards

route protection and custom guards

In plain words

A guard is the bouncer at a club door. It looks at the visitor (the request) and the room they want to enter (the route), and answers one question: yes or no? "Do you have a valid wristband (JWT)? Is your name on the VIP list (role = admin)?" If the answer is no, the visitor never gets inside. A guard doesn't change the request's data or the response; it only decides.

How it works

Step 1: the interface. A guard implements CanActivate. Its canActivate() method returns true (continue) or false (Nest throws ForbiddenException, 403). It may return a boolean, a Promise or an Observable. It can also throw its own exception, e.g. UnauthorizedException (401).

Step 2: ExecutionContext. This is what makes guards smarter than middleware. Besides the request, it tells you which handler and controller will run:

Step 4: a roles guard using metadata. First a decorator that stores the required roles, then a guard that reads them with Reflector:

401 vs 403. 401 Unauthorized means "I don't know who you are" (no or bad token). 403 Forbidden means "I know who you are, but you're not allowed". Authentication guards throw 401; authorization guards throw 403.

In a real NestJS project

Most apps protect everything by default with a global guard and mark the few public routes with a @Public() decorator. It's safer: a new route is protected even if a developer forgets to add a guard.

For ownership rules ("a user may only see their own orders"), the guard usually isn't enough, because it would need to load the order. Do that check in the service with a Prisma query like findFirst({ where: { id, userId } }).

Common mistakes
  • Listing RolesGuard before JwtAuthGuard, so request.user is still empty when roles are checked.
  • Using reflector.get() with only the handler and missing roles set on the controller class. Use getAllAndOverride (or getAllAndMerge).
  • Returning false everywhere, so every failure is a 403. Throw UnauthorizedException when the user isn't authenticated.
  • Forgetting @Public() on login/register after adding a global guard, so nobody can log in.
  • Trusting the role from the request body instead of the verified token or database.

Interview questions

What is a guard and when does it run?

A class implementing CanActivate that decides whether a request may reach the handler. It runs after middleware and before interceptors and pipes. Returning false results in 403; it can also throw a specific exception.

How does a roles guard know which roles a route needs?

A decorator like @Roles('ADMIN') stores metadata on the handler or class with SetMetadata. The guard reads it through Reflector using context.getHandler() and context.getClass().

Why make authentication global with a @Public() opt-out?

It's secure by default: new routes are protected automatically, and only routes explicitly marked public are open. Opt-in protection risks forgetting a guard on a sensitive endpoint.

Remember Guards answer "may this request continue?". Authenticate first (401), then authorize with metadata and Reflector (403), and prefer a global guard with a @Public() escape hatch.

Interceptors

logging and response transformation

In plain words

An interceptor wraps your handler like a sandwich: it gets a slice of code before the handler runs and a slice after. Think of a delivery company: before the parcel leaves, they stamp the departure time; when it arrives, they stamp the arrival time and put it in a branded box. That's exactly what logging and response-wrapping interceptors do.

How it works

Step 1: the shape. An interceptor implements NestInterceptor. next.handle() calls the rest of the chain (pipes + handler) and returns an RxJS Observable of the result. Everything before next.handle() is "before"; the operators in .pipe() run "after".

Unlike middleware, the interceptor knows the handler name (OrdersController.create), because it receives an ExecutionContext.

Step 2: a tiny bit of RxJS. You only need a few operators:

tap()Do something with the result without changing it (logging, metrics)
map()Replace the result with a new value (response wrapping, serialization)
catchError()Turn an error into another error or a fallback value
timeout()Fail if the handler takes too long

If your handler is async and returns a Promise, Nest converts it to an Observable for you, so these operators work either way.

  • Expecting interceptors to work on routes that use @Res() without passthrough. You send the response yourself, so there's nothing to transform.
  • Wrapping responses in an envelope but forgetting that errors (from filters) won't be wrapped. Keep both formats consistent.

Interview questions

What can an interceptor do that a guard or middleware cannot?

It runs both before and after the handler and has access to the returned value as an Observable, so it can transform the response, measure total time including the handler, cache results, map errors or apply timeouts.

What does next.handle() return?

An RxJS Observable that emits the handler's result (Nest wraps Promises and plain values). You attach operators like map, tap or catchError to it and return it.

How would you hide a password field from all responses?

Prefer not to select it in the Prisma query (select / omit). As a second layer, return entity classes with @Exclude() and use ClassSerializerInterceptor globally.

Remember Interceptors wrap the handler: code before next.handle() runs first, RxJS operators after it see the result. Use tap to observe, map to transform.

How do you create a custom parameter decorator?

Configuration

ConfigModule and environment variables

In plain words

Your app runs in several places: your laptop, a test server, production. The code is the same, but the settings differ: database URL, secret keys, port. Environment variables are like sticky notes the computer gives the app at start-up. ConfigModule is the assistant who reads those notes (and a local .env file), checks that nothing important is missing, and answers "what's the database URL?" whenever a service asks.

How it works

Step 1: the .env file. A simple KEY=value file in the project root for local development. It must never be committed; commit a .env.example with fake values instead.

Step 2: ConfigModule.forRoot().

It loads the .env file into process.env. Real environment variables (set by Docker, your CI or your hosting provider) take precedence over values in the file, which is exactly what you want in production.

Why validate environment variables at start-up?

Circular dependencies

forwardRef and module design

In plain words

A circular dependency is a chicken-and-egg problem. UsersService needs OrdersService to be built first, but OrdersService needs UsersService to be built first. Nest can't decide where to start, so it stops. forwardRef() is a way to say "start anyway, I'll fill in the other one later". But usually the real fix is to redesign so the two don't need each other.

How it works

Step 1: how a cycle appears. It happens naturally as features grow:

Why "undefined"? It's a JavaScript problem, not only a Nest one. When users.module.ts imports orders.module.ts, which imports users.module.ts again, Node gives back the half-loaded file, where UsersModule is not defined yet. The decorator then receives undefined. The same can happen between two service files, and even through a barrel index.ts file.

Downsides: the order in which the two are created is not guaranteed, so you must not use the other service inside the constructor (only in methods), it doesn't work well with request-scoped providers, and it hides a design smell.

Interview questions

What is a circular dependency in NestJS and how do you resolve it?

Two providers or modules that depend on each other, so neither can be created first. The quick fix is forwardRef(() => X) in both module imports and both @Inject()s. The better fix is to restructure: extract shared logic, use events, or query the data layer directly.

Why do circular imports produce undefined?

Node's module loader returns a partially initialized module when a cycle is detected, so a class exported later in that file is still undefined when the other file reads it. forwardRef defers reading it until both files are fully loaded.

What are the limitations of forwardRef?

Creation order is not guaranteed, so the injected instance must not be used in a constructor. It is problematic with request-scoped providers, and it hides tight coupling that makes code harder to test and reason about.

Remember forwardRef is a patch, not a design. Keep the module graph flowing in one direction, and break cycles with a third module, events, or direct Prisma queries.
