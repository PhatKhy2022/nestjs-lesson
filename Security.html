Input validation

sanitize and validate all input

In plain words

Think of your API as a building with a security desk. Everything that comes in (body, query string, URL params, headers, uploaded files) is a stranger until it has been checked. Validation is the guard checking the visitor's badge: "is this the right kind of thing, the right size, in the allowed range?" If not, it's turned away at the door with a 400. Sanitizing is cleaning what you let in: trimming spaces, normalizing an email to lowercase, removing dangerous HTML. Remember from Lesson 1: TypeScript types disappear at runtime, so dto: CreateUserDto alone checks nothing when a real request arrives.

In a real NestJS project

Teams usually combine three layers: (1) a global ValidationPipe with whitelist + forbidNonWhitelisted + transform, (2) DTO classes that use PickType/PartialType so the "update" DTO can never accidentally include admin-only fields, and (3) services that map DTOs to Prisma explicitly instead of spreading them:

Common mistakes
  • Using an interface or any for @Body(). Nothing is validated at runtime.
  • Forgetting whitelist: true, which leaves the door open to mass assignment.
  • Forgetting @Type(() => ItemDto) on nested arrays, so inner objects silently skip validation.
  • Accepting security-relevant values from the client: prices, userId of the owner, roles. Take them from the database or from the authenticated user.
  • No upper bounds: unlimited limit, string length, array size or file size.

Interview questions

What do whitelist and forbidNonWhitelisted do in ValidationPipe?

whitelist removes any property that has no validation decorator in the DTO. forbidNonWhitelisted rejects the request with 400 instead of silently removing them. Together they prevent mass assignment (clients setting fields like role).

What is the difference between validation and sanitization?

Validation checks that input matches the rules and rejects it if not (type, format, length, range). Sanitization transforms accepted input into a safe or normalized form (trim, lowercase, strip disallowed HTML). You usually do both: normalize, then validate.

Why isn't the TypeScript type of @Body() enough?

Types are erased at compile time. At runtime the body is whatever JSON the client sent. Only runtime validation (class-validator via ValidationPipe) actually checks it.

Remember All input is untrusted until validated: use DTO classes, a global ValidationPipe with whitelist and forbidNonWhitelisted, upper bounds on everything, and never take prices, owners or roles from the client.

SQL injection prevention

parameterized queries via Prisma

In plain words

Imagine you dictate a letter to an assistant who types exactly what you say, including instructions. If a stranger's sentence is dropped into the middle of your dictation, the assistant can't tell your instructions from theirs. That is SQL injection: user text is glued into the SQL string, so the database treats part of the user's text as commands. Parameterized queries fix this by sending the SQL command and the values separately: the database always treats the values as data, never as code.

How it works

The good news: normal Prisma queries are safe. findMany, create, update and friends always send values as parameters ($1, $2…). You can see it in the query log from Lesson 9:

The risk appears when you drop down to raw SQL (Lesson 4, "Raw queries") for reports, full-text search or performance.

The vulnerability: building SQL with string concatenation.

The value of term becomes part of the command. A single quote in the input closes the string early, and whatever follows is interpreted as SQL. That can let someone read other tables (users, password hashes), bypass filters, or modify data. Even an innocent input such as O'Brien breaks the query with a syntax error, which is often how this bug is first noticed.

The fix: $queryRaw with a tagged template. Notice there are no parentheses: $queryRaw`...` is a tagged template. Prisma receives the SQL pieces and the ${} values separately and turns each value into a parameter:

MethodSafe?Why
prisma.model.findMany(...) etc.✅Always parameterized
$queryRaw`... ${value}` / $executeRaw`...`✅Tagged template, values become parameters
$queryRawUnsafe('... $1', value)✅ if you only use $1 placeholdersValues passed as separate arguments
$queryRawUnsafe(`... ${value}`)❌Value is part of the SQL text
$queryRaw(Prisma.raw(`... ${value}`))❌Prisma.raw inserts text without escaping

Building dynamic queries safely. Use Prisma.sql to compose fragments, and Prisma.join for lists. Each piece stays parameterized:

Identifiers cannot be parameters. Parameters only work for values. Column names and sort directions (ORDER BY ${column}) cannot be parameters, so people are tempted to concatenate them. Use an allow-list instead:

Prisma's own "operator injection". Even without raw SQL, passing unvalidated objects into where is dangerous. If the query string is parsed into nested objects, a client could send a filter object instead of a string:

That's why input validation (point 1) and injection prevention work together.

In a real NestJS project

Keep raw SQL inside repositories, review every Unsafe call in code review, and add an ESLint rule so it can't sneak in unnoticed:

Defense in depth: the database user in DATABASE_URL for the app should have only the privileges it needs (read/write on the app's tables), not superuser. Then even a successful injection can't drop tables or read other databases. Migrations can run with a separate, more privileged user.

Common mistakes
  • Using $queryRawUnsafe with template literals (`... ${x}`) because "it's the same syntax". It is not: the value becomes SQL text.
  • Calling $queryRaw(...) with parentheses around a pre-built string, which loses the parameterization.
  • Concatenating column names or sort directions from user input instead of using an allow-list.
  • "Escaping" quotes by hand with replace(/'/g, "''"). Escaping is easy to get wrong; parameters are always right.
  • Connecting with a superuser account, so any injection becomes a full database takeover.

Show answer

The best fix is often to not use raw SQL. If the Prisma query API can express it, use it.

Interview questions

What is SQL injection and how do parameterized queries prevent it?

SQL injection happens when user input is concatenated into a SQL string, so part of the input is executed as SQL. Parameterized queries send the SQL text and the values separately; the database parses the command first and treats values purely as data, so they can never change the query's structure.

Is Prisma immune to SQL injection?

The query API (findMany, create…) and tagged-template $queryRaw/$executeRaw are parameterized and safe. $queryRawUnsafe/$executeRawUnsafe with concatenated strings, and Prisma.raw with user input, are vulnerable. Passing unvalidated objects into where can also change a query's meaning.

How do you safely let users choose a sort column?

Identifiers can't be parameters, so validate against an allow-list (e.g. @IsIn([...])) and map each allowed value to a fixed SQL fragment or a Prisma orderBy object. Never insert the raw string.

Remember Never build SQL by concatenating input. Use the Prisma query API or tagged-template $queryRaw, use allow-lists for identifiers, and treat every Unsafe call as a red flag in review.

CORS

configuring allowed origins

In plain words

Browsers follow a rule called the same-origin policy: JavaScript on https://evil.example is not allowed to read responses from https://api.shop.com. Otherwise any website you visit could quietly read your bank data using your logged-in cookies. CORS (Cross-Origin Resource Sharing) is how your API tells the browser "it's OK, I trust these specific websites to read my responses". It's a guest list that the browser enforces at the door. Two key facts: CORS is enforced by browsers only (curl, Postman and servers ignore it), and it is not authentication.

How it works

What is an "origin"? The combination of scheme + host + port. All three must match to be "same origin":

Page originAPI URLSame origin?
https://shop.comhttps://shop.com/api/orders✅ Yes
https://shop.comhttps://api.shop.com/orders❌ No (different host)
http://localhost:5173http://localhost:3000/orders❌ No (different port)
http://shop.comhttps://shop.com/orders❌ No (different scheme)

The request flow. For "non-simple" requests (e.g. PUT/DELETE, JSON bodies, an Authorization header), the browser first sends a preflight OPTIONS request to ask permission:

If the response doesn't allow the origin, the browser blocks the real request (or blocks JavaScript from reading its response) and shows the famous "blocked by CORS policy" error in the console.

Vulnerable configurations.

Why is #1 so bad? If your API uses cookies for auth, a user who is logged in to your shop and visits a malicious site would let that site's JavaScript call GET /me with their cookie and read their personal data. (Browsers refuse * together with credentials for exactly this reason; reflecting the origin bypasses that safety rule.)

The fix: an explicit allow-list from configuration.

A simpler form works too: origin: ['https://shop.com', 'https://admin.shop.com']. The cors package compares strings exactly.

What CORS does NOT do.

  • It doesn't stop anyone from calling your API directly with curl or a script. Only authentication and authorization do that.
  • It doesn't fully protect cookie-based APIs from CSRF (cross-site request forgery). Some "simple" requests (like a form POST) are still sent by the browser; CORS only blocks reading the response. Use SameSite cookies (point 6) and, for cookie sessions, CSRF tokens.
  • If your API uses Authorization: Bearer tokens stored by the frontend (not cookies), the browser doesn't attach credentials automatically, which reduces the CORS risk, but you should still allow-list origins.
In a real NestJS project

Keep origins per environment in config (dev: http://localhost:5173; staging and production: their real domains) and validate them at boot together with other config. Write an e2e test so nobody "temporarily" switches to origin: true:

Note: in tests, call app.enableCors(...) the same way as in main.ts (move the setup into a shared configureApp(app) function), because Test.createTestingModule doesn't run main.ts.

Common mistakes
  • origin: true (reflect any origin) with credentials: true, usually added to "fix" a CORS error quickly.
  • Loose regexes such as /shop\.com/ that match attacker-controlled domains.
  • Thinking CORS protects the API from non-browser clients. It doesn't. Authentication does.
  • Trailing slashes or wrong scheme in the allow-list (https://shop.com/ never matches an Origin header, which has no path).
  • Allowing null as an origin. Sandboxed iframes and local files send Origin: null, and attackers can produce it too.
Practice exercise

Show answer

Browsers refuse to send or expose credentialed requests (cookies) when the server answers Access-Control-Allow-Origin: *. With credentials you must return the exact origin, which is why an explicit list is required.

Interview questions

What is CORS and who enforces it?

A mechanism that lets a server tell browsers which other origins may read its responses, using Access-Control-* headers. It is enforced by the browser, so non-browser clients are not affected.

Why is origin: true with credentials: true dangerous?

It reflects whatever origin asks, so any website can make requests with the user's cookies and read the responses, which exposes the user's private data to every site they visit.

What is a preflight request?

An automatic OPTIONS request the browser sends before a non-simple cross-origin request (custom headers, JSON body, PUT/DELETE…) to check that the server allows that origin, method and headers. Access-Control-Max-Age lets the browser cache the answer.

Remember Allow-list exact origins from config, enable credentials only if you use cookies, and remember CORS is a browser rule, not a substitute for authentication.

Helmet

secure HTTP headers

In plain words

HTTP response headers are little instructions attached to every response that tell the browser how to behave: "only talk to me over HTTPS", "don't guess the file type", "don't show me inside someone else's frame". Browsers have many protections, but most are off unless you ask for them. Helmet is a middleware that adds a sensible set of these security headers in one line, like putting on a helmet before riding: it won't make you invincible, but it prevents a lot of common injuries.

How it works

X-Frame-Options / frame-ancestorsClickjacking: your page loaded invisibly inside another site's frame
Referrer-PolicyLeaking full URLs (which may contain IDs or tokens) to other sites
removes X-Powered-ByGiving away which framework and version you run

For a pure JSON API, the browser doesn't render your responses as pages, so some headers matter less. They cost nothing, though, and they protect anything else the API serves: error pages, Swagger UI, file downloads, uploaded images.

In a real NestJS project

Put security setup in one function used by both main.ts and e2e tests, and assert the headers in a test, so a refactor can't silently remove them:

Common mistakes
  • Registering Helmet after routes or other middleware that already sent the response, so its headers never get added.
  • Disabling CSP for the whole app to fix one page (often Swagger). Scope the change to that path.
  • Believing Helmet "secures the app". It only sets headers; it doesn't validate input, check auth or prevent injection.
  • Setting HSTS with a long max-age and includeSubDomains before every subdomain supports HTTPS. Browsers will refuse HTTP to those subdomains for the whole period.
Practice exercise

Show answer

For full protection against framing in modern browsers, CSP's frame-ancestors 'none' is the newer equivalent; Helmet's default CSP already sets frame-ancestors 'self', which you could tighten too.

Interview questions

What does Helmet do?

It is middleware that sets a collection of security-related HTTP response headers (CSP, HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, and others) and removes X-Powered-By, turning on browser protections that are off by default.

What is Content-Security-Policy for?

It tells the browser which sources of scripts, styles, images, frames, etc. are allowed. Even if an attacker manages to inject HTML, scripts from non-allowed sources or inline scripts won't run, which greatly limits XSS damage.

Does a JSON API need security headers?

Yes, cheaply. nosniff, HSTS and framing protections still matter for error pages, docs, file downloads and any HTML the API returns, and removing X-Powered-By reduces fingerprinting. Defense in depth costs one line.

Remember app.use(helmet()) early in main.ts, keep the defaults, loosen only narrowly (e.g. Swagger path), and test that the headers are present.

Environment secrets

.env management and secret storage

In plain words

Secrets are the keys to your house: the database password, the JWT signing key, the payment provider's API key. You wouldn't engrave your house key's shape on the front door, but putting a secret in your source code is exactly that: everyone who can see the code (teammates, contractors, a leaked laptop, a public GitHub repo by mistake) now has the key. Secrets belong outside the code, are given to the app when it starts, are different in every environment, and can be replaced (rotated) without changing code.

How it works

The vulnerable patterns.

Step 1: .env for local development only, never committed.

Generate strong random secrets instead of inventing them:

Step 2: validate configuration at startup (fail fast). If a secret is missing or obviously wrong, the app should refuse to start, not run with a default. ConfigModule accepts a validate function; here with class-validator, which you already use for DTOs:

Step 3: where production secrets live. In production there is no .env file in the repository or the Docker image. The platform injects environment variables when the container starts, reading them from a secret store:

OptionGood for
Platform env settings (Render, Railway, Fly.io, Heroku)Small projects; encrypted at rest, edited in a dashboard
AWS Secrets Manager / SSM Parameter Store, GCP Secret Manager, Azure Key VaultCloud deployments; access controlled by IAM roles, audit logs, rotation
HashiCorp Vault, Doppler, InfisicalMulti-cloud or many services; central management
Kubernetes Secrets (ideally synced from one of the above)K8s deployments; mounted as env vars or files
CI secrets (GitHub Actions secrets)Values needed only during build/deploy pipelines

Also add a .dockerignore containing .env*, so a COPY . . never pulls local secrets into the image.

Step 4: when a secret leaks, rotate it. If a secret was ever committed, pushed, pasted into a chat or printed in logs, consider it compromised. Deleting the commit is not enough (forks, clones, caches and CI logs keep copies). The response is:

  1. Rotate: generate a new value, deploy it, revoke the old one at the provider.
  2. Check for misuse in the provider's and your own logs.
  3. Clean history if needed, and add prevention: secret scanning (GitHub secret scanning / push protection, or a pre-commit hook such as gitleaks).

Design for rotation from the start: for example, accept JWTs signed with the current key or the previous key for a short overlap period, so rotating the signing key doesn't log everyone out.

In a real NestJS project

Use a different secret per environment (dev, staging, production never share a JWT secret or a database password), give each service only the secrets it needs, and access configuration only through ConfigService (no scattered process.env reads). A typed wrapper keeps it tidy:

Common mistakes
  • Committing .env "just once", or putting real values in .env.example.
  • Fallback defaults like process.env.JWT_SECRET || 'secret' that hide a missing secret in production.
  • Copying .env into Docker images, or printing process.env / the config object at startup "for debugging".
  • Sharing the same secrets across dev, staging and production, so a leak in dev compromises production.
  • Deleting a leaked secret from git instead of rotating it.
Practice exercise

A teammate's PR contains: const stripe = new Stripe(process.env.STRIPE_KEY ?? 'sk_live_51H...', { apiVersion: '2024-06-20' }) inside a service. List everything wrong and write the fixed version.

Show answer

Problems: (1) a live secret key is now in git history, so it must be rotated at Stripe immediately, even if the PR is never merged; (2) the fallback hides a missing env var; (3) process.env is read directly instead of through validated config; (4) the client is created inside a service instead of as a provider, which makes it hard to mock in tests.

Interview questions

How do you manage secrets in a NestJS application?

Secrets come from environment variables, never from code. Locally a git-ignored .env; in production they are injected from a secret manager or the platform. ConfigModule validates them at startup (fail fast, no defaults), and the code reads them only through ConfigService. Use different secrets per environment and plan for rotation.

A secret was committed to the repository. What do you do?

Treat it as compromised: rotate it (create a new one, deploy it, revoke the old one), check logs for misuse, then clean the history if necessary and add secret scanning to prevent it happening again. Removing the commit alone is not enough.

Why validate environment variables at startup?

So a misconfigured deployment fails immediately and visibly, instead of starting with a missing or weak secret, or crashing later on the first request that needs the value.

Remember Secrets never go in code, git or Docker images: inject them at runtime, validate them at boot without fallbacks, keep them different per environment, and rotate anything that leaks.

HTTPS

understand secure API communication

In plain words

Plain HTTP is like sending a postcard: every post office, Wi-Fi router and network provider between the user and your server can read it, and even change it. HTTPS puts the postcard in a locked, tamper-proof envelope, and also checks the ID of the recipient. It gives three guarantees: confidentiality (nobody can read the password or token), integrity (nobody can change the response on the way) and authentication (the client is really talking to api.shop.com, proven by a certificate). For any API that handles logins or personal data, HTTPS is not optional.

How it works

The basics of TLS (the "S" in HTTPS):

  1. The client connects and the server presents its certificate: "I am api.shop.com", signed by a certificate authority (CA) such as Let's Encrypt that the client already trusts.
  2. The client checks the signature, the domain name and the expiry date. If anything is wrong, it refuses to continue.
  3. Both sides agree on a fresh encryption key, and all further traffic, including headers like Authorization and cookies, is encrypted.

Where HTTPS ends in a typical deployment. Usually your NestJS app does not handle certificates itself. A load balancer or reverse proxy "terminates" TLS and forwards plain HTTP to the app over a private network:

This keeps certificate renewal out of your code. But it means the app sees an HTTP request, so it needs to know the original request was secure. The proxy sends X-Forwarded-Proto: https, and you tell Express to trust exactly your proxy (as in Lesson 9's rate limiting):

Never accept credentials over plain HTTP. Redirecting HTTP to HTTPS is fine for websites, but for an API the first request has already sent the token in clear text before the redirect happens. Better: don't serve the API on port 80 at all (or answer with an error), and use HSTS so browsers never even try HTTP:

Helmet sets this header by default (point 4). After the browser sees it once, it rewrites every http:// request to that domain into https:// locally for a year.

Cookies must be secure too. If you store a refresh token in a cookie, these flags matter:

HTTPS for outgoing connections too. The same rule applies when your app is the client: to the database, Redis, and third-party APIs.

HTTPS in local development is usually not needed (cookies with secure: true are allowed on localhost in modern browsers). When you do need it, for example to test something that requires a secure context, create a locally trusted certificate (e.g. with mkcert) and pass it to Nest:

In a real NestJS project

Checklist for a production NestJS API: TLS terminated at the load balancer with automatically renewed certificates; only TLS 1.2+ enabled there; port 80 closed or rejecting API traffic; trust proxy set to the right number of hops; Helmet's HSTS on; cookies httpOnly + secure + sameSite; sslmode=require (or stricter, verify-full with the CA) for the database. Remember that the hop between the load balancer and the app is unencrypted, so keep it on a private network, or enable TLS there too if your security requirements demand end-to-end encryption.

Common mistakes
  • Disabling certificate verification (NODE_TLS_REJECT_UNAUTHORIZED=0, rejectUnauthorized: false) to make an error go away.
  • Relying on an HTTP→HTTPS redirect for API calls. The token has already travelled in clear text.
  • Forgetting trust proxy, so req.secure is false and secure cookies or redirects misbehave.
  • Connecting to a managed database or Redis over the public internet without TLS.
  • Putting tokens or secrets in URLs (?token=...). HTTPS encrypts them on the wire, but URLs end up in proxy logs, browser history and Referer headers.
Practice exercise

Your API is behind an AWS load balancer that terminates TLS. After deploying, the refresh-token cookie with secure: true works, but req.protocol logs http and the rate limiter counts every user under the same IP. What single line is missing, and why does it fix both problems?

Show answer

The app receives connections from the load balancer, so without trusting it Express uses the connection's own protocol (HTTP) and IP (the load balancer's). With trust proxy set to one hop, Express reads X-Forwarded-Proto and X-Forwarded-For as set by that load balancer, so req.protocol becomes https and req.ip is the real client. Trusting exactly one hop (not true) prevents clients from faking those headers.

Interview questions

What does HTTPS protect against?

Eavesdropping (confidentiality), tampering with requests or responses in transit (integrity), and impersonation of the server (authentication via certificates). It does not protect against bugs in your application, such as injection or broken authorization.

What is TLS termination and what must the app do about it?

A load balancer or reverse proxy decrypts HTTPS and forwards plain HTTP to the app. The app must trust that proxy (trust proxy) to learn the original protocol and client IP from X-Forwarded-* headers, and the internal hop should stay on a private network.

What is HSTS?

The Strict-Transport-Security header tells browsers to use only HTTPS for the domain for a set period. It prevents downgrade attacks and accidental HTTP requests after the first visit.

Remember HTTPS everywhere, including to your database and Redis: terminate TLS at the proxy, trust exactly that proxy, enable HSTS, use secure cookies, and never disable certificate verification.

Sensitive logs

never expose tokens, passwords or secrets

In plain words

Logs are copied everywhere: to log servers, to monitoring tools, to backups, into support tickets and screenshots, and many more people can read them than can read your database. Writing a password or a token into a log is like writing your PIN on the back of a receipt and handing out copies. The rule is simple: logs should tell you what happened (who, which action, which record, the result), but never contain the secret things themselves. The same goes for error responses: the client should never see stack traces, SQL or internal details.

How it works

Where secrets leak into logs (each one is common in real projects):

Fix 1: log identifiers and outcomes, not payloads.

Fix 2: redact automatically, as a safety net. Developers will eventually log something they shouldn't. pino's redact option removes or masks known sensitive paths before the line is written:

Redaction paths match exact structures, so they are a safety net, not a replacement for logging carefully. Test them (see the exercise).

Fix 3: never return sensitive data in responses. Leaks also happen in the other direction: an API that returns the full user row sends passwordHash to the browser, where it can end up in browser logs, analytics or a screenshot.

Fix 4: safe error responses. Unhandled errors (for example a Prisma error) can contain SQL fragments, table names and values. Log them on the server, and send the client only a generic message and the request ID:

(Known cases, like the unique email conflict above, should be mapped to a proper 409 Conflict with a friendly message instead.)

Also watch the Prisma query log. In Lesson 9 you logged queries for debugging. Prisma's query event includes params, which contain user data such as emails and password hashes. Keep query logging (especially params) for development only.

In a real NestJS project

Combine the layers: a team rule ("log IDs, not objects"), pino redact as a safety net, select/@Exclude for responses, a global exception filter that hides internals, and short log retention with restricted access. Personal data (emails, addresses, phone numbers) also deserves care because of privacy laws such as GDPR: prefer user IDs in logs. If a secret is ever found in logs, treat it like a leaked secret: rotate it (point 5), and purge the logs if possible.

Common mistakes
  • Logging whole request bodies, DTOs, headers or entities "temporarily" and forgetting to remove it.
  • Logging raw errors from HTTP clients, which contain request headers with API keys.
  • Returning Prisma models directly, exposing passwordHash and internal tokens.
  • Sending stack traces, SQL or Prisma messages to clients in production.
  • Putting tokens in query strings, where every proxy's access log records them.

Interview questions

What should and shouldn't go into application logs?

Should: event names, IDs (user, order, request), outcomes, durations, error codes. Shouldn't: passwords, tokens, API keys, session cookies, card data, full request bodies, and (as far as possible) personal data such as emails and addresses.

How do you prevent secrets from appearing in logs?

Log selected fields instead of whole objects, configure automatic redaction (pino redact) for known sensitive paths, keep query parameter logging to development, avoid secrets in URLs, test the redaction, and review logging in code review.

Why hide error details from API clients?

Stack traces, SQL and ORM messages reveal internal structure (tables, file paths, library versions) and sometimes data, which helps attackers. Clients need a status code, a safe message and a request ID; the details belong in server logs.

Remember Log IDs and outcomes, never secrets or whole objects; redact automatically as a safety net; and return only safe fields and generic error messages to clients.
8

Brute force protection

rate limiting sensitive endpoints

In plain words

A brute-force attack is someone trying every key on a giant key ring until one opens your door: thousands of password guesses against a login form, or every 6-digit code against a verification endpoint. Each attempt is cheap for the attacker. The defence is to make guessing slow and expensive: allow only a few attempts per minute, slow down further after failures, and notice when it happens. A phone that locks for 1 minute after 5 wrong PINs uses exactly this idea.

How it works

Which endpoints are sensitive? Anything that checks a secret or creates something costly:

  • POST /auth/login: password guessing and "credential stuffing" (trying email/password pairs leaked from other sites).
  • POST /auth/verify-otp, 2FA codes: a 6-digit code has only 1,000,000 possibilities.
  • POST /auth/forgot-password, /auth/register: abuse sends floods of emails or checks which emails exist.
  • POST /auth/refresh, coupon/gift-card redemption, anything with a guessable code.

The vulnerable version: unlimited attempts and revealing messages.

With no limit, an automated client can try thousands of passwords per minute. With different messages (and even different response times: the "no user" branch returns instantly because it skips bcrypt), it can first find out which emails have accounts.

Layer 1: strict rate limit on the endpoint with @nestjs/throttler (Lesson 9, point 5), keyed by IP and by the targeted account:

Remember Lesson 9: use Redis storage for the throttler when you run several instances, and configure trust proxy correctly, or the limits are either useless or block everyone.

Layer 2: per-account protection with progressive delays. IP limits alone are weak against distributed attacks (many IPs, one account). Track failures on the account itself and lock it temporarily, with the lock growing after repeated failures:

Failed attempts in a rowEffect
1–4Normal "Invalid email or password"
5Locked 1 minute
6 / 7 / 8Locked 2 / 4 / 8 minutes
11+Locked 60 minutes (cap). Consider emailing the owner

Why temporary and not permanent? A permanent lock lets anyone lock out any user just by typing wrong passwords for their email. That is a denial-of-service against your own customers. Progressive delays make guessing impractical (at most a few dozen guesses per day) while real users recover by themselves.

Layer 3: make the secret itself strong. Rate limits work best together with: a minimum password length (point 1 used 12), blocking very common or breached passwords, short-lived one-time codes (OTP valid 5 minutes, invalidated after 5 wrong tries), and offering 2FA. A CAPTCHA after several failures from the same IP adds friction for bots without bothering normal users.

Layer 4: detect and alert. The warning logs above feed dashboards and alerts: a spike in login_failed events across many accounts usually means a credential-stuffing attempt. Edge protection (WAF, bot management at the CDN) can then block it before it reaches the app.

In a real NestJS project

Put it all in the auth module: LoginThrottlerGuard on login, OTP and reset endpoints; Redis-backed throttler storage; the lockout logic in AuthService; one generic error message; forgot-password always answering 202. Then write e2e tests for the security behaviour, not only the happy path:

Common mistakes
  • Relying only on the global rate limit (e.g. 200/min), which still allows thousands of password guesses per hour.
  • Limiting only by IP. Distributed attacks use many IPs against one account; add per-account limits.
  • Permanent lockouts, which let anyone lock real users out of their accounts.
  • Different error messages or response times for "unknown email" and "wrong password" (user enumeration).
  • Forgetting the less obvious endpoints: OTP verification, password reset, refresh, coupon codes.

Show answer

With 5 attempts per code and a 5-minute expiry, an attacker has a 5 in 1,000,000 chance per code, instead of being able to try all of them.

Interview questions

How would you protect a login endpoint against brute force?

A strict rate limit on the endpoint by IP and by account (shared storage like Redis), progressive temporary lockouts after repeated failures, identical error messages and similar timing for unknown users and wrong passwords, strong password rules and 2FA, CAPTCHA after several failures, and monitoring/alerts on failure spikes.

What is credential stuffing and why is IP-based limiting not enough?

Attackers try email/password pairs leaked from other sites, spread over many IP addresses and many accounts. Each IP stays under the limit, so you also need per-account limits, breached-password checks, 2FA and anomaly detection.

Why not lock an account permanently after 5 failures?

Because anyone who knows a user's email could lock them out on purpose (denial of service). Temporary, progressively longer locks stop guessing while letting legitimate users recover automatically.

Remember Make guessing slow and expensive: strict per-IP and per-account limits on every secret-checking endpoint, temporary progressive lockouts, one generic error message, and alerts when failures spike.
