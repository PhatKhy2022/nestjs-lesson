Prisma schema

datasource, generator and models

In plain words

The Prisma schema (prisma/schema.prisma) is the single blueprint of your database. You describe your tables once, in a short readable language, and Prisma uses that blueprint for two jobs: it creates SQL migrations that build the real tables in PostgreSQL, and it generates a TypeScript client whose types match those tables exactly. Change the blueprint, and both the database and your types follow. The file has three kinds of blocks: where the database is (datasource), what code to generate (generator), and which tables exist (model).

  • Creating new PrismaClient() in several services. Each one opens its own pool and you run out of connections. Use one injected PrismaService.
  • Forgetting @@map/@map and ending up with quoted PascalCase tables ("OrderItem") that are painful to query by hand. Decide on naming before the first migration.
  • Editing the schema and forgetting to run prisma generate (or a migration), so your types are out of date.

Interview questions

What are the three main blocks of a Prisma schema?

datasource (database provider and connection URL), generator (what to generate, usually the Prisma Client), and model (one per table, with fields, types and attributes). There are also enum blocks and, as a preview feature, view blocks.

What's the difference between @ and @@ attributes?

@ attributes apply to a single field (@id, @unique, @default, @map). @@ attributes apply to the model as a whole and usually involve several fields (@@id([a, b]), @@unique, @@index, @@map).

How do you integrate Prisma into NestJS?

Create a PrismaService that extends PrismaClient, connects in onModuleInit and disconnects in onModuleDestroy; provide and export it from a (usually global) PrismaModule; inject it into services or repositories via the constructor.

Remember schema.prisma is the single source of truth: datasource = where, generator = what to build, models = tables. Map names to snake_case early, and use one injected PrismaService.

Field types

scalars, optional fields, default values

In plain words

Each field in a model has a type that does double duty: it decides the PostgreSQL column type and the TypeScript type you get back. String becomes text in the database and string in your code. A question mark means "this may be empty" (NULL in SQL, null in TypeScript). A default value is what the database fills in when you don't provide one.

Common mistakes
  • Using Float for money. Use Decimal @db.Decimal(p, s).
  • Making every field optional "to be flexible". You then handle null everywhere. Required by default, optional on purpose.
  • Using DateTime without @db.Timestamptz: the column is timestamp without time zone, which is easy to misread across time zones (Prisma writes UTC).
  • Returning BigInt from an endpoint: JSON.stringify throws "Do not know how to serialize a BigInt".
  • Expecting @default(uuid()) or @updatedAt to work for rows inserted with raw SQL.

Interview questions

How should you store money with Prisma and PostgreSQL?

As Decimal with a native type like @db.Decimal(10, 2). In code it's a Prisma.Decimal; use its methods (mul, plus) for math and send it as a string in JSON. Alternatively, store integer cents in an Int/BigInt.

What's the difference between @default(uuid()) and @default(dbgenerated("gen_random_uuid()"))?

The first is generated by Prisma Client in Node, so it only applies to inserts made through Prisma. The second is a database default, so it applies to every insert, including raw SQL and other tools.

What does @updatedAt do?

Prisma Client automatically sets the field to the current time on every update made through Prisma. It isn't a database trigger, so updates made outside Prisma don't change it.

Remember The Prisma type decides both the column and the TypeScript type. Use Decimal for money, Timestamptz for time, ? only when "missing" is meaningful, and know who generates each default.

Migrations

prisma migrate dev and migrate deploy

In plain words

A migration is a numbered, saved SQL script that moves the database from one version of the schema to the next, like a git commit for your database structure. migrate dev is what you run while developing: it compares your schema to the database, writes the next SQL file, and applies it. migrate deploy is what your server/CI runs: it only applies the SQL files that were already written and reviewed, never inventing new ones.

How it works

Your first migration. With the User and Product models from point 1:

What migrate dev did, step by step:

  1. Replayed the existing migrations on a temporary shadow database to find the current state, and checked for drift (manual changes to your dev DB).
  2. Compared that state to schema.prisma and wrote the difference as a new migration.sql.
  3. Applied it to your dev database and recorded it in the _prisma_migrations table.
  4. Ran prisma generate so your TypeScript types match (Prisma 5/6).

Commit the prisma/migrations folder to git. It is the history of your database.

The next change. Add a field and run it again:

Editing the SQL before applying it (--create-only). Prisma generates good SQL, but sometimes you must adjust it: add a CHECK constraint or partial index (not expressible in the schema), or fix a rename. Prisma can't tell a rename from "drop one column, add another":

Always read every generated migration before committing it. Prisma also warns you in the terminal when a migration may lose data.

Adding a required column to a table that has data. ALTER TABLE users ADD COLUMN country text NOT NULL fails if rows exist (they'd have NULL). Options: give it a @default("VN"); or do it in steps: add it as optional, backfill with an UPDATE, then make it required in a second migration. This "expand, migrate, contract" approach is also how you change columns without downtime.

In a real NestJS project

The usual workflow: change schema.prisma → npm run db:migrate -- --name xyz → review the SQL → commit schema and migration together in the same PR. In deployment, run migrate deploy once, before the new app version starts:

If you run several app instances, don't let each one run migrations at boot at the same time. Use one CI step or one release job.

Common mistakes
  • Running migrate dev against production. It can propose a reset, which deletes all data. Production uses migrate deploy only.
  • Editing a migration that has already been applied somewhere. Its checksum changes and Prisma reports it as modified. Create a new migration instead.
  • Committing schema.prisma without the migration folder (or the other way round).
  • Accepting a generated "DROP + ADD" for what was meant to be a rename.
  • Using db push in a team project, so there is no migration history for others or for production.

Interview questions

What is the difference between prisma migrate dev and prisma migrate deploy?

migrate dev is for development: it uses a shadow database to detect changes and drift, generates new migration files, applies them, regenerates the client, and may reset the DB. migrate deploy is for production/CI: it only applies pending, committed migrations, and never generates or resets anything.

How do you rename a column without losing data in Prisma?

Change the schema, create the migration with --create-only, replace the generated DROP/ADD with ALTER TABLE … RENAME COLUMN …, then apply it. Alternatively keep the column name and only change the Prisma field name using @map.

When would you use prisma db push?

For quick prototyping or throwaway databases, when you don't need migration history. For any shared or production database, use migrations.

Remember migrate dev writes and applies migrations on your machine; migrate deploy only applies committed ones in production. Read every generated SQL file, and never edit one that's already applied.

Relations

one-to-one, one-to-many, many-to-many

In plain words

In SQL (Lesson 3), relationships are foreign key columns. In Prisma you describe them from both ends, so that you can walk them in code: user.orders and order.user. Only one end really stores something in the database (the foreign key). The other end is a "virtual" field that tells Prisma "you can follow this link backwards". A simple way to remember it: the model with @relation(fields: […]) is the one carrying the label with the other's id.

How it works

One-to-many: a user has many orders.

Read ③ as: "the user of this order is found by matching my userId to User.id". Field ① has no column; it exists so you can write include: { orders: true }. If you forget one side, npx prisma format adds it for you.

One-to-one: a user has at most one profile. It looks like one-to-many, but the FK is @unique and the back-relation is optional (Profile?), not a list:

Put the FK on the side that is "less important" or created later: a profile can't exist without a user, but a user can exist without a profile.

Many-to-many, implicit: products and categories. When the link has no extra data, just put a list on both sides. Prisma creates and manages a hidden join table (_CategoryToProduct with columns A and B):

Many-to-many, explicit: orders and products. The link carries data (quantity, unit price), so you model the join table yourself, exactly like order_items in Lesson 3. It's two one-to-many relations meeting in the middle:

Implicit m-nExplicit m-n
Join tablehidden, managed by Prismaa normal model you write
Extra columns (quantity, role, addedAt)not possibleyes
Query styleproduct.categories directlyorder.items[i].product (one extra level)
Use whena pure tag-like linkthe link itself has data, or may get some later

Many teams always use explicit join tables, because "the link never needs data" often turns out to be wrong later, and converting an implicit relation needs a data migration.

Referential actions (onDelete, onUpdate) map directly to the SQL ON DELETE options from Lesson 3: Cascade, Restrict, NoAction, SetNull, SetDefault. If you don't set one, Prisma uses Restrict for required relations and SetNull for optional ones. Choose on purpose: deleting an order should cascade to its items; deleting a user who has orders should be refused.

Common mistakes
  • Forgetting @unique on the FK of a one-to-one, which silently makes it one-to-many.
  • Not adding @@index on FK scalar fields. Prisma doesn't add them for PostgreSQL.
  • Using an implicit many-to-many and later needing a "quantity" or "createdAt" on the link.
  • Leaving the default onDelete without thinking, then hitting "Foreign key constraint failed" (P2003) when deleting, or the opposite: an unexpected cascade.
  • Two relations between the same models (e.g. author and reviewer) without naming them: Prisma requires @relation("AuthoredPosts") names to tell them apart.

Interview questions

What's the difference between a relation field and a relation scalar field?

The relation scalar field (userId) is a real column holding the foreign key. The relation field (user or orders) has no column; it lets Prisma Client navigate the relation in queries and nested writes.

Implicit vs explicit many-to-many in Prisma?

Implicit: lists on both models, Prisma manages a hidden join table, no extra fields. Explicit: you write the join model with two relations and can add fields like quantity or timestamps. Use explicit whenever the link carries data.

How do you model a one-to-one relation?

Put the foreign key on one side and mark it @unique; the other side has an optional relation field (Profile?).

Remember The side with @relation(fields, references) stores the FK. 1:1 = FK + @unique, 1:N = FK + list on the other side, M:N = join model (explicit when the link has data). Index FKs and choose onDelete on purpose.

Prisma Client

generated types and end-to-end type safety

In plain words

Prisma Client is code that Prisma writes for you by reading your schema. For every model you get a set of methods (prisma.user.findMany, prisma.order.create…) and a set of TypeScript types that match your tables exactly. It's like a custom-made remote control for your database: it only has buttons for things that really exist, so pressing a button that doesn't exist (a misspelled field) is impossible. "End-to-end type safety" means a change in the database schema shows up as red lines in every piece of code it affects.

How it works

Generating. npx prisma generate reads schema.prisma and writes the client (with the classic generator, into node_modules/.prisma/client, re-exported by @prisma/client). migrate dev runs it for you; in CI, add "postinstall": "prisma generate" so a fresh npm ci always has up-to-date types.

Common mistakes
  • Forgetting to run prisma generate after pulling a schema change, then seeing confusing "property does not exist" errors (or none, with stale types).
  • Using any or hand-written interfaces for query results instead of the generated/derived types.

Interview questions

What does "end-to-end type safety" mean with Prisma?

The schema is the source of truth; Prisma generates TypeScript types from it, and query results are typed according to select/include. Any schema change that breaks code shows up as compile errors, from the database layer through services to anything that consumes those types.

When does the Prisma Client need to be regenerated?

Whenever schema.prisma changes: migrate dev does it automatically (Prisma 5/6), otherwise run prisma generate. In CI and Docker builds, run it after installing dependencies (e.g. with a postinstall script).

Should you use Prisma's generated types as your API DTOs?

Generally no. Generated types disappear at runtime, so they can't be validated by ValidationPipe, and they mirror the database rather than the API contract. Use class-based DTOs for input and explicit select/response types for output.

Remember Prisma Client is generated from your schema, and its return types follow your select/include. Regenerate after every schema change, derive reusable types with GetPayload, and keep API DTOs separate.

Queries

findMany, findUnique, include, select

In plain words

Interview questions

What's the difference between findUnique and findFirst?

findUnique only accepts unique identifiers (id, @unique fields, compound uniques) and is guaranteed to match at most one row. findFirst accepts any filter and returns the first match according to orderBy.

What's the difference between select and include?

include returns all scalar fields of the model plus the listed relations. select returns only the listed fields (scalars or relations). They can't be used at the same level, but can be nested inside each other.

What is the N+1 query problem and how do you avoid it with Prisma?

Loading N parent rows and then running one extra query per row for related data, giving N+1 round-trips. Avoid it with include/nested select (Prisma loads relations in bulk) or by collecting ids and using one where: { id: { in: ids } } query.

Remember findUnique for unique keys (handle null), findFirst with orderBy, findMany for lists. select what you need, include relations deliberately, and never query in a loop.

Filtering & pagination

where, skip, take, cursor

In plain words

Filtering (where) is the search form: "status is PAID, total above 50, customer's email ends with @shop.dev". Pagination is splitting a long result into pages so you don't send 100,000 rows at once. There are two styles. Offset pagination is like a book's page numbers: "skip 40, take 20". Cursor pagination is like a bookmark: "give me the 20 items after this one", which stays fast and correct even when the list is huge or changing.

How it works

Offset pagination (skip + take). Simple and supports "jump to page 7". Return the total so the UI can show page numbers:

Downside (from Lesson 3): skip: 100000 still makes Postgres read and discard 100,000 rows, and inserts between requests shift items so users see duplicates or miss rows.

Cursor pagination (cursor + skip: 1 + take). The client sends back the id of the last item it received; you continue from there. It uses the index directly, so page 5,000 is as fast as page 1:

Common mistakes
  • Passing an accidentally undefined value into where of an updateMany/deleteMany. The condition vanishes and every row is affected.
  • Paginating without a deterministic orderBy (include a unique column like id).
  • No upper limit on take, so a client can request the whole table.
  • Forgetting skip: 1 with a cursor, which repeats the last item of the previous page.
  • Using contains on a big table and expecting it to be fast. LIKE '%x%' can't use a B-tree index (consider full-text search or pg_trgm).

Interview questions

Offset vs cursor pagination: when do you use each?

Offset (skip/take) when users need page numbers and the data set is moderate, like admin tables. Cursor when the data is large or changes often (feeds, infinite scroll, public APIs): it's constant-time and doesn't skip or duplicate rows when data changes.

What's the difference between undefined and null in a Prisma where?

undefined removes the condition (as if not written); null filters for IS NULL. That's convenient for optional filters but dangerous for bulk updates/deletes if a value is unexpectedly undefined.

How do you find users who have no orders with Prisma?

With a relation filter: prisma.user.findMany({ where: { orders: { none: {} } } }).

Remember Build filters as objects (undefined = skip, null = IS NULL), always sort with a unique tie-breaker, cap take, and prefer cursor pagination for large or fast-changing lists.

Mutations

create, update, upsert, delete

In plain words

Mutations are the methods that change data. create adds a row, update changes one, upsert means "update it if it exists, otherwise create it", and delete removes one. Each has a "many" version for bulk work. They also understand relations, so you can create an order together with its items in one call, and Prisma makes sure it's all-or-nothing.

How it works

create returns the new row (including generated id and defaults):

There are two equivalent styles for setting a relation: the checked style (user: { connect: { id: 2 } }) and the unchecked style (just the FK: userId: 2). You can't mix both for the same relation in one call. The unchecked style is shorter; the checked style lets you use connectOrCreate and nested create on that relation.

Interview questions

What's the difference between update and updateMany?

update targets one record by a unique field, returns it, and throws P2025 if not found. updateMany takes any filter, returns { count }, never throws for zero matches, and can't return the rows or do nested writes.

How do you safely decrement stock with Prisma under concurrency?

Use an atomic operation in a conditional update: updateMany({ where: { id, stock: { gte: qty } }, data: { stock: { decrement: qty } } }), then check count. The check and the write happen in one SQL statement.

What is connect in a nested write?

It links the new or updated record to an existing related record by its unique field, setting the foreign key. create makes a new related record; connectOrCreate does whichever is needed; disconnect/set remove or replace links.

Remember create/update/delete work on one row (and throw when it's missing), the *Many versions return a count. Use nested writes for related data, atomic operators for counters, and never pass raw input as data.

Transactions

$transaction and interactive transactions

In plain words

You learned in Lesson 3 that a transaction is an "all or nothing" package of database changes. Prisma gives you three ways to make one. Nested writes are automatically one package. Batch transactions ($transaction([a, b, c])) are a shopping list handed over at once: all succeed or none. Interactive transactions ($transaction(async (tx) => …)) are a conversation: you can read, decide with normal code, then write, and any thrown error cancels everything.

How it works

1. Nested writes are already transactional. Creating an order with items: { create: […] } (point 8) is one transaction. If any item fails (e.g. a bad product id), the order isn't created either. Prefer this when it fits.

2. Batch (sequential) transactions: pass an array of Prisma queries. They run in order inside one transaction:

Limitation: the queries are built before any of them runs, so a later query can't use the result of an earlier one, and you can't put if logic in between. Note: don't await the queries inside the array; pass the unexecuted query objects.

3. Interactive transactions: a callback that receives tx, a transaction-bound client. All queries through tx share one connection and one transaction. Returning commits; throwing rolls back.

Options (second argument):

Retrying conflicts. With Serializable (or under deadlocks), Postgres may abort a transaction; Prisma reports P2034 ("Transaction failed due to a write conflict or a deadlock. Please retry"). The right response is to run the whole transaction again:

Optimistic concurrency control is an alternative to locks for "edit forms": add a version Int @default(0) field, and only update if nobody else changed the row since you read it:

NeedUse
Create/update a record with its childrennested write
Several independent writes, all-or-nothing$transaction([...])
Read → decide → write, all-or-nothing$transaction(async (tx) => ...)

In a real NestJS project

When a use case spans several services, pass the transaction client down. Its type is Prisma.TransactionClient:

NestJS exceptions like ConflictException thrown inside the callback both roll back the transaction and become the HTTP response. Some teams use a library such as @nestjs-cls/transactional to avoid passing tx around manually.

Common mistakes
  • Using this.prisma instead of tx inside the callback. That query runs outside the transaction and won't be rolled back.
  • Doing slow work inside the callback (HTTP calls, emails, file uploads). It holds a connection and locks, and hits the 5-second timeout.
  • Catching errors inside the callback and not re-throwing them, so Prisma commits a half-done operation.
  • Awaiting queries inside the array of a batch transaction ($transaction([await a, await b])), which runs them outside the transaction.
  • Using Serializable without retry logic for P2034.

Interview questions

Batch $transaction([...]) vs interactive $transaction(async tx => ...)?

Batch runs a fixed list of independent queries atomically; it's simple and fast, but later queries can't depend on earlier results. Interactive lets you run arbitrary logic between queries using tx; it's more flexible but holds a connection for the duration, so it must be short.

How does a Prisma interactive transaction roll back?

By throwing any error from the callback (or exceeding the timeout). Prisma catches it, sends ROLLBACK, and re-throws the error to the caller. Returning normally commits.

How do you share one transaction across several NestJS services?

Pass the tx (Prisma.TransactionClient) as a parameter to the methods that must participate, or use a CLS-based transactional library that stores the active transaction client in async context.

Remember Nested writes and $transaction([...]) for simple atomic groups, $transaction(async (tx) => …) for read-decide-write. Always use tx inside, keep it short, throw to roll back, and do side effects after commit.

Interview questions

How do you configure and run a seed with Prisma?

Interview questions

What is Prisma Studio and when do you use it?

A browser-based GUI (npx prisma studio, port 5555) to view and edit data through your Prisma models. It's used in development to verify seeds and migrations, debug data issues and prepare manual test scenarios.

Why shouldn't you edit production data with Prisma Studio?

Edits bypass application validation, business logic, side effects and audit trails, there's no fine-grained access control, and mistakes are immediate. Production changes should go through the app, a reviewed script/migration, or a proper admin tool.

Does Prisma Studio enforce database constraints?

Yes. It writes through Prisma to the real database, so NOT NULL, UNIQUE, foreign key and CHECK constraints all apply, and failed saves show the corresponding error.

Remember Prisma Studio (npx prisma studio) is your development window into the data: great for checking seeds, debugging and setting up test cases, but it bypasses your app's rules and doesn't belong anywhere near production.

Raw queries

know when it's safe to drop to raw SQL

In plain words

Prisma's query API covers most everyday needs, but SQL can do much more: window functions, CTEs, special Postgres features. Raw queries let you send your own SQL through Prisma. The danger is SQL injection: if user input is glued into the SQL text, a clever user can change what the query does. The rule is simple: values travel separately from the SQL text, as parameters. Prisma's tagged template $queryRaw`...` does that for you automatically; the Unsafe functions don't.

How it works

The four methods:

MethodForReturnsParameters
$queryRaw`…`SELECT (anything returning rows)array of rows✅ automatic from ${}
$executeRaw`…`INSERT/UPDATE/DELETE/DDLnumber of affected rows✅ automatic from ${}
$queryRawUnsafe(sql, ...values)SQL built as a stringarray of rows⚠️ only if you use $1, $2 yourself
$executeRawUnsafe(sql, ...values)same, for writesnumber⚠️ same

Safe by default: the tagged template. Each ${value} becomes a parameter ($1, $2…), not text:

A real reason to go raw: a report Prisma can't express. Top customers with their rank and share of revenue uses a CTE and a window function:

Notice three details. Column aliases are quoted ("userId") because Postgres lower-cases unquoted names. Counts and window results are cast (::int, ::float8) because Postgres bigint comes back as a JavaScript BigInt and numeric as Decimal. And the generic <TopCustomerRow[]> is a promise you make, not something Prisma checks. If the SQL and the type disagree, TypeScript won't notice.

Other good reasons for raw SQL:

Dynamic SQL, safely. Parameters can only replace values, never identifiers (table/column names) or keywords like ASC. Use Prisma.sql, Prisma.join, Prisma.empty for composition, and a whitelist for identifiers:

Typed SQL. Recent Prisma versions (5.19+, preview feature typedSql) can generate types from .sql files in prisma/sql/, so the result type is checked against the real database instead of being a promise you make. It's worth trying once your project has several raw reports.

When to stay with the Prisma API: simple CRUD, filters, relations and pagination. You keep type safety, automatic mapping (@map names, enums, Decimal), and refactoring support. Go raw for: complex reports (CTEs, window functions, GROUP BY across joins), Postgres-specific features (FOR UPDATE SKIP LOCKED, full-text search, LATERAL), bulk operations, and measured performance problems.

In a real NestJS project

Keep raw SQL in a dedicated place (a repository or "queries" class), type the result rows explicitly, and convert database types before returning JSON:

Pair it with a DTO that validates from/to (@Type(() => Date) @IsDate()), and an e2e test that runs the query against a real database, since the compiler can't check the SQL for you.

Common mistakes
  • String-concatenating user input into $queryRawUnsafe or Prisma.raw. That's SQL injection.
  • Trying to parameterize a column name or sort direction (ORDER BY ${col}). It becomes a value, not an identifier, and silently does nothing useful. Whitelist instead.
  • Returning COUNT(*) results directly: bigint → BigInt → "Do not know how to serialize a BigInt". Cast with ::int.
  • Forgetting that raw SQL uses database names (user_id, order_items), not Prisma model/field names. Also, comparing a Prisma enum column with a parameter needs a cast (${status}::"OrderStatus"), otherwise Postgres reports operator does not exist.
  • Trusting the generic type argument as if it were validated. It isn't; test the query.

Interview questions

How does $queryRaw prevent SQL injection?

It's a tagged template: the interpolated ${} values are not inserted into the SQL string but sent to PostgreSQL as bound parameters ($1, $2), so the database treats them strictly as data, never as SQL code.

When is it reasonable to use raw SQL with Prisma?

For queries the API can't express or expresses inefficiently: complex reporting (CTEs, window functions, grouped joins), Postgres-specific features (row locking with SKIP LOCKED, full-text search, LATERAL), bulk updates and maintenance commands. Keep it isolated, parameterized and tested.

How do you safely build a dynamic ORDER BY in raw SQL?

Identifiers can't be parameters, so map user input through a whitelist of allowed columns and directions, and only then insert the known-safe text with Prisma.raw or Prisma.sql. Never pass raw user input to Prisma.raw.

Remember Use the Prisma API by default and raw SQL when it truly helps. With raw SQL: always the tagged template (or $1 parameters), whitelist identifiers, cast bigint, and type and test the result yourself.
