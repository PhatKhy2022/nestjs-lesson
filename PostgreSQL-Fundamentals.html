Relational model

tables, rows, columns, relationships

In plain words

A relational database is a set of very strict spreadsheets. Each table is one sheet about one kind of thing (users, products, orders). Each row is one thing (one user). Each column is one fact about it (the email), and every value in a column must have the same type. Tables don't copy each other's data. Instead, a row points to a row in another table by storing its id, like writing "customer #1" on an order slip instead of rewriting the customer's whole address. Those pointers are the relationships.

How it works

Why not just store JSON documents? In JavaScript you might keep a user object with an orders array inside it. That's easy at first, but what happens when a product's name changes? You'd have to update it inside every order of every user. The relational model avoids this by storing each fact once and connecting facts with ids. The database then guarantees that the connections are valid (you can't create an order for user #999 if that user doesn't exist).

Common mistakes
  • Storing lists in one column (product_ids = '1,2,3'). You can't join on it, index it properly or enforce that the ids exist. Use a join table.
  • Copying data between tables (the user's email inside every order). When it changes, the copies disagree. Store the id and join.
  • Using float for prices. Use numeric.
  • Expecting rows to come back in insertion order without ORDER BY.
  • Using timestamp without time zone for events. Use timestamptz.

Interview questions

How do you model a many-to-many relationship in a relational database?

With a join (junction) table that holds two foreign keys, one to each side, usually with a composite primary key on the pair. Extra facts about the pair (quantity, role, joined_at) go in the join table too.

Why is a table described as a "set" of rows? What does it mean in practice?

Rows have no built-in order and (with a primary key) no duplicates. In practice: the order of results is undefined unless you use ORDER BY, and you identify rows by key, never by position.

When would you choose a relational database over a document database?

When data is highly connected and consistency matters: orders, payments, users, inventory. Relational databases enforce types, relationships and constraints, and support multi-row transactions and flexible joins. Document stores fit data that is read as one self-contained blob with few cross-links.

Remember One table per kind of thing, one row per thing, one fact per column. Connect tables with ids (foreign keys), never with copied data.

SQL basics

SELECT, WHERE, ORDER BY, LIMIT

In plain words

SQL is how you ask the database questions. You don't tell it how to find the data (no loops). You describe what you want, like ordering at a counter: "the name and price (SELECT) of products (FROM) that cost less than 50 (WHERE), cheapest first (ORDER BY), just the top 3 (LIMIT)". The database works out the fastest way to get it.

How it works

SELECT … FROM. Choose the columns you need. * means "all columns", which is handy while exploring but should be avoided in application code, because you fetch data you don't use and your code breaks silently when columns change.

WHERE filters rows. Only rows where the condition is true are kept. Combine conditions with AND, OR, NOT, and use brackets when you mix them.

In Postgres, NULLs sort last in ascending order and first in descending order. You can control it with NULLS FIRST / NULLS LAST.

LIMIT and OFFSET take a slice of the sorted result. This is how page-based pagination works: page n with size s is LIMIT s OFFSET (n - 1) * s.

Two rules: (1) always use ORDER BY with LIMIT, otherwise "page 2" is random; (2) include a unique column (like id) in the sort so ties can't swap between pages. Large OFFSETs are slow because Postgres still reads and throws away all the skipped rows. Lesson 4 shows cursor pagination, which fixes that.

The order SQL is actually evaluated. You write SELECT first, but the database runs it almost last. This explains many confusing errors:

Each Prisma call is translated into exactly this kind of SQL. Turning on query logging is the best way to learn what your code really does:

The log shows something like SELECT "public"."products"."id", ... WHERE ("price" < $1 AND "stock" > $2) ORDER BY ... LIMIT $3 OFFSET $4. The $1, $2 are parameters: values are sent separately from the SQL text, which is what protects you from SQL injection.

Common mistakes
  • Writing = NULL instead of IS NULL.
  • Using double quotes for strings. In Postgres, "PAID" means a column named PAID. Strings use single quotes: 'PAID'.
  • Paginating without ORDER BY, or ordering by a non-unique column only, so rows repeat or vanish between pages.
  • Mixing AND and OR without brackets: a OR b AND c means a OR (b AND c).
  • Filtering dates with BETWEEN '2026-09-01' AND '2026-09-30', which misses everything after midnight on the 30th. Use >= start AND < next_start.

Interview questions

Why can't you use a column alias from SELECT inside WHERE?

Because of the logical evaluation order: WHERE runs before SELECT, so the alias doesn't exist yet. Repeat the expression, or wrap the query in a subquery/CTE. ORDER BY runs after SELECT, so it can use aliases.

Why is SELECT * discouraged in application code?

It fetches columns you don't need (more I/O and network, possibly sensitive data like password hashes), it can prevent index-only scans, and the result shape changes silently when someone adds or reorders columns.

What's wrong with LIMIT/OFFSET pagination on big tables?

The database must still produce and skip all OFFSET rows, so deep pages get slower and slower. Rows inserted or deleted between requests also shift the pages. Keyset (cursor) pagination, WHERE id < :lastId ORDER BY id DESC LIMIT n, avoids both problems.

Remember Written order is SELECT → FROM → WHERE → ORDER BY → LIMIT, but it runs FROM → WHERE → SELECT → ORDER BY → LIMIT. Use IS NULL for NULLs, and always sort before you paginate.

Joins

INNER, LEFT, RIGHT and FULL joins

In plain words

Because data is split into tables, you need a way to put it back together for a question like "which user placed which order?". A join lines up rows from two tables that match on some condition, usually "this foreign key equals that primary key", and glues them side by side into one wider row. The join type decides what happens to rows that have no partner: drop them (INNER) or keep them with empty (NULL) cells (LEFT, RIGHT, FULL).

How it works

INNER JOIN: keep only rows that have a match on both sides.

Three things to notice. u and o are table aliases (short names). An appears twice, because she matches two orders: a join produces one row per matching pair. And Dung is missing, because he has no orders. JOIN on its own means INNER JOIN.

RIGHT JOIN is a mirror of LEFT JOIN: it keeps every row from the right table. A RIGHT JOIN B is the same as B LEFT JOIN A. Most teams just swap the tables and always write LEFT JOIN, because reading "start from this table, attach that" is easier.

Common mistakes
  • Using INNER JOIN when you need LEFT JOIN, so rows "mysteriously" disappear (users without orders, products never sold).
  • Putting a filter on the right table in WHERE after a LEFT JOIN, which turns it into an INNER JOIN.
  • Forgetting the ON condition (or writing FROM a, b), which produces a cross join: every row times every row.
  • Summing a parent column (orders.total) after joining children (order_items). The parent value is counted once per child.
  • Not using table aliases, then getting column reference "id" is ambiguous.

Interview questions

What is the difference between INNER JOIN and LEFT JOIN?

INNER JOIN returns only pairs that match on both sides. LEFT JOIN returns every row of the left table; where there is no match, the right table's columns are NULL.

How do you find rows in table A that have no related row in table B?

An anti-join: A LEFT JOIN B ON ... WHERE B.key IS NULL, or WHERE NOT EXISTS (SELECT 1 FROM B WHERE B.a_id = A.id). Avoid NOT IN (subquery) if the subquery can return NULL, because then it returns nothing.

Why can a join return more rows than the left table has?

Because a join produces one output row per matching pair. If one user has three orders, that user appears three times. That's expected for 1:N joins, and it's why you must aggregate carefully after joining.

Remember INNER = only matches. LEFT = all of the left, NULLs where no match. Put right-table filters in ON for LEFT JOINs, and watch for row multiplication.

Aggregation

GROUP BY, HAVING, COUNT, SUM

In plain words

Aggregation turns many rows into a few summary numbers, like a cashier counting the day's receipts. COUNT, SUM, AVG, MIN and MAX squash rows into one value. GROUP BY first sorts the receipts into piles (one pile per customer, per product, per day…) and then counts each pile separately. HAVING throws away whole piles you don't care about, after counting.

How it works

Aggregates over the whole table return exactly one row:

order_countrevenueavg_ordersmallestbiggest
4326.0081.5019.50189.00

Aggregates ignore NULL values (except COUNT(*), which counts rows). And on zero rows, SUM returns NULL, not 0. Wrap it in COALESCE(SUM(x), 0) when you need a number.

GROUP BY makes one output row per group. Here: revenue per product, not counting cancelled orders.

nameunits_soldrevenue
Monitor1189.00
Keyboard149.00
Mouse239.00

Order matters: WHERE removed the cancelled order 104 before grouping, so the Keyboard only counts once.

The golden rule of GROUP BY: every column in SELECT must either be in GROUP BY or be inside an aggregate function. Otherwise, which value should Postgres show for the group?

A Postgres convenience: if you group by a table's primary key, you may select any other column of that table (GROUP BY u.id lets you select u.name), because the key determines them.

COUNT(*) vs COUNT(column) matters a lot with LEFT JOIN. COUNT(*) counts rows; COUNT(o.id) counts non-NULL ids:

namewrong_countorder_countspent
An22257.50
Binh1119.50
Chi110

FILTER (WHERE …) is a Postgres feature that applies an aggregate to only some rows of the group. It lets you compute several conditional totals in one pass, for example COUNT(*) FILTER (WHERE status = 'PAID') AS paid, COUNT(*) FILTER (WHERE status = 'PENDING') AS pending.

HAVING vs WHERE. WHERE filters rows before grouping, so it cannot use aggregates. HAVING filters groups after aggregation.

user_idorder_count

Rule of thumb: if the condition can be checked on a single row, put it in WHERE (it's cheaper, since fewer rows reach the grouping step). Use HAVING only for conditions on aggregates.

Other handy aggregates: COUNT(DISTINCT user_id) (unique customers), string_agg(name, ', ') (join strings), array_agg(id), json_agg(...). And grouping by a computed value works too, e.g. revenue per day with GROUP BY date_trunc('day', created_at).

Common mistakes
  • Selecting a column that is neither grouped nor aggregated.
  • Using COUNT(*) after a LEFT JOIN and getting 1 instead of 0 for "no children".
  • Forgetting that SUM of no rows is NULL. Use COALESCE.
  • Putting row conditions in HAVING (works, but slower) or aggregate conditions in WHERE (error).
  • Summing a parent column after joining to children, which double-counts it.

Interview questions

What is the difference between WHERE and HAVING?

WHERE filters individual rows before grouping and can't use aggregate functions. HAVING filters groups after aggregation and is where conditions like COUNT(*) > 1 go.

What's the difference between COUNT(*), COUNT(col) and COUNT(DISTINCT col)?

COUNT(*) counts rows. COUNT(col) counts rows where col is not NULL. COUNT(DISTINCT col) counts the different non-NULL values.

How would you find duplicate emails in a users table?

SELECT lower(email), COUNT(*) FROM users GROUP BY lower(email) HAVING COUNT(*) > 1; Grouping by the lower-cased email also catches duplicates that differ only by letter case.

Remember GROUP BY makes piles, aggregates summarize each pile, WHERE filters rows before, HAVING filters piles after. Every selected column must be grouped or aggregated.

Keys

primary keys, foreign keys, composite keys

In plain words

A primary key is a row's ID card: unique, never empty, and it shouldn't change. A foreign key is a reference to someone else's ID card, like a parcel label that says "deliver to customer #1"; the database refuses labels for customers that don't exist. A composite key is an ID made of two or more columns together, like "seat 12 in row F": neither part alone is unique, but the pair is.

How it works

Primary key (PK) = UNIQUE + NOT NULL, and a table has at most one. Postgres automatically creates a unique index for it, so lookups by id are fast.

GENERATED ALWAYS refuses manual ids (you'd need OVERRIDING SYSTEM VALUE), while GENERATED BY DEFAULT allows them. That's why our orders table uses BY DEFAULT: the seed inserts ids 101–104 by hand.

Surrogate vs natural keys. A natural key is real-world data that happens to be unique (an email, a tax number). A surrogate key is a meaningless generated number or UUID. Prefer surrogate primary keys: emails change, and changing a PK means updating every foreign key that points to it. Keep natural identifiers as UNIQUE columns instead.

ChoiceProsCons

Foreign key (FK): a column whose value must exist as a key in another table (or be NULL, if the column allows it). This is called referential integrity.

The FK also protects the other direction. Try deleting An, who has orders:

Composite keys. In order_items, a row is identified by the pair (order_id, product_id). The composite PK also enforces a business rule: the same product can't appear twice in one order (you increase quantity instead).

Column order inside a composite key matters for its index: (order_id, product_id) makes "all items of order 101" fast, but not "all orders that contain product 1". For that, add a separate index on product_id.

Important: Postgres does not index foreign keys automatically. It indexes primary keys and unique constraints, but not orders.user_id. Common mistakes
  • Using email (or any changeable business value) as the primary key.
  • Forgetting to index foreign key columns, then wondering why joins and deletes are slow.
  • Using ON DELETE CASCADE everywhere. Deleting one user could silently wipe years of orders and invoices.

Interview questions

What's the difference between a primary key and a unique constraint?

Both enforce uniqueness and create a unique index. A PK also implies NOT NULL, there can be only one per table, and it's the row's main identity that foreign keys normally reference. A table can have many UNIQUE constraints, and their columns may be NULL.

Does PostgreSQL create indexes on foreign keys automatically?

No. It indexes PKs and UNIQUE constraints only. You should usually add an index on FK columns yourself, both for joins/filters and to make deletes on the parent table fast.

Integer ids or UUIDs?

Integers are compact and fast but guessable and centrally generated. UUIDs are unguessable and can be created anywhere (good for distributed systems and public URLs) but are bigger; random v4 UUIDs also fragment B-tree indexes, which time-ordered UUIDv7 avoids. Many apps use integer PKs internally and expose a separate UUID or slug publicly.

Remember PK = stable identity (prefer surrogate). FK = guaranteed valid reference (index it, and choose ON DELETE on purpose). Composite key = identity made of a pair.

Indexes

when and why to index a column

In plain words

An index is like the index at the back of a book. Without it, to find every page that mentions "Postgres", you read the whole book (a sequential scan). With it, you look up the word, which is sorted alphabetically, and jump straight to pages 12, 87 and 203. The cost: the index takes space, and every time you add or change a page, the index must be updated too. So you index the things you search by often, not everything.

How it works

Seeing the difference with EXPLAIN. Indexes don't matter with 4 rows, so first generate a realistic amount of data:

"Seq Scan" and "Rows Removed by Filter: 333301" (per worker) mean Postgres read a million rows to return 97. Now add an index and run it again:

From about 49 ms to 0.25 ms: roughly 200 times faster. EXPLAIN shows the plan; EXPLAIN ANALYZE actually runs the query and shows real timings (so be careful running it on UPDATE/DELETE).

How a B-tree index works. The default index type is a B-tree: a sorted, balanced tree of the column's values, each pointing to the row's location. Finding a value takes a few steps even with millions of rows (like a binary search). Because it's sorted, a B-tree helps with =, <, >, BETWEEN, IN, ORDER BY, and LIKE 'abc%' (prefix only, with the right collation or operator class).

When to add an index:

  • Columns you filter by often in WHERE (orders.status, users.email).
  • Foreign keys used in joins (orders.user_id, order_items.product_id).
  • Columns you ORDER BY together with LIMIT (newest orders first).
  • Columns that must be unique: use a UNIQUE constraint, which creates a unique index.

When not to:

  • Small tables (a few thousand rows): a sequential scan is already fast.
  • Columns with very few distinct values, if the query returns a big share of the table (e.g. is_active where 95% are true). Postgres will ignore the index anyway.
  • Columns you never search by. Every index slows down every INSERT, and every UPDATE of that column, and uses disk.

Composite (multi-column) indexes. The column order matters. An index on (user_id, created_at) is sorted by user_id first, then by created_at within each user. It's perfect for "this user's latest orders":

This is the leftmost prefix rule: an index on (A, B, C) helps queries on A, on A + B, and on A + B + C, but not on B or C alone. Put equality columns first and range/sort columns last. Note that this composite index also makes the plain orders_user_id_idx redundant, so you could drop it.

Common mistakes
  • Indexing every column "just in case". Writes get slower, and the planner ignores most of them.
  • Wrong column order in a composite index (range column first, equality column second).
  • Forgetting to index foreign keys.
  • Wrapping an indexed column in a function (WHERE date(created_at) = …) and expecting the index to be used. Rewrite it as a range.
  • Running plain CREATE INDEX on a large production table during traffic. It blocks writes; use CONCURRENTLY.

Interview questions

Why not index every column?

Each index costs disk space and memory, and must be updated on every insert and on updates of indexed columns, which slows writes. The planner also won't use indexes that aren't selective. Index based on real query patterns.

Explain the leftmost prefix rule for composite indexes.

A B-tree on (A, B) is sorted by A, then B. It can be used for conditions on A, or A and B, and for WHERE A = ? ORDER BY B, but not efficiently for conditions on B alone, just like a phone book sorted by last name can't find everyone named "An" quickly.

A query has an index on its column but still does a Seq Scan. Why?

Possible reasons: the query returns a large fraction of the table (a seq scan is cheaper); the column is wrapped in a function or cast; a leading-wildcard LIKE; outdated statistics (run ANALYZE); a type mismatch between the column and the parameter; or the table is simply small.

Remember Index what you filter, join and sort by, especially foreign keys. Put equality columns before range columns, and prove it works with EXPLAIN ANALYZE.

Constraints

NOT NULL, UNIQUE, CHECK, DEFAULT

In plain words

Constraints are rules the database enforces on every single write, no matter who writes: your NestJS app, a script, a colleague in pgAdmin, or a bug. Think of them as a bouncer at the door of each table. NOT NULL says "you must bring this". UNIQUE says "nobody else can have the same one". CHECK says "it must follow this rule". DEFAULT isn't a rule but a helper: "if you didn't bring one, here's the standard one".

How it works

NOT NULL. By default, every column accepts NULL. Mark a column NOT NULL whenever a missing value would be a bug. Most columns should be NOT NULL; nullable should be a conscious decision ("a user may have no phone number").

UNIQUE. No two rows may have the same value (or the same combination of values, for a multi-column UNIQUE). It's enforced by a unique index, so it also makes lookups by that column fast.

Two details trip people up. First, UNIQUE is case-sensitive: An@shop.dev and an@shop.dev are different values. Use a unique index on lower(email) (point 6), or store emails lower-cased. Second, NULLs are considered different from each other, so many rows can have NULL in a UNIQUE column. Since PostgreSQL 15 you can change that with UNIQUE NULLS NOT DISTINCT.

CHECK. Any boolean expression on the row. The row is rejected if it evaluates to false (note: NULL passes, so combine with NOT NULL when needed).

CHECK can only look at the current row. It can't check other rows or other tables ("stock must cover all pending orders"). That's the job of foreign keys, unique constraints, transactions or application logic. For a fixed list of values, Postgres also offers enum types (CREATE TYPE order_status AS ENUM ('PENDING', 'PAID', ...)), which is what Prisma enums become.

DEFAULT. The value used when an INSERT doesn't mention the column:

idstatustotalcreated_at
105PENDING0.002026-10-05 09:15:02.31+00

Common defaults: now() for timestamps, gen_random_uuid() for UUIDs, false for flags, 0 for counters, an initial status for state machines. RETURNING (used above) is a Postgres feature that gives you back the inserted row, including generated ids and defaults, without a second query.

Why put rules in the database if the app already validates? Because the app is not the only writer, and because of race conditions. Two sign-up requests for the same email arrive at the same millisecond: both run findUnique, both see "no user", both insert. Only the UNIQUE constraint can stop the second insert. App validation gives nice error messages; constraints give guarantees. Use both.

Adding a constraint to a big existing table. ALTER TABLE … ADD CONSTRAINT checks every existing row, which can take a while and fails if old data breaks the rule. Postgres lets you split it: ADD CONSTRAINT … NOT VALID (applies to new writes immediately) and later VALIDATE CONSTRAINT (checks old rows without blocking writes).

Interview questions

The app already validates input. Why add database constraints?

Because other writers exist (scripts, admin tools, other services, future code), and because validation in the app can't prevent race conditions: two concurrent requests can both pass a "does it exist?" check. Constraints are enforced atomically by the database on every write.

Can a UNIQUE column contain several NULLs?

Yes, by default in PostgreSQL, because NULL is "unknown" and two unknowns are not considered equal. Since PostgreSQL 15 you can declare UNIQUE NULLS NOT DISTINCT to allow only one NULL.

What can't a CHECK constraint do?

It can only use values of the row being written. It can't query other rows or tables. For cross-row rules, use UNIQUE/exclusion constraints, foreign keys, triggers, or transactional application logic.

Remember Make columns NOT NULL unless missing is meaningful, use UNIQUE for anything that must not repeat, CHECK for simple row rules, DEFAULT for sensible starting values, and map constraint errors to clear HTTP responses.

Transactions

ACID, COMMIT, ROLLBACK

In plain words

A transaction groups several changes into one "all or nothing" package. Think of a bank transfer: taking money from account A and adding it to account B must both happen, or neither. If the power goes out in between, you don't want the money to have vanished. BEGIN opens the package, COMMIT seals and delivers it, and ROLLBACK throws it away as if nothing happened.

How it works

The problem. Placing an order is several statements: create the order, add its items, reduce stock, set the total. If the app crashes after reducing stock but before adding the item, you have stock missing and an empty order. Wrap them in a transaction:

If anything goes wrong, run ROLLBACK; instead and every change since BEGIN is undone. Also, if a statement fails inside a transaction, Postgres refuses any further commands (ERROR: current transaction is aborted, commands ignored until end of transaction block) until you roll back. A half-done transaction can never be committed by accident.

Without BEGIN, Postgres runs in autocommit mode: every single statement is its own tiny transaction. A single UPDATE touching 1,000 rows is still all-or-nothing; you only need BEGIN to group several statements.

In a real NestJS project

Common mistakes
  • Running related writes as separate queries without a transaction ("it never fails locally").
  • Read-then-write without a lock or atomic update, which loses updates under concurrency (overselling, double-spending).
  • Calling external APIs or doing slow work inside a transaction, holding locks for seconds.
  • Using SERIALIZABLE without retry logic for error 40001.
  • Using the global prisma client instead of tx inside $transaction. That query runs outside the transaction.

Interview questions

Explain ACID.

Atomicity: all or nothing. Consistency: constraints hold before and after. Isolation: concurrent transactions don't see each other's uncommitted changes (to a degree set by the isolation level). Durability: committed data survives crashes.

How do you prevent two users from buying the last item at the same time?

Make the check and the write one atomic operation: UPDATE products SET stock = stock - 1 WHERE id = ? AND stock >= 1 and check the affected row count. Alternatives: SELECT … FOR UPDATE inside a transaction, optimistic locking with a version column, or SERIALIZABLE isolation with retries.

What is PostgreSQL's default isolation level, and what does it allow?

READ COMMITTED. It never shows uncommitted data, but two queries in the same transaction can see different data if another transaction commits in between (non-repeatable reads), and read-then-write logic can lose updates unless you lock or use atomic updates.

Remember Group related writes in one transaction, keep it short, and make check-and-update a single atomic statement (or lock the row) whenever concurrent requests can race.

Normalization

1NF, 2NF, 3NF and denormalization trade-offs

In plain words

Normalization is tidying up your tables so that every fact is stored in exactly one place. If a customer's email is written on 500 order rows, changing it means 500 updates, and missing one leaves the data contradicting itself. The "normal forms" (1NF, 2NF, 3NF) are a checklist for finding facts stored in the wrong place. Denormalization is deliberately breaking the rule, copying a fact to make reading faster, and accepting the work of keeping the copies in sync.

How it works

Start from a messy spreadsheet. This is what an export from a quick prototype might look like:

order_idcustomer_emailcustomer_nameproductstotal
101an@shop.devAnKeyboard x1 @49.00, Mouse x1 @19.5068.50
102an@shop.devAnMonitor x1 @189.00189.00
103binh@shop.devBinhMouse x1 @19.5019.50

Problems (called anomalies):

  • Update anomaly: An changes her name, so you must update several rows. Miss one and she has two names.
  • Insert anomaly: you can't record a new product, or a new customer, until someone orders it.
  • Delete anomaly: delete order 103 and you lose the only record that Binh exists.
  • And you can't query "how many mice were sold?" without parsing strings.

First Normal Form (1NF): one value per cell, no repeating groups. The products column holds a list, so split it into one row per order line:

order_idproduct_namecustomer_emailcustomer_namequantityunit_price
101Keyboardan@shop.devAn149.00
101Mousean@shop.devAn119.50
102Monitoran@shop.devAn1189.00
103Mousebinh@shop.devBinh119.50

Now we can query items, but the customer data is repeated even more. The key of this table is the pair (order_id, product_name).

Second Normal Form (2NF): every non-key column depends on the whole key. This only matters for composite keys. Ask, for each column: "do I need both parts of the key to know this?"

  • quantity: needs both (how many Mice in order 101). ✅ stays.
  • customer_email, customer_name: depend only on order_id. ❌ move to an orders table.
  • The product's details (its current price, stock): depend only on the product. ❌ move to a products table with its own id.

Third Normal Form (3NF): no column depends on another non-key column. In orders, customer_name depends on customer_email (the customer), not on the order. That's a transitive dependency: order → customer → name. Move customer facts to users, and keep only user_id in orders:

That's exactly our running schema. The classic summary: every non-key column must depend on "the key, the whole key, and nothing but the key" (1NF, 2NF, 3NF).

Wait, isn't order_items.unit_price a copy of products.price? No, and this is an important design insight. products.price is "what it costs today". order_items.unit_price is "what this customer paid on that day". They are different facts. If you joined to products.price instead, every old order and invoice would change when you raise a price. The same applies to the shipping address on an order: it's a snapshot, not a duplicate of the user's current address.

Denormalization: copying data on purpose. A fully normalized schema sometimes makes common reads expensive. Our orders.total is a real denormalization: it could always be computed with SUM(quantity * unit_price), but storing it makes "list my orders with totals" a single cheap query.

Common mistakes
  • Storing comma-separated lists or JSON arrays of ids instead of a join table (breaks 1NF).
  • Repeating user data (name, email) in orders "for convenience" without treating it as a deliberate snapshot.
  • Over-normalizing: splitting things like first_name into a separate table, or creating lookup tables for values that never change, adding joins with no benefit.
  • Not snapshotting prices on order lines, so historical orders change when the catalog changes.

Interview questions

Explain 1NF, 2NF and 3NF in one sentence each.

1NF: every cell holds a single value and there are no repeating groups. 2NF: 1NF, and no non-key column depends on only part of a composite key. 3NF: 2NF, and no non-key column depends on another non-key column.

When would you denormalize?

When a measured, frequent read is too slow or complex in normalized form, e.g. order totals, counters, or dashboards, and the cost of keeping the copy consistent (in a transaction, trigger, or periodic refresh) is acceptable.

Is storing unit_price on order items a normalization violation?

No. It's a different fact: the historical price paid at purchase time, which must not change when the product's current price changes. It's a snapshot, not a duplicate.

Remember Each fact in one place: "the key, the whole key, and nothing but the key". Snapshot historical values, and denormalize only on purpose, with a clear way to keep the copy correct.

Views

simplify complex or repeated queries

In plain words

A view is a saved query with a name that you can use like a table. It's like a saved filter in your email client: the emails aren't copied anywhere, the filter just runs every time you open it. A materialized view is different: it's like taking a photo of the results. Reading it is instant, but the photo gets old until you take a new one (refresh it).

How it works

A view stores no data. Postgres replaces the view name with its query and optimizes the whole thing together, so your WHERE is pushed into it where possible. A view is never slower than the query it contains, but also not faster. Its value is reuse, readability and a stable interface.

Simple views (one table, no GROUP BY/DISTINCT) are even updatable: UPDATE public_users SET name = 'An N.' WHERE id = 1 updates the users table. Complex views like order_summaries are read-only.

Interview questions

What's the difference between a view and a materialized view?

A view is a stored query that runs every time you select from it, so it's always fresh but not faster. A materialized view stores the query result on disk, so it's fast and indexable, but stale until REFRESH MATERIALIZED VIEW runs.

Why would you use a view at all?

To name and reuse a complex query, to encode a business definition in one place, to give a stable interface while tables change underneath, and to restrict access to certain columns or rows.

How do you refresh a materialized view without blocking readers?

REFRESH MATERIALIZED VIEW CONCURRENTLY name; It requires a unique index on the materialized view and is slower than a normal refresh, but reads can continue during it.

Remember A view is a named query (always fresh, no speed gain). A materialized view is a stored snapshot (fast, needs refreshing). Use them to stop repeating complex SQL.
