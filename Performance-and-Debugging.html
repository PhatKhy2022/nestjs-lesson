Query optimization

avoid N+1 with include/select

In plain words

Imagine you need 100 books from a library. You can walk to the desk, ask for one book, walk back, and repeat that 100 times. Or you can hand the librarian a list once and get all 100 books together. The first way is the N+1 problem: 1 query to get a list, then N more queries (one per item) to get related data. Each trip to the database is small, but 101 trips add up. Query optimization means asking for what you need, in as few trips as possible, and only the columns you need.

How it works

Step 1: make queries visible. You cannot fix what you cannot see. Turn on Prisma's query log in development so every SQL statement is printed with its duration:

Each query only takes ~1ms inside PostgreSQL, but every query also pays a network round trip, a connection checkout and Prisma's own processing. That overhead (often 2–5ms per query) is what makes the endpoint slow. With 1,000 users it becomes 1,001 queries.

Step 3: fix it with include. Tell Prisma about the relation up front. Prisma loads all the related rows in one extra query using WHERE "userId" IN (...):

❌ Loop with await inside1011,001~410ms / ~4s
✅ include22~9ms / ~45ms

Step 4: fetch only what you need with select. include returns every column of both tables. If the screen only shows the email and the order totals, that is wasted data (and possibly leaked data, like passwordHash). select lets you pick columns, including nested ones:

You cannot use include and select at the same level of the same query, but you can nest one inside the other.

Step 5: count and aggregate in the database, not in JavaScript. Another common waste is loading rows only to count or sum them:

Step 6: when you really need a loop, batch it. Sometimes the IDs come from somewhere else (a cache, another service). Collect them and run one IN query instead of one query per ID:

Good to know: Prisma automatically batches several findUnique() calls that happen in the same tick into one query (this is how it avoids N+1 in GraphQL resolvers). That does not apply to findFirst or findMany, and you should not rely on it as your main strategy.

In a real NestJS project

A useful habit is to assert the query count in an e2e test for important list endpoints. If someone later adds a loop that causes N+1, the test fails instead of production slowing down:

Also watch mappers and serializers. N+1 often hides in a mapper that calls a repository for each item (toDto(order) loading order.customer). Load relations in the repository, and keep mappers pure (no database calls).

Common mistakes
  • Using await inside a for loop over database results. That is the classic N+1 shape.
  • Replacing the loop with Promise.all(ids.map(...)) and calling it fixed. It is still N queries, just in parallel, and it can now empty your connection pool in one request.
  • Using include everywhere "just in case". Deep includes load huge amounts of data. Use select for API responses.
  • Returning Prisma models directly, which exposes columns like passwordHash. select fixes performance and security.
  • Optimizing without measuring. Count queries and time the request before and after.

Interview questions

What is the N+1 query problem and how do you detect it?

You run 1 query to load a list, then 1 more query for each item to load related data, so N items cause N+1 queries. You detect it by logging queries (Prisma log: ['query']), counting queries per request, or seeing many identical queries with different parameters in APM tools or pg_stat_statements.

What is the difference between include and select in Prisma?

include returns all scalar fields of the model plus the listed relations. select returns only the listed fields and relations. select is better for API responses because it transfers less data and never leaks columns by accident.

Is Promise.all a fix for N+1?

No. It makes the N queries run in parallel, which may be faster, but the database still does N times the work and the request can hold many pool connections at once. The real fix is one batched query (include, select or where: { id: { in: ids } }).

Remember Log your queries, count them per request, and load related data with include/select or an IN query, never with a query inside a loop.

Indexing strategy

match indexes to real query patterns

In plain words

An index is like the index at the back of a textbook. Without it, to find "transactions" you read every page (a sequential scan). With it, you jump straight to page 212. But an index only helps if it is sorted by the thing you search for: a textbook index sorted by topic is useless if you search by page colour. So you do not add indexes "everywhere". You look at the queries your app actually runs and build indexes that match them.

How it works

  • Sort: it then sorted the 131 matches in memory.
  • actual time=...96.1 and Execution Time: 96.142 ms: the real cost. cost= numbers are the planner's estimates, in arbitrary units.

Design the index to match the query. The rule of thumb for a composite (multi-column) B-tree index: equality columns first, then the sort / range column. Here: userId and status (equality), then createdAt (sort).

Output after:

96ms → 0.08ms, more than 1000× faster. Notice the Sort step disappeared: the index is already sorted by createdAt DESC, so PostgreSQL reads the first 20 entries and stops.

Column order matters (the "leftmost prefix" rule). A B-tree index on (userId, status, createdAt) is sorted first by userId, then by status inside each user, and so on, like a phone book sorted by last name, then first name.

Query filterCan it use (userId, status, createdAt)?
WHERE userId = 42✅ Yes, leftmost column
WHERE userId = 42 AND status = 'PAID'✅ Yes
WHERE userId = 42 ORDER BY createdAt DESC⚠️ Partly: finds the user fast, but must sort (status sits in between)
WHERE status = 'PAID'❌ Usually not: skips the first column
WHERE createdAt > now() - interval '1 day'❌ No

Foreign keys are not indexed automatically in PostgreSQL. Prisma creates the foreign key constraint, but PostgreSQL does not add an index on Order.userId for you. Every include: { orders: true } filters on that column, so add @@index([userId]) (or a composite index that starts with it) on almost every relation field.

On a big production table, use CREATE INDEX CONCURRENTLY so writes are not blocked while it builds (it cannot run inside a transaction, so put it in its own migration).

Common mistakes
  • Indexing every column "to be safe". Writes get slower and most indexes are never used.
  • Creating single-column indexes on userId and createdAt separately and expecting them to serve WHERE userId ORDER BY createdAt as well as one composite index.
  • Wrong column order in a composite index (range/sort column first, equality columns after).
  • Testing EXPLAIN on a tiny dev table. With 50 rows PostgreSQL correctly prefers a Seq Scan, so you learn nothing.
  • Wrapping the column in a function (WHERE lower(email) = ..., Prisma's mode: 'insensitive') and expecting a plain index on email to be used. You need an expression index.

Interview questions

How do you decide which indexes to create?

From real query patterns: the WHERE, JOIN and ORDER BY columns of frequent or slow queries (found with query logs or pg_stat_statements). Put equality columns first and the sort/range column last, check the plan with EXPLAIN ANALYZE, and remove indexes that are never used.

Why might PostgreSQL ignore an index that exists?

The table is small, so a sequential scan is cheaper. Or the query matches a large fraction of the rows. Or the query does not use the leftmost column. Or the column is wrapped in a function or cast. Or the statistics are out of date (run ANALYZE).

What is the cost of an index?

Slower writes (every insert/update/delete must update each index), extra disk and memory, and longer vacuum and backups. That is why you index for real queries, not for every column.

Remember Indexes serve queries: read the plan with EXPLAIN ANALYZE, build composite indexes as "equality columns, then sort column", and always index your foreign keys.

Connection pooling

understand Prisma connection limits

In plain words

Opening a database connection is like opening a phone line to PostgreSQL: it takes time (TCP, TLS, authentication) and every open line costs PostgreSQL memory (one process per connection). So instead of opening a new line for every query, Prisma keeps a small set of open lines ready: the connection pool. A query borrows a connection, uses it, and gives it back. If all connections are busy, the next query waits in line. Most "the API is randomly slow under load" problems are really "requests are waiting for a free connection".

In a real NestJS project

Configure the pool per environment and make it visible. A small health check that reports pool usage is very helpful during incidents. Load test before you change the pool. Example with 4 CPUs (default limit 9) and an endpoint holding each connection ~40ms: about 9 / 0.04 = 225 requests per second before requests start queuing. If you need more, first make the query faster (an index often turns 40ms into 2ms, i.e. 20× the capacity), and only then raise the limit within PostgreSQL's budget.

Common mistakes
  • Calling new PrismaClient() in many places, or on every request. Use one shared PrismaService.
  • Raising connection_limit to 100 on every pod and hitting PostgreSQL's max_connections.
  • Making HTTP calls, sending emails or waiting on queues inside $transaction.
  • Using Promise.all over thousands of items, which floods the pool. Use set-based queries or process in chunks.
  • Using PgBouncer in transaction mode without pgbouncer=true and without a directUrl for migrations.

Interview questions

What is a connection pool and why do we need one?

A set of database connections that are opened once and reused. Opening connections is slow (TCP, TLS, auth) and each one costs PostgreSQL memory and a process, so reusing a limited number keeps latency low and protects the database.

What does Prisma error P2024 mean and how would you investigate it?

A query waited longer than pool_timeout for a free connection. Check what holds connections: long or slow queries, transactions containing external calls, unbounded Promise.all, too many PrismaClient instances. Only after that, consider tuning connection_limit within the database's max_connections budget.

When would you add PgBouncer?

When many processes (lots of pods, serverless functions) need connections and their total pool sizes would exceed what PostgreSQL can handle. PgBouncer multiplexes many client connections over a few server connections.

Remember Total connections = instances × pool size. Keep one PrismaClient per process, keep transactions short, and fix slow queries before making the pool bigger.

Caching

Redis for hot or expensive data

In plain words

A cache is a sticky note on your desk. If people keep asking "what's today's exchange rate?", you look it up once, write it on a sticky note, and read the note for the next hour instead of calling the bank every time. Redis is a very fast in-memory store that all your app instances can share, like a sticky note on the office wall. The hard part is not storing the note. It is knowing when the note is out of date and throwing it away.

How it works

What is worth caching? Data that is read often, changes rarely, and is expensive to compute. Measure first: cache what actually shows up as hot or slow.

Good candidates ✅Bad candidates ❌
Product catalogue, category treeAccount balance, stock count at checkout
Dashboard stats computed from millions of rowsData that must be correct the instant it changes
Third-party API responses (exchange rates, geo lookups)Per-user data read once
Feature flags, settingsAnything that is already a fast primary-key lookup (often)

The cache-aside pattern (also called "lazy loading") is the one you will use 90% of the time:

  1. Look in the cache.
  2. Hit: return the cached value.
  3. Miss: load from the database, store it in the cache with a TTL (time to live), return it.
  4. When the data changes: delete the cache key (invalidate).

Notice the details: the key has a prefix and a version (v1) so you can change the cached shape later without reading old data; the value is a DTO (not a raw Prisma model, whose Decimal and Date fields don't survive JSON.stringify unchanged); and the TTL is a safety net in case an invalidation is ever missed.

Before/after numbers (product details endpoint, local load test, 50 concurrent users):

No cacheRedis cache-aside (95% hit rate)
p50 latency38 ms3 ms
p95 latency180 ms9 ms
DB queries / second~1,300~65 (only the misses)

Track your hit rate (hits ÷ total lookups). A cache with a 20% hit rate adds a network hop to 80% of requests and may make things slower.

Cache stampede. When a popular key expires, hundreds of requests miss at the same moment and all hit the database together. Simple protections:

Using Nest's built-in cache module. @nestjs/cache-manager gives you an injectable cache and a CacheInterceptor that caches whole GET responses. In current versions (cache-manager v6+, built on Keyv), TTLs are in milliseconds:

Be careful: CacheInterceptor keys by URL. Never put it on endpoints whose response depends on the logged-in user (/me, /orders), or user A may receive user B's data.

In a real NestJS project

Keep caching out of controllers and inside the service or repository layer, behind a small helper, so the rest of the code doesn't care whether data came from Redis or PostgreSQL. Make the cache optional: if Redis is down, log a warning and read from the database instead of failing the request.

Common mistakes
  • Caching before measuring. Caching a 2ms primary-key lookup adds complexity for no gain; fix slow queries with indexes first.
  • Forgetting to invalidate on update/delete, so users see stale prices for the whole TTL. Or no TTL at all, so stale data lives forever.
  • Caching per-user responses under a shared key (e.g. CacheInterceptor on /me). This is a data leak.
  • Using the in-memory store with several app instances: each pod has a different cache and invalidation only reaches one of them. Use Redis.
  • Mixing up units: @nestjs/cache-manager v5+ uses milliseconds, Redis EX uses seconds.

Interview questions

Explain the cache-aside pattern.

The application reads from the cache first. On a miss it loads from the database, writes the value into the cache with a TTL, and returns it. On writes, it updates the database and then deletes the cache key, so the next read reloads fresh data.

What is a cache stampede and how do you prevent it?

When a hot key expires, many concurrent requests miss and all hit the database at once. You prevent it with TTL jitter, request coalescing (one loader per key), a short lock in Redis, or refreshing the value in the background before it expires.

Why delete the key on update instead of writing the new value into the cache?

Deleting is simpler and safer under concurrency. Two concurrent updates could write their cache values in the opposite order from their database writes, leaving the cache with old data. After a delete, the next read always loads the current database state.

Remember Cache data that is hot, expensive and allowed to be slightly stale; always set a TTL, invalidate on writes, and measure the hit rate.

Rate limiting

@nestjs/throttler

In plain words

A rate limit is the "maximum 6 items per customer" sign at a shop counter. It doesn't stop normal customers, but it stops one person from emptying the shelves so nobody else gets served. In an API, rate limiting says "each client may make at most N requests per time window". Above that, the server answers 429 Too Many Requests quickly and cheaply instead of letting one noisy client (a buggy script, a retry loop, a scraper) slow down everyone else.

How it works

Install and register. @nestjs/throttler counts requests per client in a time window. Since v5, ttl is in milliseconds, and you can define several named limits at once:

Every request is now checked against both limits. The guard adds headers so well-behaved clients can slow down by themselves, and returns 429 with Retry-After when a limit is exceeded:

(Headers carry the throttler name as a suffix when you use named throttlers; with a single unnamed throttler they are just X-RateLimit-Limit, Retry-After, etc.)

Per-route overrides. Expensive or sensitive endpoints get stricter limits; health checks and webhooks skip throttling:

Who is "the client"? By default the throttler tracks by IP address (req.ip). Two traps:

  • Behind a proxy or load balancer, every request appears to come from the proxy's IP, so all users share one counter. Tell Express to trust the proxy so req.ip is the real client IP taken from X-Forwarded-For.
  • For logged-in users, tracking by user ID is fairer: an office of 200 people behind one IP should not share a limit.

Note that guards run in the order they are registered. For req.user to exist, your auth guard must run before this one, so apply UserThrottlerGuard after the JWT guard (for example with @UseGuards(JwtAuthGuard, UserThrottlerGuard)), or register the JWT guard first in the APP_GUARD list.

Storage: memory vs Redis. The default storage is an in-memory map inside each Node process. With 4 pods, a client effectively gets 4× the limit, because each pod counts separately (and counters reset when a pod restarts). In production with more than one instance, use shared storage:

SetupReal limit for one client with 4 pods
In-memory storage, limit 200/minup to 800/min (depends on load balancing)
Redis storage, limit 200/min200/min ✅
In a real NestJS project

A typical setup is a generous global limit (it protects against bugs and scrapers, and normal users never notice it), stricter limits on expensive endpoints (search, exports, file uploads) and on sensitive endpoints (login, password reset, which Lesson 10 covers in detail), Redis storage, and @SkipThrottle() for health checks and signed webhooks. Rate limiting in the app is a second layer: large traffic floods should be stopped earlier, at the CDN, WAF or API gateway, before they reach Node.

Common mistakes
  • Writing ttl: 60 thinking it means 60 seconds. Since v5 it is 60 milliseconds; use 60_000.
  • Forgetting trust proxy behind a load balancer, so every user shares one counter and real users get 429s.
  • Setting trust proxy to true, which lets clients fake their IP with an X-Forwarded-For header.
  • Using in-memory storage with several instances and wondering why limits look higher than configured.
  • Throttling health checks, so the orchestrator thinks the app is down and restarts it.
Practice exercise

Configure: a global limit of 100 requests per minute; GET /search limited to 20 per minute; GET /health not throttled. Logged-in users should be tracked by user ID.

Show answer

Interview questions

Why rate limit an API?

To protect shared resources (CPU, database, connection pool) from one client's excessive traffic, to make abuse such as scraping and brute force expensive, and to control cost. It keeps the service fair and available for everyone.

What problems appear when rate limiting across multiple instances?

Each instance keeps its own counter, so the effective limit is multiplied by the number of instances, and counters are lost on restart. The fix is shared storage such as Redis. Behind a proxy you must also configure trust proxy correctly so you track the real client IP.

Should rate limiting be done in the app or in the infrastructure?

Both. The edge (CDN, WAF, gateway) stops large floods before they cost you anything. The app can apply smarter, business-aware limits: per user, per endpoint, per plan.

Remember Use a generous global limit plus strict per-route limits, use milliseconds for ttl, Redis storage for multiple instances, and the real client identity (correct proxy settings or user ID).

Logging

structured logs and correlation IDs

In plain words

Logs are the black box recorder of your app. When something breaks at 3 a.m., they are often the only witness. Structured logs are written as JSON objects ({"level":"error","orderId":42}) instead of free text, so a log tool can search and filter them like a database. A correlation ID is a sticker with a unique number put on each request when it arrives. Every log line written while handling that request carries the same sticker, so you can pull out the whole story of one request from millions of lines.

Interview questions

What is a correlation ID and why is it useful?

A unique ID assigned to each request (or reused from an incoming x-request-id header), attached to every log line produced while handling it and forwarded to downstream services. It lets you reconstruct everything that happened during one request across many log lines and services.

How does nestjs-pino attach the request ID to logs written in a service that doesn't receive the request?

It uses Node's AsyncLocalStorage: the request context is stored when the request starts and stays available through all the async calls made for that request, so the logger can read it without you passing it around.

Why structured (JSON) logs instead of plain text?

Log platforms can index the fields, so you can filter (userId=7), aggregate (errors per minute) and alert reliably, without fragile text parsing.

Remember Log JSON with levels and useful fields, give every request a correlation ID and return it to the client, log each error once, and never log secrets.

Debugging process

reproduce → hypothesize → test → fix → verify

In plain words

Good debugging is like a doctor's diagnosis, not a guessing game. A doctor doesn't prescribe random pills; they reproduce the symptom ("does it hurt when I press here?"), form a hypothesis ("maybe it's the knee ligament"), run a test (an X-ray) that can prove it wrong, apply a fix, and verify at the follow-up visit that the patient is really better. Changing code until the error disappears is not debugging. It often just moves the bug somewhere else.

How it works

Let's walk through a realistic bug. Bug report: "Sometimes customers are charged the wrong total. It happened 3 times this week."

Step 1: Reproduce. Collect facts before touching code: which orders, which request IDs, which version was deployed, what the logs say. Then make the bug happen on your machine, ideally in an automated test, because a bug you can reproduce on demand is half fixed.

Step 2: Hypothesize. Write down a specific, testable explanation, not "something with money". Look at the code with the failing input in mind:

Hypothesis: "JavaScript floating-point arithmetic turns 33.615 into something like 33.6149999…, so rounding goes down instead of up." Good hypotheses predict something you can check.

Step 3: Test the hypothesis. Check it with the smallest possible experiment, using the debugger or a quick log. Don't fix yet.

Floating-point values are indeed imprecise. To see what happens inside the real code path, use the debugger instead of adding console.log everywhere:

Set a breakpoint on the return line, run the failing test with "Debug current Jest test", and inspect total in the Variables panel. You can also add a conditional breakpoint (right-click the line, e.g. discount !== undefined) or a logpoint, which prints a value without editing the code. If the hypothesis is wrong, you go back to step 2 with new information. That is normal, not failure.

Step 4: Fix the root cause, not the symptom.

Step 5: Verify. The failing test now passes. Then go further:

  • Run the whole test suite: did you break anything else?
  • Add more cases around the edge (0 items, 100% discount, many items).
  • Keep the test forever as a regression test.
  • After deploying, check the logs/metrics that revealed the bug: no new wrong totals.
  • Ask "where else could this happen?" (search for Number( on prices across the codebase).

Works locally, 500 in productionMissing env variable: use ConfigService.getOrThrow and validate config at boot

For production-only bugs, rely on the request ID and structured logs from the previous point to reproduce: find the exact input, then copy it into a test.

Common mistakes
  • Changing code before reproducing the bug, so you can never be sure the change fixed it.
  • Changing several things at once. If it works, you don't know which change mattered; if it doesn't, you don't know which one made it worse.
  • Patching the symptom (a special-case if) instead of fixing the cause.
  • Not writing a regression test, so the same bug comes back six months later.
  • Assuming ("the database must be slow") instead of checking with data.
Practice exercise

Bug report: "GET /users/:id sometimes returns 500." Logs show TypeError: Cannot read properties of null (reading 'email') in UsersService.findOne. Write the five steps you would take, with a concrete action for each.

Show answer
  1. Reproduce: find the failing request IDs and their :id values. Notice they are IDs that don't exist (or soft-deleted users). Write a test: GET /users/999999 expects 404, gets 500.
  2. Hypothesize: "findUnique returns null for unknown IDs and the code reads user.email without checking."
  3. Test: set a breakpoint after findUnique with ID 999999 and confirm user === null.
  4. Fix: if (!user) throw new NotFoundException(...). Also enable strictNullChecks if it is off, since the compiler would have caught this.
  5. Verify: the test passes (404), the full suite passes, and after the deploy there are no new 500s on this route in the logs.

Interview questions

Walk me through how you debug a production issue.

Gather facts first: logs by request ID, metrics, the recent deploy, which users are affected. Reproduce it locally or in a test with the same input. Form a specific hypothesis and test it with the debugger or targeted logs. Fix the root cause with a regression test, run the full suite, deploy, and confirm in production metrics that the problem is gone.

Why is reproducing the bug first so important?

Without a reproduction you cannot tell whether your change fixed the bug or the bug just didn't happen this time. A reproducible test case is also the regression test that stops it from coming back.

What is git bisect?

A Git command that binary-searches the commit history between a known good and a known bad commit to find the commit that introduced a bug. With git bisect run it can run a test automatically at each step.

Remember Reproduce first, change one thing at a time, fix the root cause, and leave a regression test behind. Evidence beats guessing.
8

Profiling

find slow queries and slow endpoints

In plain words

Profiling is putting a stopwatch on every part of your system to find where the time actually goes. It's like a slow restaurant: before hiring more cooks, you time each step and discover the kitchen is fast, but there's only one waiter. Developers' guesses about what is slow are wrong surprisingly often. Profiling replaces "I think the JSON serialization is slow" with "92% of the time is one SQL query".

How it works

Work from the outside in: which endpoint is slow → which part of it (database, external API, CPU in Node) → which line or query.

Level 1: time every endpoint. A small interceptor logs the duration of each request. Look at percentiles (p95, p99), not averages: an average of 50ms can hide 5% of users waiting 3 seconds.

(With nestjs-pino, every request log already contains responseTime; in production a metrics tool such as Prometheus or an APM like Datadog/New Relic/Sentry Performance draws the percentile charts for you.)

Level 2: find slow queries. Inside the app, use Prisma's query events to log any query above a threshold:

On the database side, pg_stat_statements is the most valuable tool: PostgreSQL records statistics for every query shape (parameters replaced by $1), across all clients:

Read this carefully: row 1 is slow per call (89ms): run EXPLAIN ANALYZE on it, it probably needs an index. Row 2 is fast per call (0.05ms) but called 4.5 million times: that smells like an N+1 (point 1), and the fix is fewer calls, not a faster query. Sorting by total_exec_time shows you where the database spends its time overall.

Level 3: load test to measure before/after. autocannon (written in Node) sends many concurrent requests and prints percentiles:

Level 4: profile CPU in Node. If the database is fast but the endpoint is still slow, or CPU usage is high, the time is spent in JavaScript. Remember that Node runs your code on one thread (the event loop): one slow synchronous function blocks every request.

In a real NestJS project

A practical profiling routine for a slow endpoint report:

  1. Confirm with numbers: p95 of the route from logs/APM.
  2. Count and time the queries for one request (Prisma query log). Many queries → N+1. One slow query → EXPLAIN ANALYZE + index.
  3. Check external calls (payment, email, other services): log their duration, add timeouts.
  4. If DB + external calls don't add up to the total, CPU-profile the Node process.
  5. Fix one thing, re-run the same autocannon command, and compare numbers in the PR description.
Common mistakes
  • Optimizing code that "looks slow" without measuring. Most of the time goes somewhere else.
  • Looking only at averages. Use p95/p99, which show what your slowest users experience.
  • Load testing against a tiny dev database. Results mean nothing without realistic data volumes.
  • Using synchronous APIs (*Sync, heavy loops, huge JSON.parse) in request handlers, which block the event loop for everyone.
  • Leaving --inspect open on a public port in production. The debugger allows running arbitrary code.

Interview questions

How do you find the slowest queries in a PostgreSQL database?

Enable pg_stat_statements and sort by total_exec_time (overall load) and mean_exec_time (slow per call). Then run EXPLAIN ANALYZE on the top ones. From the app side, log Prisma queries above a duration threshold.

Why are p95/p99 latencies more useful than the average?

Averages hide the tail. A few very slow requests barely move the average but represent real users having a bad experience, and they are often the first sign of contention (locks, pool exhaustion, GC pauses).

What does "blocking the event loop" mean in Node.js?

Node runs JavaScript on a single thread. A long synchronous operation (CPU-heavy loop, *Sync file or crypto call, parsing huge JSON) prevents the event loop from handling any other request until it finishes, so latency rises for every user. You find it with event-loop delay metrics and CPU profiles.

Remember Measure from the outside in (endpoint → database/external calls/CPU → line), use percentiles, and prove every optimization with before/after numbers.
